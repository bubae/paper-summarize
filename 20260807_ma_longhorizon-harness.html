TL;DR

  • 문제: 현재 agent harness들(Claude Code, Codex CLI, OpenClaw)은 (1) 태스크 실행과 태스크 상태 관리가 같은 growing context를 공유해 컨텍스트 자체가 부풀며 state tracking이 어려워지고, (2) executor가 스스로 완료를 판단하는 self-assessment 방식이라 잘못된 판단이 이후 결정에 그대로 전파된다. 결과적으로 long-horizon task에서 compounding errors, context rot, task-state loss 세 병목이 나타난다.
  • 해결: Manage-Execute-Audit (MEA) 루프로 세 역할을 분리한다. Manager가 태스크 상태를 유지하며 subtask contract를 발행, Executor는 fresh context에서 딱 그 contract만 수행, Auditor는 read-only 도구로 환경 상태를 독립 검증. Executor의 raw trajectory는 round마다 폐기하고 auditor report만 축적되어 컨텍스트가 O(rounds) 선형 증가.
  • 왜 작동하는가: (1) State가 execution 외부에 명시적으로 유지되므로 부풀지 않는다. (2) Independent audit이 executor의 잘못된 완료 주장을 걸러내 error propagation을 차단. (3) Fresh-context executor는 context rot에서 벗어난다. (4) 모든 backend(Claude Code, Codex, OpenClaw)를 AgentAdapter로 감싸 native loop 그대로 활용 가능.
  • 비유: 전통적인 agent는 프리랜서 한 명이 모든 것을 자기 메모에 적으며 스스로 검사하고 다음 일을 계획하는 방식. LongHorizon-Harness는 PM(Manager), 실무자(Executor), 감사관(Auditor) 3인 팀으로 나누고, 실무자는 매 라운드 새로운 방에서 지시서만 받아 일하고, 감사관은 실무자의 자기평가를 못 보고 결과물만 검증한다.

핵심 기여 (Key Contributions)

  1. Long-horizon execution을 task-state management 문제로 재정의: 단일 growing trajectory 대신 명시적 외부 태스크 상태와 environment-verified fact만으로 다음 subtask를 결정하는 문제 설정.
  2. ##Manage-Execute-Audit 루프##: 세 역할(관리·실행·감사)을 fresh context, 독립 도구 접근, 역할별 environment 권한 등으로 구조적으로 분리. Executor의 self-assessment가 task state에 들어오지 못하도록 아키텍처 레벨에서 차단.
  3. AgentAdapter 인터페이스: Claude Code, Codex CLI, OpenClaw 등 서로 다른 agent framework를 수정 없이 executor/auditor backend로 활용. Multi-backend, multi-model 실험을 통일된 프로토콜로 수행.
  4. 3개 최신 long-horizon 벤치마크에서 SOTA: Qwen 3.7-Plus 백본으로 WeaveBench PassRate 51.8% → 80.7%, Terminal-Bench 2.1 69.7% → 77.2%, OSWorld 2.0 binary completion 2.8% → 8.3% (3×). Claude Opus 4.7에서도 34-task subset에서 20.0% → 34.3% (+14.3점).
  5. Agent capability는 model + harness의 시스템 속성이라는 실증적 명제: 같은 모델(Qwen 3.7-Plus)이 harness에 따라 mean score 0.524 → 0.733까지 변동. 강한 모델(Opus 4.7)조차 harness가 성능의 결정적 변수.

배경: 왜 이 시점에 필요한가

Long-horizon agent의 3가지 병목

METR (Kwa et al., 2026) 보고에 따르면 최전선 agent의 task-completion horizon이 약 7개월마다 두 배가 되고 있다. 프론티어 코딩 agent는 이미 단일 프로젝트에서 수 시간~수 일간의 자율 작업을 지속할 수 있으나, 이 긴 horizon이 자동으로 실행 신뢰성을 보장하지는 않는다. 저자들은 3가지 병목을 정리한다:

  1. Compounding errors and goal drift: 초기 잘못된 결정이 뒤로 축적되어 결과적으로 원래 목표에서 이탈. (Sun et al., 2026)
  2. Context rot: 상호작용 이력이 커지면서 중요 정보 검색이 어려워지고, context utilization이 특정 threshold를 넘으면 성능이 급락. (Liu et al., 2024; Hong et al., 2025)
  3. Task-state loss: 만족해야 할 requirement, 이미 완료한 action, 생성한 artifact, 발견한 fact 등을 정확히 추적·유지·업데이트하지 못함.

기존 harness의 두 가지 구조적 한계

(i) Task execution과 task-state management가 같은 growing context를 공유한다. Claude Code, Codex CLI 등은 agent가 하나의 확장되는 대화 context 안에서 실행과 상태 유지를 동시에 수행한다. Execution history가 커질수록 state가 이 안에 묻혀서 tracking이 어려워진다.

(ii) Task execution과 completion assessment가 결합되어 있다. Agent가 subtask를 수행한 뒤 스스로 완료 여부를 판단한다. 이 판단이 잘못되면 완료 처리된 상태로 task state에 기록되어, 이후 결정의 전제가 된다. Self-assessment 오류는 조기 발견 없이 downstream으로 전파.

LongHorizon-Harness의 방법론 (Section 2)

2.1 Overview

Long-horizon task $\mathcal{T}$와 computer environment가 주어졌을 때, LongHorizon-Harness는 태스크를 동적으로 결정되는 라운드의 시퀀스로 실행한다. 각 라운드는 Manage-Execute-Audit (MEA) 루프를 따른다:

Round i: S_i (현재 task state), e_{i-1} (환경), V_{i-1}=(v_1,...,v_{i-1}) (audit history) ↓ [Manager] c_i ← 다음 subtask contract 구성 (S_i, T, V_{i-1} 참조; 환경에 직접 접근 불가) ↓ [Executor] (e_i, o_i) ← contract c_i를 fresh context에서 수행 (예산 20 turns / 1800s, e_{i-1} → e_i 변경) ↓ [Auditor] v_i ← e_i를 read-only 검사, executor 궤적/추론 무시 ↓ [Manager] S_{i+1} ← S_i에 v_i의 검증 사실만 반영 종료 조건: v_i가 T를 만족하고 integrity violation 없음, 또는 어떤 허용 subtask도 남은 requirement를 진전시키지 못함, 또는 사용자 입력 필요, 또는 라운드 예산 소진.

핵심 특징: ##오직 태스크 상태와 audit report만이 라운드 간에 지속##된다. Executor의 raw interaction trajectory는 매 라운드 종료 시 폐기되어 컨텍스트가 부풀지 않는다.

2.2 Manager

Manager는 persistent task state의 유일한 소유자이며 다음 control decision을 만든다:

$$(S_{i+1}, q_{i+1}, c_{i+1}) = \Phi_{\text{mgr}}(\mathcal{T}, S_i, V_i) \tag{1}$$

$q_{i+1} \in \{\text{EXECUTE}, \text{DONE}, \text{BLOCKED}, \text{ASK}\}$. Contract $c_{i+1}$은 EXECUTE일 때만 반환.

Task state의 구조: 3가지 record type으로 구성:

  • requirement: 원 태스크에서 유도된 objective/constraint
  • artifact: 실행 중 생성/수정된 output
  • fact: 이후 subtask에 필요한 환경 정보

각 record는 completed, pending, blocked, untrusted 중 하나로 표시되며 audit evidence 참조를 유지한다. Executor의 주장만으로 상태가 바뀌지 않는다 — clean audit evidence가 있어야만 completed로 표시된다.

Next-subtask construction: Manager는 $S_{i+1}$을 원 태스크와 비교해 진행 가능한 unresolved objective를 선택, dependency와 prerequisite를 확인한 뒤 bounded contract $c_{i+1}$을 구성. Contract는 즉시 goal, acceptance criteria, boundary constraints, 관련 task-state records, 관련 prior audit reports를 포함한다. Contract는 필요한 environment transition에 따라 GUI 또는 CLI executor에 라우팅.

2.3 Executor

Executor는 환경을 의도적으로 수정할 수 있는 유일한 역할이다. Round $i$에서:

$$(e_i, o_i) = \Phi_{\text{exec}}(\mathcal{T}, S_i, c_i; e_{i-1}) \tag{2}$$

Executor는 원 task $\mathcal{T}$, 현재 태스크 상태 $S_i$, subtask contract $c_i$, contract가 참조하는 prior audit report들만 받는다. 환경을 $e_{i-1}$ → $e_i$로 변화시키고 execution report $o_i$를 반환. $o_i$는 수행한 행동, 결과 상태, 생성 artifact, 발생 이슈를 요약하지만 contract 완료를 확립하지 않는다 — 이는 auditor가 판단.

Fresh-context execution: 각 executor 호출은 이전 라운드의 raw trajectory 없이 시작한다. 에피소드 내부에서는 planning, environment interaction, observation, revision을 여러 사이클 반복할 수 있으나, 에피소드 종료 시 raw trajectory와 internal reasoning은 폐기되고 $o_i$만 auditor에 전달.

GUI vs CLI capability boundaries:

  • GUI executor: 스크린샷, 클릭, 스크롤, 텍스트 입력 등 화면 기반 능력. Application/interface state 중심의 transition 담당.
  • CLI executor: shell 실행, 파일 편집, 코딩, 테스팅 등. Workspace/process/program state 중심의 transition 담당.

Backend execution: AgentAdapter를 통해 Claude Code, Codex CLI, OpenClaw 같은 기존 backend를 수정 없이 bounded episode로 실행. 저자들은 backend의 내부 실행 프로세스를 대체하지 않고 제공되는 context, tools, environment permissions, execution budget, returned report만 제어한다.

2.4 Auditor

Auditor는 executor가 만든 environment state를 독립적으로 검증. 실행 후 다음을 받는다: 원 태스크 $\mathcal{T}$, 태스크 상태 $S_i$, contract $c_i$, contract가 참조하는 prior audit report들, executor report $o_i$. Executor의 raw trajectory나 internal reasoning은 받지 않는다. Auditor는 결과 환경 $e_i$를 검사해:

$$v_i = \Phi_{\text{aud}}(\mathcal{T}, S_i, c_i, o_i; e_i) \tag{3}$$

Independent environment inspection: Auditor는 fresh context에서 시작해 executor의 궤적을 배제한다. $o_i$를 힌트로 관련 파일/윈도우/로그/프로세스를 찾을 수 있으나, 완료 결정은 환경을 goal, acceptance criteria, boundary constraints와 직접 비교해서 결정. GUI auditor는 observation-oriented 상호작용으로 검사, CLI auditor는 non-mutating 명령과 inspection 도구로 검사.

Read-only authority: Auditor는 필요시 observation view를 바꿀 수 있으나 task-relevant environment state를 수정할 수 없다. Protected artifact를 편집/덮어쓰기/이동/삭제하거나 state-changing 명령을 실행하거나 결과에 영향을 주는 GUI 액션을 수행할 수 없다. Task-relevant workspace와 artifact state가 감사 중 감시되며, 감지된 mutation은 integrity violation으로 기록되고 결과 report는 completed 상태를 지지할 수 없다.

Audit-result construction: audit report $v_i$는 3가지 상태를 기록:

  • Completion status: complete, incomplete, blocked
  • Integrity status: clean, suspect, violation
  • Task-state updates: verified facts, supporting evidence, remaining gaps

실험 결과 (Section 3)

Setup

Primary backbone: Qwen-3.7-Plus. 추가로 Claude Opus 4.7 평가. 각 backbone마다 원본 Claude Code evaluation framework와 LongHorizon-Harness(Claude Code를 execution backend로 사용)를 비교. Manager, executor, auditor는 같은 backbone model로 인스턴스화되어 harness 효과와 model 능력을 분리.

Implementation: Executor 예산 1800s, manager/auditor 예산 300s each. 최대 MEA 라운드 $N_{\max}=25$.

Benchmarks:

  • WeaveBench (Li et al., 2026): 114 tasks. GUI+CLI 상호작용 조합.
  • OSWorld 2.0 (Yuan et al., 2026): 108 desktop workflows. 중앙값 human completion time 1.6시간.
  • Terminal-Bench 2.1 (Merrill et al., 2026): 어려운 커맨드라인 태스크.

Task-dependent effectiveness (Figure 6)

Category별 개선폭이 크게 다르다:

  • WeaveBench 최대 이득: Design +60.0점, Spatial/3D +50.0점. Desktop 도메인은 이미 83.3%라 개선폭이 5.6점으로 작다.
  • OSWorld 2.0 최대 이득: streaming interaction, human-in-the-loop, tutorial following.
  • Terminal-Bench 최대 이득: system-administration, game tasks. 반면 짧은 분석 category 몇 개는 개선이 작거나 regression.

패턴: 개선이 큰 category는 공통적으로 여러 dependent environment state를 확장 궤적에 걸쳐 preserve, inspect, revise해야 하는 태스크. 개선이 작은 것들은 individual model capability(visual perception, math reasoning, coding, algorithm design)이 병목인 태스크. Auditor는 잘못된 결과는 감지할 수 있지만 모델에 없는 능력을 공급하지는 못한다.

태스크: WebRTC simulcast-layer audit.
Baseline (0.59): Wireshark의 "Decode As" 다이얼로그가 unresponsive임을 인식하지만, growing execution history에 이 관찰이 묻힌 채 같은 상호작용을 400+ steps 반복. 예산 소진까지 남은 태스크 증거를 수집하지 못함.
LH (0.92): 실패한 상호작용과 unresolved evidence gap을 task state에 기록. 이후 executor들이 누락된 simulcast-layer chart와 packet-level evidence에 집중. 실패 궤적이 아닌 최신 audit 상태에서 recovery 재개.

Case 2: Apparent Completion 감사 (Figure 8, DOC_task_2)

태스크: LibreOffice에서 문서 heading style 정규화.
Baseline (0.00): 문서 XML을 직접 편집해 시각적으로 그럴듯한 결과를 만든 뒤 종료. 그러나 LibreOffice workflow를 사용하지 않았고 실제 style이 적용되지 않음.
LH (0.89): 규정된 GUI workflow로 heading style을 적용, 문서를 페이지별로 다시 검사. Auditor가 XML을 파싱해 15개 heading 모두 요구 style이 확인됨을 검증.

태스크: Calc VLOOKUP 수식 수리, before-and-after evidence 보존.

Case 4: Verified Progress 지속 (Figure 10, WEB_task_10)

태스크: Lighthouse performance-optimization.
Baseline (0.53): Core optimization 완료 후 DevTools evidence 수집에서 stuck. Growing session이 DevTools 조작을 계속 해야 하며 예산 소진.
LH (0.85): 완료된 optimization을 task state에 유지. Fresh-context executor들이 페이지 상태 확인, script structure 검사, performance trace 수집을 분산 수행. 완료된 optimization이 execution history 밖에 있어 이후 executor들이 reconstruct하지 않아도 됨.

비판적 분석 (Critical Analysis)

강점

  • Model-agnostic 실증의 힘: Qwen 3.7-Plus와 Claude Opus 4.7 모두에서 개선을 보였다는 점이 접근의 일반성을 강하게 뒷받침.
  • Backend-agnostic: Claude Code, Codex CLI, OpenClaw를 수정 없이 executor로 사용. 실무자가 기존 tool을 버리지 않고 도입 가능.
  • Case study의 구체성: 4개 case에서 baseline과 LH의 궤적을 스크린샷 단위로 비교. 왜 개선이 나오는지 mechanistic하게 설명.
  • Independent auditor의 개념적 우아함: Executor의 self-assessment 오류가 task state에 스며들지 못하도록 아키텍처 레벨에서 차단. 이는 테스트 이론에서 self-testing의 근본적 한계를 우회하는 방식.
  • Context 선형 증가 보장: Executor raw trajectory 폐기로 O(rounds) 성장. Long-horizon task에서 context rot 병목을 구조적으로 해결.

한계와 의문점

  • Token cost 증가: Qwen에서 3.6× (OSWorld) ~ 3.2× (Games) 증가. Terminal-Bench 예외를 제외하면 대체로 비용 상승. Cost-normalized 성능(품질/토큰) 관점의 분석이 부족.
  • Auditor 비용의 큰 비중: 총 토큰의 19~38%가 auditor. Independent verification의 값은 명확하지만 이 비율이 최적인지 조사 안됨. 더 저렴한 auditor(smaller model)로 대체 가능한지 미검증.
  • Manager/Executor/Auditor 모두 같은 backbone: 이는 harness 순수 효과를 분리하려는 실험 설계지만, 실무에서 각 역할에 최적화된 다른 모델을 쓰면 어떻게 되는지 조사 없음. Manager는 planning 모델, Executor는 tool-use 강한 모델, Auditor는 verification 강한 모델로 mix하는 자연스러운 확장이 부재.
  • Task-dependent effectiveness의 원인 분석 부족: 개선이 큰 category(Design +60)와 작은 category(coding 강한 요구) 구분은 명확하나, 왜 그런지 정량 지표로 예측 가능한 것은 아니다. 새 태스크에 LH가 도움될지 판단하는 rule of thumb이 부재.
  • Contract 설계 heuristics의 불투명성: Manager가 어떻게 subtask contract를 구성하는지의 프롬프트/heuristics 세부가 논문에 부족. 재현성에는 코드가 있지만, 원리 수준의 설명이 얕음.
  • OSWorld의 부분 점수 8.3%는 여전히 낮다: 3× 개선은 인상적이지만 절대값 8.3%는 대부분 태스크에서 실패함을 의미. Human 완료 시간 중앙값 1.6h인 태스크의 어려움을 감안해도, harness만으로는 넘지 못하는 벽이 존재.
  • Auditor collusion 가능성: Executor와 auditor가 같은 모델이라 유사한 blind spot을 공유. 예컨대 GUI reasoning 오류를 executor가 하면 같은 model의 auditor도 놓칠 수 있다. Adversarial auditor(다른 model family)의 유효성 미검증.

실무 관점 트레이드오프

  • Weaker model에는 큰 이득, 비용도 큼: Qwen에서 3× 토큰 증가로 3× 성능 상승. Cost/quality trade-off가 명확.
  • Stronger model에서는 token 절약도 가능: Opus에서 33% 토큰 감소하며 성능 상승. 강한 모델일수록 LH가 pure win.
  • 도메인 dependent: 시각/공간/디자인 태스크에는 큰 이득, 순수 알고리즘/coding 태스크에는 작은 이득. Deployment 전 sample task로 예상 이득 측정 필요.

Key Takeaways: 이 논문에서 가져갈 것

  • Agent capability는 model + harness의 시스템 속성: 같은 모델도 harness에 따라 20~30점 변동. 이는 agent 연구에서 harness는 종속변수가 아니라 독립변수라는 강력한 재정의.
  • Task-state를 execution 외부로 빼내라: Growing context의 자기 관리에 의존하지 말고, 명시적 외부 state + independent audit으로 유지해야 long-horizon reliability가 확보된다.
  • Executor의 self-assessment를 task state에 넣지 말라: 잘못된 판단이 downstream으로 전파되는 것을 아키텍처 레벨에서 차단하는 것이 최선.
  • Fresh-context executor 원칙: 매 라운드 raw trajectory 폐기로 context rot 회피. 이는 long agent session의 근본 병목을 해결하는 실용 기법.
  • Auditor는 model에 없는 능력을 만들지 못한다: harness는 execution reliability를 크게 개선하지만, 코드/수학/알고리즘 근본 능력이 부족하면 도움이 제한적. Application category에 따라 도입 여부 결정.
  • AgentAdapter 패턴: 서로 다른 agent framework를 감싸는 얇은 adapter로 상호 호환. 향후 harness 실험의 표준 패턴이 될 수 있다.
  • Weaker model에서 harness ROI가 가장 크다: Qwen 3.7-Plus가 harness만 바꿔 Opus 4.7 + base harness를 능가. 오픈 모델 배포에 특히 매력적.
