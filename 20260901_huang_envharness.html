목차

TL;DR

  • 문제: LLM 에이전트는 환경과 상호작용하며 배우는데, ##그 환경들은 손으로 만들어졌고 정적이다## — 에이전트의 약점에 눈이 멀어 있고, 에이전트가 개선되면 금세 뒤처진다. 이 경직성이 학습을 두 가지로 제한한다: ⑴ 특정 에이전트의 약점을 겨냥한 신호를 주지 못하고, ⑵ 에이전트가 기존 과제를 다 풀고 나면 더 가르칠 것이 없다. 최근의 환경 생성 연구는 이를 해결하려 하지만 도메인 특정 파이프라인을 요구하고, 비싸거나 신뢰할 수 없는 verifier에 의존하며, 여전히 정적인 환경을 만들어 낸다.
  • 해결: EnvHarness — 정적 환경을 감싸서 내부 로직을 전혀 건드리지 않고 그 동작을 재구성하는 플러그인 컴포넌트의 프로그래밍 가능한 층. 표준 reset/step 인터페이스를 통해서만 작동하므로 도메인 무관하고, ##재구성된 모든 환경이 원래의 verifier를 그대로 물려받는다##. 세 컴포넌트: Stage(에피소드 시작 상태), Contract(허용 행동·관측·전이), Chain(여러 환경을 이어 확장 에피소드 구성). 자동화를 위해 EnvRigger를 도입한다 — 정책을 블랙박스로 취급하고, 실행 궤적을 관찰해 진단된 결함을 겨냥한 컴포넌트를 합성하고, 새 rollout으로 검증한다.
  • 왜 작동하는가: 두 개의 분리가 핵심이다. ⑴ 인터페이스 경계에서만 개입하므로 verifier가 보존된다 — LLM이 전이와 성공 판정을 시뮬레이션하는 생성 방식(GenEnv)의 환각·평가 드리프트를 원천 차단한다. ⑵ 정책을 조건으로 환경을 재구성하므로 학습 신호가 항상 능력 경계에 놓인다 — 무조건적 환경 확장은 이미 할 줄 아는 것을 반복시키지만, 진단 기반 재구성은 지금 못 하는 것을 겨냥한다.
  • 결과: 4개 도메인 5개 벤치마크(ALFWorld, WebArena, SWE-bench Verified, OfficeQA, SpreadsheetBench)에서 원본 환경과 도메인 특화 생성 파이프라인 모두를 능가한다 — ##held-out 인스턴스에서 최대 9.0점 개선, 실행 스텝은 9.8% 감소##. RL에서도 최대 6.5점 개선. 그리고 ##환경 수를 300개까지 늘릴 때 실제 환경과 생성 환경은 평평해지는데 EnvHarness만 계속 오른다## (47.67 → 54.79).
  • 비유: 같은 교과서로 모든 학생을 가르치는 대신, 교과서는 그대로 두고 문제 출제 방식만 바꾸는 것이다 — 이 학생이 늘 건너뛰는 단계를 못 건너뛰게 막고, 이미 완료된 앞부분은 미리 채워 주고, 두 단원을 이어 붙여 끈기를 시험한다. 채점 기준은 교과서의 것을 그대로 쓰므로 ##난이도를 바꿔도 채점의 신뢰도는 떨어지지 않는다##.

핵심 기여 (Key Contributions)

  1. EnvHarness — 환경 쪽 harness 패러다임의 제안: agent harness가 frozen LLM을 자율 에이전트로 만드는 것과 정확히 대칭적으로, 정적 환경을 제어 가능한 환경으로 만드는 프로그래밍 가능한 층. 형식적으로 환경 $E = (\mathcal{S}, \mathcal{A}, \mathcal{O}, T, R, s_0)$에 대한 환경 무관 변환 $w$로 정의되며 $E' = w(E)$. ##변환은 인터페이스 수준에서만 일어나므로 시뮬레이터 백엔드와 구현 세부를 건드리지 않고, 따라서 ground-truth 평가 로직이 보존된다##.
  2. 세 가지 구체적 컴포넌트: ⑴ Stage $w_{stage,\delta}$ — 상태 조작 행동열 $\delta$를 reset()이 만든 $s_0$에 적용해 시작점을 바꾼다. ⑵ Contract $w_{contract,r}$ — 변환 맵 삼중항 $r = (f_A, f_T, f_O)$로 행동 공간·전이 역학·관측 공간을 다시 쓴다. ⑶ Chain $w_{chain,\ell}$ — 추가 환경 $E_{ext}$와 합성 로직 $g$로 확장 에피소드를 만든다. ##세 컴포넌트가 같은 인터페이스를 공유하므로 자유롭게 합성되지만, 비가환적이다($w_1 \circ w_2 \neq w_2 \circ w_1$)##.
  3. EnvRigger — task-policy-conditioned 자동 커스터마이징: 과제-정책 조건부 사상 $\mathcal{H}$를 실현하는 4단계 자율 루프 — Observe(베이스라인 rollout $K{=}5$ 수집) → Diagnose(근본 원인 식별 + 방향 결정) → Write(컴포넌트 합성) → Validate(새 rollout $K{=}5$로 accept/reject/refine). ##결정적으로 정책이 완벽하게 성공하면 "환경이 너무 관대하다"고 진단하고 더 어렵게 만든다## — 난이도 조절이 양방향이다.
  4. verifier 보존이라는 구조적 안전장치: 보상 축 $R$은 설계자에게 노출되지 않는다. 설계자 prompt가 명시한다 — "R 축은 노출되지 않는다. 성공은 벤치마크 자신의 판정이므로, 보상을 재구성해서 평가 지표를 움직일 수 없다." Chain의 합성 판정도 $R' = R_A \wedge R_B$로, 각 항이 해당 하위 환경의 자체 verifier가 내린 것이다.
  5. 도메인 무관성의 실증: 7개 Bridge가 4가지 이질적 런타임 클래스(순수 인메모리 게임, 텍스트 어드벤처 엔진, 인스턴스별 Docker 컨테이너, Playwright 브라우저)를 하나의 ActionableEnv 계약으로 흡수하며, ##Bridge 위의 모든 것(정책 루프·오케스트레이터·컴포넌트 코드)이 7개 환경에서 문자 그대로 공유된다##.
  6. skill 학습과 RL 양쪽에서의 검증: skill-based learning에서 held-out 최대 +9.0점(ALFWorld OOD), SWE-bench Verified에서 스텝 5.40 감소. RL(GRPO, Qwen3-8B-base)에서 4개 지표 중 3개 개선. 그리고 도메인 특화 생성 베이스라인(GenEnv, VeriEnv, SWE-smith)을 그들이 적용 가능한 모든 곳에서 능가한다.
  7. 환경 스케일링에서의 co-evolution: 동일 예산에서 환경 수를 300개까지 늘리면 ##EnvHarness는 47.67 → 54.79(+7.12점)로 계속 오르는 반면 원본 환경은 52.13, 생성 환경은 50.37에서 평평해진다##. EnvHarness만이 이미 축적된 skill을 장착한 정책을 겨냥해 다음 배치를 합성하기 때문이다.
  8. 목표 지정 가능성: 자율 진단 외에 명시적 사용자 제약도 받는다. 정량 목표(성공률을 $[0.4, 0.6]$ 밴드로) 지정 시 밴드 내 과제 비율이 ##6.0% → 80.0%##로 오르고, 자연어로 서술한 능력 약점("테스트를 돌리지 않고 패치를 제출한다")을 주면 그것을 치명적으로 만드는 Contract를 작성해 낸다.

배경 — 왜 "환경 쪽" harness인가

1. 학습의 원천이 텍스트에서 환경으로 이동했다

출발 관측: LLM이 자율 에이전트로 배치되면서 학습의 원천이 큐레이션된 텍스트 데이터에서 상호작용 환경으로 옮겨 갔다. 웹 페이지를 탐색하든, 코드베이스의 이슈를 해결하든, 임바디드 플랫폼을 제어하든, 에이전트는 각자의 환경에서 학습 신호를 얻는다. 환경은 상호작용 상대로서 네 가지 일을 한다 — 특정 과제를 제시하고, 변하는 상태를 관리하고, 행동에 반응하고, 성공을 평가한다.

왜 문제인가: 그런데 이런 환경을 만들려면 상호작용 로직과 verifier를 하드코딩하는 상당한 인간 노력이 든다. 그 결과 환경은 경직되게 정적이 되고, ##어떤 에이전트가 상호작용하든, 그 에이전트가 얼마나 개선되었든 동일하게 행동한다##. 이 경직성이 학습을 두 가지 근본적 방식으로 제한한다:

  1. 특정 에이전트의 약점을 겨냥한 신호를 주지 못한다 (Dennis+ 2020, Jiang+ 2021의 unsupervised environment design 문제의식)
  2. 에이전트가 기존 과제를 풀 줄 알게 되면 더 가르칠 것이 없다 (Beukman+ 2024, Wang+ 2019의 open-ended learning 문제의식)

2. 핵심 유추 — agent harness의 거울상

agent harness란: LLM을 감싸 자율 에이전트를 만드는 소프트웨어 층이다 — 실행 루프, 도구 레지스트리, 컨텍스트 관리. ##Agent = Model + Harness##이며, 결정적으로 모델 가중치를 바꾸지 않고 새 능력을 더한다. Anthropic의 "Effective harnesses for long-running agents"(2025), "Harness design for long-running application development"(2026), OpenAI의 Codex 관련 문헌, 그리고 Meng+ 2026의 서베이가 이 개념을 정착시켰다.

이 논문의 착상: 같은 아이디어를 ##에이전트–환경 루프의 반대편##에 적용한다. EnvHarness는 기존 정적 환경을 감싸 커스터마이징 가능한 환경으로 만드는 프로그래밍 가능한 층이다 — ##Customized Env = Static Env + EnvHarness##. 커스터마이징은 표준 인터페이스를 통과하는 정보 흐름을 수정함으로써 이뤄지며, 기저 환경은 완전히 손대지 않는다.

3. 기존 대안 — 환경 생성(environment generation)의 두 한계

환경을 손으로 만드는 것이 비싸기 때문에, 상당수 연구가 자동 환경 생성으로 향했다. 논문은 이 계열의 한계를 두 가지로 정리한다.

4. verifier 신뢰 사슬 — 이 논문의 가장 구조적인 주장

왜 중요한가: 환경을 바꾸면 채점도 바꿔야 하는가가 이 분야의 핵심 난제다. 새 과제를 만들면 그 과제의 정답도 만들어야 하고, 정답을 LLM이 만들면 그 정답이 틀릴 수 있다. EnvHarness의 설계는 이 문제를 해결하는 것이 아니라 발생하지 않게 한다.

직관적으로 말하면: 시험 문제를 새로 출제하면 채점 기준도 새로 만들어야 하지만, ##기존 문제를 그대로 두고 "풀이 조건"만 바꾸면 채점 기준은 손댈 필요가 없다##. 머그컵을 서랍에 숨겨도 "깨끗한 머그컵이 책상 위에 있는가"라는 채점 기준은 그대로다. 어렵게 만들었지만 채점의 신뢰도는 1도 떨어지지 않았다.

§2.1 형식화 — EnvHarness 패러다임

환경의 정의: 논문은 환경을 6-튜플로 모델링한다.

$$E = (\mathcal{S},\ \mathcal{A},\ \mathcal{O},\ T,\ R,\ s_0)$$

여기서 $\mathcal{S}$는 상태 공간, $\mathcal{A}$는 행동 공간, $\mathcal{O}$는 관측 공간, $T: \mathcal{S} \times \mathcal{A} \to \mathcal{S}$는 상태와 행동을 다음 상태로 보내는 전이 함수, $R$은 verifier가 유도하는 보상, $s_0$는 초기 상태다.

EnvHarness 컴포넌트의 정의: 환경 무관 변환(environment-agnostic transformation) $w$이다.

$$E' = w(E), \qquad E' = (\mathcal{S}',\ \mathcal{A}',\ \mathcal{O}',\ T',\ R',\ s_0') \tag{1}$$

$w$는 ##환경을 엄격히 인터페이스 수준에서만 재구성하며, 기저 시뮬레이터 백엔드나 구현 세부를 수정하지 않는다##. 구체적으로 초기 상태($s_0'$)를 커스터마이징하고, 노출되는 공간($\mathcal{A}'$, $\mathcal{O}'$)을 필터링하고, 전이 역학($T'$)을 갱신한다. 모든 개입이 외부에 머물기 때문에 ground-truth 평가 로직이 보존되고, 원본 verifier가 여전히 에피소드를 채점할 수 있다.
