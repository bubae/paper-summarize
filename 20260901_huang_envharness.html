목차

TL;DR

  • 문제: LLM 에이전트는 환경과 상호작용하며 배우는데, ##그 환경들은 손으로 만들어졌고 정적이다## — 에이전트의 약점에 눈이 멀어 있고, 에이전트가 개선되면 금세 뒤처진다. 이 경직성이 학습을 두 가지로 제한한다: ⑴ 특정 에이전트의 약점을 겨냥한 신호를 주지 못하고, ⑵ 에이전트가 기존 과제를 다 풀고 나면 더 가르칠 것이 없다. 최근의 환경 생성 연구는 이를 해결하려 하지만 도메인 특정 파이프라인을 요구하고, 비싸거나 신뢰할 수 없는 verifier에 의존하며, 여전히 정적인 환경을 만들어 낸다.
  • 해결: EnvHarness — 정적 환경을 감싸서 내부 로직을 전혀 건드리지 않고 그 동작을 재구성하는 플러그인 컴포넌트의 프로그래밍 가능한 층. 표준 reset/step 인터페이스를 통해서만 작동하므로 도메인 무관하고, ##재구성된 모든 환경이 원래의 verifier를 그대로 물려받는다##. 세 컴포넌트: Stage(에피소드 시작 상태), Contract(허용 행동·관측·전이), Chain(여러 환경을 이어 확장 에피소드 구성). 자동화를 위해 EnvRigger를 도입한다 — 정책을 블랙박스로 취급하고, 실행 궤적을 관찰해 진단된 결함을 겨냥한 컴포넌트를 합성하고, 새 rollout으로 검증한다.
  • 왜 작동하는가: 두 개의 분리가 핵심이다. ⑴ 인터페이스 경계에서만 개입하므로 verifier가 보존된다 — LLM이 전이와 성공 판정을 시뮬레이션하는 생성 방식(GenEnv)의 환각·평가 드리프트를 원천 차단한다. ⑵ 정책을 조건으로 환경을 재구성하므로 학습 신호가 항상 능력 경계에 놓인다 — 무조건적 환경 확장은 이미 할 줄 아는 것을 반복시키지만, 진단 기반 재구성은 지금 못 하는 것을 겨냥한다.
  • 결과: 4개 도메인 5개 벤치마크(ALFWorld, WebArena, SWE-bench Verified, OfficeQA, SpreadsheetBench)에서 원본 환경과 도메인 특화 생성 파이프라인 모두를 능가한다 — ##held-out(학습에 쓰이지 않은 보류) 인스턴스에서 최대 9.0점 개선, 실행 스텝은 9.8% 감소##. RL(reinforcement learning)에서도 최대 6.5점 개선. 그리고 ##환경 수를 300개까지 늘릴 때 실제 환경과 생성 환경은 평평해지는데 EnvHarness만 계속 오른다## (47.67 → 54.79).
  • 비유: 같은 교과서로 모든 학생을 가르치는 대신, 교과서는 그대로 두고 문제 출제 방식만 바꾸는 것이다 — 이 학생이 늘 건너뛰는 단계를 못 건너뛰게 막고, 이미 완료된 앞부분은 미리 채워 주고, 두 단원을 이어 붙여 끈기를 시험한다. 채점 기준은 교과서의 것을 그대로 쓰므로 ##난이도를 바꿔도 채점의 신뢰도는 떨어지지 않는다##.

핵심 기여 (Key Contributions)

  1. EnvHarness — 환경 쪽 harness 패러다임의 제안: agent harness가 frozen LLM을 자율 에이전트로 만드는 것과 정확히 대칭적으로, 정적 환경을 제어 가능한 환경으로 만드는 프로그래밍 가능한 층. 형식적으로 환경 $E = (\mathcal{S}, \mathcal{A}, \mathcal{O}, T, R, s_0)$에 대한 환경 무관 변환 $w$로 정의되며 $E' = w(E)$. 변환은 인터페이스 수준에서만 일어나므로 시뮬레이터 백엔드와 구현 세부를 건드리지 않고, 따라서 ground-truth 평가 로직이 보존된다.
  2. 세 가지 구체적 컴포넌트: ⑴ Stage $w_{stage,\delta}$ — 상태 조작 행동열 $\delta$를 reset()이 만든 $s_0$에 적용해 시작점을 바꾼다. ⑵ Contract $w_{contract,r}$ — 변환 맵 삼중항 $r = (f_A, f_T, f_O)$로 행동 공간·전이 역학·관측 공간을 다시 쓴다. ⑶ Chain $w_{chain,\ell}$ — 추가 환경 $E_{ext}$와 합성 로직 $g$로 확장 에피소드를 만든다. 세 컴포넌트가 같은 인터페이스를 공유하므로 자유롭게 합성되지만, 비가환적이다($w_1 \circ w_2 \neq w_2 \circ w_1$).
  3. EnvRigger — task-policy-conditioned 자동 커스터마이징: 과제-정책 조건부 사상 $\mathcal{H}$를 실현하는 4단계 자율 루프 — Observe(베이스라인 rollout $K{=}5$ 수집) → Diagnose(근본 원인 식별 + 방향 결정) → Write(컴포넌트 합성) → Validate(새 rollout $K{=}5$로 accept/reject/refine). 결정적으로 정책이 완벽하게 성공하면 "환경이 너무 관대하다"고 진단하고 더 어렵게 만든다 — 난이도 조절이 양방향이다.
  4. verifier 보존이라는 구조적 안전장치: 보상 축 $R$은 설계자에게 노출되지 않는다. 설계자 prompt가 명시한다 — "R 축은 노출되지 않는다. 성공은 벤치마크 자신의 판정이므로, 보상을 재구성해서 평가 지표를 움직일 수 없다." Chain의 합성 판정도 $R' = R_A \wedge R_B$로, 각 항이 해당 하위 환경의 자체 verifier가 내린 것이다.
  5. 도메인 무관성의 실증: 7개 Bridge가 4가지 이질적 런타임 클래스(순수 인메모리 게임, 텍스트 어드벤처 엔진, 인스턴스별 Docker 컨테이너, Playwright 브라우저)를 하나의 ActionableEnv 계약으로 흡수하며, Bridge 위의 모든 것(정책 루프·오케스트레이터·컴포넌트 코드)이 7개 환경에서 문자 그대로 공유된다.
  6. skill 학습과 RL 양쪽에서의 검증: skill-based learning에서 held-out 최대 +9.0점(ALFWorld OOD, out-of-distribution — 학습 시 보지 못한 객체–수납처 구성), SWE-bench Verified에서 스텝 5.40 감소. RL(GRPO, Qwen3-8B-base)에서 4개 지표 중 3개 개선. 그리고 도메인 특화 생성 베이스라인(GenEnv, VeriEnv, SWE-smith)을 그들이 적용 가능한 모든 곳에서 능가한다.
  7. 환경 스케일링에서의 co-evolution: 동일 예산에서 환경 수를 300개까지 늘리면 EnvHarness는 47.67 → 54.79(+7.12점)로 계속 오르는 반면 원본 환경은 52.13, 생성 환경은 50.37에서 평평해진다. EnvHarness만이 이미 축적된 skill을 장착한 정책을 겨냥해 다음 배치를 합성하기 때문이다.
  8. 목표 지정 가능성: 자율 진단 외에 명시적 사용자 제약도 받는다. 정량 목표(성공률을 $[0.4, 0.6]$ 밴드로) 지정 시 밴드 내 과제 비율이 6.0% → 80.0%로 오르고, 자연어로 서술한 능력 약점("테스트를 돌리지 않고 패치를 제출한다")을 주면 그것을 치명적으로 만드는 Contract를 작성해 낸다.

배경 — 왜 "환경 쪽" harness인가

1. 학습의 원천이 텍스트에서 환경으로 이동했다

출발 관측: LLM이 자율 에이전트로 배치되면서 학습의 원천이 큐레이션된 텍스트 데이터에서 상호작용 환경으로 옮겨 갔다. 웹 페이지를 탐색하든, 코드베이스의 이슈를 해결하든, 임바디드 플랫폼을 제어하든, 에이전트는 각자의 환경에서 학습 신호를 얻는다. 환경은 상호작용 상대로서 네 가지 일을 한다 — 특정 과제를 제시하고, 변하는 상태를 관리하고, 행동에 반응하고, 성공을 평가한다.

왜 문제인가: 그런데 이런 환경을 만들려면 상호작용 로직과 verifier를 하드코딩하는 상당한 인간 노력이 든다. 그 결과 환경은 경직되게 정적이 되고, 어떤 에이전트가 상호작용하든, 그 에이전트가 얼마나 개선되었든 동일하게 행동한다. 이 경직성이 학습을 두 가지 근본적 방식으로 제한한다:

  1. 특정 에이전트의 약점을 겨냥한 신호를 주지 못한다 (Dennis+ 2020, Jiang+ 2021의 unsupervised environment design 문제의식)
  2. 에이전트가 기존 과제를 풀 줄 알게 되면 더 가르칠 것이 없다 (Beukman+ 2024, Wang+ 2019의 open-ended learning 문제의식)

2. 핵심 유추 — agent harness의 거울상

agent harness란: LLM을 감싸 자율 에이전트를 만드는 소프트웨어 층이다 — 실행 루프, 도구 레지스트리, 컨텍스트 관리. Agent = Model + Harness이며, 결정적으로 모델 가중치를 바꾸지 않고 새 능력을 더한다. Anthropic의 "Effective harnesses for long-running agents"(2025), "Harness design for long-running application development"(2026), OpenAI의 Codex 관련 문헌, 그리고 Meng+ 2026의 서베이가 이 개념을 정착시켰다.

이 논문의 착상: 같은 아이디어를 에이전트–환경 루프의 반대편에 적용한다. EnvHarness는 기존 정적 환경을 감싸 커스터마이징 가능한 환경으로 만드는 프로그래밍 가능한 층이다 — Customized Env = Static Env + EnvHarness. 커스터마이징은 표준 인터페이스를 통과하는 정보 흐름을 수정함으로써 이뤄지며, 기저 환경은 완전히 손대지 않는다.

3. 기존 대안 — 환경 생성(environment generation)의 두 한계

환경을 손으로 만드는 것이 비싸기 때문에, 상당수 연구가 자동 환경 생성으로 향했다. 논문은 이 계열의 한계를 두 가지로 정리한다.

4. verifier 신뢰 사슬 — 이 논문의 가장 구조적인 주장

왜 중요한가: 환경을 바꾸면 채점도 바꿔야 하는가가 이 분야의 핵심 난제다. 새 과제를 만들면 그 과제의 정답도 만들어야 하고, 정답을 LLM이 만들면 그 정답이 틀릴 수 있다. EnvHarness의 설계는 이 문제를 해결하는 것이 아니라 발생하지 않게 한다.

직관적으로 말하면: 시험 문제를 새로 출제하면 채점 기준도 새로 만들어야 하지만, 기존 문제를 그대로 두고 "풀이 조건"만 바꾸면 채점 기준은 손댈 필요가 없다. 머그컵을 서랍에 숨겨도 "깨끗한 머그컵이 책상 위에 있는가"라는 채점 기준은 그대로다. 어렵게 만들었지만 채점의 신뢰도는 1도 떨어지지 않았다.

§2.1 형식화 — EnvHarness 패러다임

환경의 정의: 논문은 환경을 6-튜플로 모델링한다.

$$E = (\mathcal{S},\ \mathcal{A},\ \mathcal{O},\ T,\ R,\ s_0)$$

여기서 $\mathcal{S}$는 상태 공간, $\mathcal{A}$는 행동 공간, $\mathcal{O}$는 관측 공간, $T: \mathcal{S} \times \mathcal{A} \to \mathcal{S}$는 상태와 행동을 다음 상태로 보내는 전이 함수, $R$은 verifier가 유도하는 보상, $s_0$는 초기 상태다.

EnvHarness 컴포넌트의 정의: 환경 무관 변환(environment-agnostic transformation) $w$이다.

$$E' = w(E), \qquad E' = (\mathcal{S}',\ \mathcal{A}',\ \mathcal{O}',\ T',\ R',\ s_0') \tag{1}$$

$w$는 환경을 엄격히 인터페이스 수준에서만 재구성하며, 기저 시뮬레이터 백엔드나 구현 세부를 수정하지 않는다. 구체적으로 초기 상태($s_0'$)를 커스터마이징하고, 노출되는 공간($\mathcal{A}'$, $\mathcal{O}'$)을 필터링하고, 전이 역학($T'$)을 갱신한다. 모든 개입이 외부에 머물기 때문에 ground-truth 평가 로직이 보존되고, 원본 verifier가 여전히 에피소드를 채점할 수 있다.

§2.2 세 가지 컴포넌트

전제: 수식 (1)의 사상 $w$는 일반 인터페이스를 정의하며, 이 인터페이스를 따르는 어떤 변환이든 유효한 EnvHarness 컴포넌트다. 논문은 세 가지 구체적 유형을 제시하는데, 이는 환경 커스터마이징의 세 가지 근본 모드를 커버하도록 선택된 것이며 저자들은 "더 많은 것이 뒤따를 것으로 기대한다"고 명시한다.

이 절의 러닝 예제: 논문은 하나의 ALFWorld 과제 "put a clean mug on the desk"(깨끗한 머그컵을 책상에 놓기)로 세 컴포넌트를 전부 설명한다. 기본 인스턴스는 머그컵이 훤히 보이는 곳에 있고, 놓는 순간 에피소드가 끝난다. 이 두 성질이 각각 Stage와 Chain의 공략 지점이 된다.

Stage — 초기 상태를 바꾼다

정의: Stage $w_{stage,\delta}$는 상태 조작 행동열 $\delta = (a_1, \ldots, a_k)$로 지정된다. 이 행동들은 reset()이 만들어 낸 초기 상태 $s_0$에 적용된다:

$$E' = w_{stage,\delta}(E) = (\mathcal{S}, \mathcal{A}, \mathcal{O}, T, R, s_0'), \quad \text{where } s_0' = T(\cdots T(T(s_0, a_1), a_2) \cdots, a_k) \tag{2}$$

이 변환 하에서 오직 초기 상태만 바뀐다. Stage는 에이전트의 출발점을 커스터마이징하는데, 두 방향 모두 가능하다 — ⑴ 특정 skill을 요구하는 장애물을 도입하거나, ⑵ 초기 하위 목표를 미리 완료해 과제 지평을 단축한다.

직관적으로 말하면: 수식 (2)에서 결정적인 것은 새 상태를 주입하는 것이 아니라 환경 자신의 전이 함수 $T$를 k번 호출해서 도달한다는 점이다. 그래서 $s_0'$는 항상 reachable state다 — 환경 규칙상 도달 불가능한 상태가 만들어질 수 없고, 벤치마크 특정 상태 스키마가 아니라 환경 자신의 행동 어휘로 표현된다. 저장 형태도 행동 리스트 그 자체일 뿐이다.

Contract — 상호작용을 다시 쓴다

정의: Contract $w_{contract,r}$는 변환 맵 삼중항 $r = (f_A, f_T, f_O)$로 지정되며, 각각은 기본적으로 항등 함수다. 이 맵들이 행동 공간·전이 역학·관측 공간을 각각 다시 쓴다:

$$E' = w_{contract,r}(E) = (\mathcal{S}, \mathcal{A}', \mathcal{O}', T', R, s_0), \quad \text{where } (\mathcal{A}', \mathcal{O}', T') = \big(f_A(\mathcal{A}),\ f_O(\mathcal{O}),\ f_T(T)\big) \tag{3}$$

실무에서 이 변환들은 세 가지 일을 한다 — 행동 사전조건 강제, 관측 증강 또는 마스킹, 특정 결과에 구조화된 피드백 부착. 수식에서 $\mathcal{S}$, $R$, $s_0$가 변하지 않는다는 점에 주목할 것 — Contract는 매 스텝의 입출력만 손댄다.

직관적으로 말하면: Contract는 환경과 정책 사이에 앉은 미들웨어다. 정책이 무엇을 할 수 있는지($f_A$), 그 행동이 어떤 응답을 받는지($f_T$), 세계가 어떻게 보이는지($f_O$)를 재정의한다. 여기서 agent harness와의 비대칭이 드러나는데 — agent harness는 능력을 더하지만, Contract는 능력을 빼기도 한다. 순간이동 명령을 제거하고 관측을 절단하는 것은 환경을 더 불편하게 만드는 일이며, 그것이 정확히 목적이다.

Chain — 환경을 확장한다

정의: Chain $w_{chain,\ell}$은 쌍 $\ell = (E_{ext}, g)$로 지정된다. 여기서 $E_{ext}$는 추가 환경, $g$는 합성 로직이다. 합성 로직은 원 환경 $E$와 $E_{ext}$를 같은 인터페이스로 노출되는 복합 환경 $E'$로 결합한다:

$$E' = w_{chain,\ell}(E) = (\mathcal{S}', \mathcal{A}', \mathcal{O}', T', R', s_0'), \quad \text{where } E' = g(E, E_{ext}) \tag{4}$$

교차 환경 결합을 허용하기 위해 새 공간들은 단순히 기저 환경들의 합집합이다 (예: $\mathcal{A}' = \mathcal{A} \cup \mathcal{A}_{ext}$). 합성 로직 $g$는 제약이 없어서 환경들을 이어 붙이거나, 교차시키거나, 중간 결과에 따라 동적으로 분기시킬 수 있다.

그리고 결정적으로 복합 보상은:

$$R' = R_A \wedge R_B$$

각 항이 해당 하위 환경 자신의 verifier가 내린 판정이므로, evaluate()는 두 하위 과제가 모두 성공했을 때만 성공하고, 체인된 과제는 두 부모로부터 신뢰받는 검증을 물려받는다.

합성 — 그리고 비가환성

모든 EnvHarness 컴포넌트가 같은 인터페이스를 공유하므로 자유롭게 합성된다. 러닝 예제인 머그컵 과제에 Stage·Contract·Chain을 쌓으면 하나의 복합 환경이 나온다:

$$E' = w_{chain,\ell}\Big(w_{contract,r}\big(w_{stage,\delta}(E)\big)\Big) \tag{5}$$

이 설정에서 $w_{stage,\delta}$는 머그컵을 서랍에 숨겨 공간 탐색을 강제하고, $w_{contract,r}$은 관측을 두 문장으로 절단해 부분 관측성을 시험하며, $w_{chain,\ell}$은 후속 과제를 이어 붙여 목표 지속성을 시험한다.

중요한 단서: 논문은 이 변환들이 비가환적(non-commutative)임을 명시한다 — $w_1 \circ w_2 \neq w_2 \circ w_1$. 중첩 순서가 결과 환경이 어떻게 구성되는지, 그리고 어떤 제약이 초기화 시점에 적용되고 어떤 것이 능동적 상호작용 중에 적용되는지를 결정한다.

§3 에이전트 학습을 위한 EnvHarness

3.1 문제 설정 — 왜 정책 조건부여야 하는가

목표: 기저 과제 집합을 지원하는 기저 환경 $E$와 타깃 정책 에이전트 $\pi$가 주어졌을 때, 특정 과제 $t$에 맞춰진 수정 환경 $E'$를 자동 생성하는 것이다. 그 $E'$는 $\pi$ 고유의 결함을 노출시켜 표적화된 정책 개선을 촉진해야 한다.

핵심 구별: 논문은 여기서 미묘하지만 중요한 구분을 한다.

단일 EnvHarness 컴포넌트는 그 자체로 정책 무관(policy-agnostic)하다 — 수식 (1)이 $w$를 환경만의 변환으로 정의하므로, 같은 컴포넌트를 수정 없이 어떤 정책에도 적용할 수 있다. 반대로 이 컴포넌트들의 선택과 파라미터화는 기저 과제 $t$와 관찰된 정책 $\pi$의 행동 둘 다에 조건화되어야 한다.

그래서 과제-정책 조건부 사상 $\mathcal{H}$를 도입한다:

$$E' = \mathcal{H}(E, t;\ \pi) = (w_k \circ w_{k-1} \circ \cdots \circ w_1)(E) \tag{6}$$

각 $w_i$는 기저 환경 $E$를 감싸 과제 $t$에서의 $\pi$의 결정적 약점을 노출하도록 커스터마이징된 컴포넌트다. 내부 모델 가중치를 들여다보는 대신, 이 컴포넌트들은 에이전트를 블랙박스로 취급하고 오직 그 출력에만 작용해 꾸준한 교정 학습 신호를 만든다.

3.2 EnvRigger — Observe / Diagnose / Write / Validate

전체 흐름: EnvRigger는 과제 $t$에서 환경에 $\pi$를 실행하고, 결과 궤적을 분석하고, 이 과제를 위한 구체적 EnvHarness 컴포넌트를 작성하고, 새 정책 rollout으로 커스터마이징된 환경을 검증한다. 적절한 학습 신호를 제공하는 후보는 수용되고, 그렇지 않은 후보의 컴포넌트는 기각되거나 수정된다.

중요한 가정: Stage가 도입하는 초기 상태 변형이 신뢰성 있게 재현되려면, 기저 환경이 검증 단계에서 결정론적 reset을 지원해야 한다. 이것이 부록 H가 "구속 제약(binding constraint)은 reset이다"라고 말하는 지점이다.

Diagnose의 양방향성 — 너무 쉬워도 문제다

이 설계가 왜 특별한가: 대부분의 curriculum 방법은 "어려우면 쉽게"만 한다. EnvRigger는 반대 방향도 한다. 논문의 서술을 그대로 옮기면:

고전하는 정책에 대해서는 목표가 빠진 단계를 scaffold하고 과제를 단순화하는 것이다. 반대로 ##정책이 완벽한 성공률을 달성하면, 이는 현재 환경이 남은 약점을 드러내기에 너무 관대하다는 뜻이다. 이 시나리오에서 EnvRigger는 환경이 더 어려워져야 한다고 진단하고, 정책의 잠재적 결함을 밖으로 끌어내는 더 도전적인 시나리오를 주입하는 쪽으로 커스터마이징을 전환한다.##

§4 실험

4.1 실험 설정

초점: 본문은 주로 skill-based learning (SL) 패러다임에 집중한다 — 환경에서 skill을 추출해 에이전트 능력을 개선하는 방식이다. online RL (online reinforcement learning, 온라인 강화학습) 패러다임에서의 호환성과 성능은 §5 분석의 일부로 제시된다.

4.2 주요 결과

이 절이 답하려는 세 질문: ⑴ 재구성된 환경에서 뽑은 skill이 원본 환경에서 뽑은 것보다 나은가? ⑵ 하나의 인터페이스가 정말 모든 도메인에서 작동하는가, 그리고 도메인 특화 생성 파이프라인을 이기는가? ⑶ 효과가 성공률뿐 아니라 효율에서도 나타나는가?

결과 ⑴ — 정적 환경이 못 하는 곳에서 일관된 이득: EnvHarness가 커스터마이징한 환경에서 획득한 skill이 모든 벤치마크에서 원본 환경에서 추출한 것을 능가하며, ALFWorld에서 최대 9.0점 개선이다.

그리고 반대 방향의 발견: ##정적 기저 환경에서 skill을 추출하면 오히려 성능이 떨어질 수 있다##. SpreadsheetBench에서 무변형 환경의 skill은 no-skill 베이스라인보다 낮고(45.88 vs 46.44), SWE-bench Verified에서는 실행 궤적을 오히려 늘린다(55.01 vs 53.58). 논문의 설명: "정적 환경은 에이전트가 이미 실행하는 행동만 연습하게 하므로 그 특정 한계를 다루지 못하고, 종종 중복되거나 차선인 skill을 검색하게 된다." 대조적으로 EnvRigger의 write-and-validate 루프는 새 정책 궤적으로 검증된 컴포넌트만 커밋하므로, EnvHarness는 모든 벤치마크에서 no-skill 베이스라인을 상회한다.

결과 ⑵ — 도메인 무관 인터페이스를 통한 일반화: 기저 인터페이스 프로토콜, EnvRigger 루프, skill 추출 파이프라인이 5개 벤치마크 전부에서 일관되게 적용되며, 환경마다 필요한 것은 도메인 특화 prompt 템플릿뿐이다. 반면 특화 생성 베이스라인은 각자의 타깃 벤치마크에 갇혀 있다 (Table 2·3의 "–" 표시).

그럼에도 EnvHarness는 이들이 적용 가능한 곳에서 일관되게 능가한다:

  • ALFWorld: GenEnv를 평균 5.7점, OOD 설정에서 8.5점 앞선다. 논문의 진단 — "일반적 인스턴스 생성은 정책 약점을 다루지 않은 채 반복 연습만 늘린다."
  • SWE-bench Verified: 목적 특화된 SWE-smith를 성공률에서 2.46점 앞서면서 에피소드당 실행 스텝은 5.11 적게 쓴다.

결론: "통합 인터페이스를 통해 진단된 취약점을 겨냥하는 것이, 도메인 특화 생성으로 학습 에피소드 양을 늘리는 것보다 우월함이 입증된다."

결과 ⑶ — 낭비 행동을 고쳐 효율을 높인다: SWE-bench Verified에서 EnvHarness 환경의 skill은 에피소드당 평균 스텝을 53.6 → 49.6으로 줄이는 반면, 무변형 환경의 skill은 오히려 55.0으로 늘린다. 그리고 이 효율 이득이 어디서 오는지를 논문이 특정한다 — EnvRigger의 구체적 진단과 직접 상관된다: 반복 행동 루프를 깨고 장황한 관측을 걸러 내도록 설계된 Contract와 Stage가 실행 궤적을 성공적으로 단축시켰다.

표준편차를 이용한 재분석 — 논문에 없는 확인

왜 이 분석이 가능한가: 이 논문은 앞선 harness 연구들과 달리 3회 독립 실행의 평균과 표준편차를 전부 보고한다. 이것은 드물고 좋은 실천이며, 동시에 독자가 직접 검정을 해 볼 수 있게 해 준다. 아래는 보고된 평균·표준편차로 이 문서가 계산한 근사 신뢰구간이다.

해석 — 균형 있게: 14개 비교 중 6개가 0을 넘지 않는 구간을 갖는다. 이것을 "논문이 과장했다"로 읽으면 부정확하다. ⑴ $n=3$은 검정력이 매우 낮다 — 구간이 0을 포함한다는 것은 "효과가 없다"가 아니라 "3회로는 확정할 수 없다"는 뜻이다. ⑵ 14개 지표 중 14개 전부가 양의 방향이라는 사실 자체가 강한 증거다 (부호 검정만으로도 $p = 2^{-14} \approx 0.00006$). ⑶ 논문은 표준편차를 숨기지 않고 전부 보고했다.

다만 실무적으로 유의할 지점은 있다: SWE-bench Verified 성공률($+2.70 \pm 6.02$)이 유의 구간에 들지 않는데, Figure 1·5·6과 Table 9가 전부 이 지표로 논증한다. 즉 논문의 가장 시각적으로 인상적인 세 그림(스케일링 곡선, 크로스 모델 막대)이 모두 분산이 큰 지표 위에 서 있다. 스케일링 실험의 추세(계속 오르는 vs 평평해지는)는 개별 점의 유의성보다 강한 증거이므로 이 지적이 그 결론을 뒤집지는 않지만, 개별 수치를 인용할 때는 주의가 필요하다.

§5 분석

논문은 EnvHarness를 다섯 축으로 분석한다 — ⑴ RL 학습 신호로서의 호환성, ⑵ 표준 데이터셋 확장 대비 스케일링 효율, ⑶ 정책 모델 계열·강도에 걸친 전이성(OOD, out-of-distribution 전이 포함), ⑷ 장기 지평 환경에서 Chain의 고유 가치, ⑸ EnvRigger가 명시적 사용자 지정 목표를 받아들이는 능력.

⑴ EnvHarness가 더 나은 RL을 가능하게 한다

실험 의도: skill 학습을 넘어, EnvHarness가 커스터마이징한 환경이 online RL에서 능동적 학습 신호를 제공할 수 있는가? 이는 재구성된 환경이 보조 데이터가 아니라 독립적 최적화 신호인지를 묻는 질문이다.

설정: ALFWorld와 WebShop에서 Qwen3-8B-base를 정책으로 쓰고 GRPO (Group Relative Policy Optimization)로 최적화한다. 두 정책을 학습시킨다 — 하나는 원본 정적 환경만으로, 다른 하나는 전부 EnvHarness로 재구성된 환경으로. 그리고 같은 held-out 인스턴스에서 평가한다.

⑵ Chain이 장기 지평 과제를 효율적으로 풀게 한다

실험 의도: 실세계 응용은 종종 에이전트가 확장된 지평에서 작동하기를 요구한다. Chain은 무작위로 짝지어진 두 base 환경을 하나의 확장 에피소드로 결합해 이를 다룬다. 효과를 분리하기 위해 이 짝짓기는 자율 EnvRigger 루프와 독립적으로 작동한다 — §4.1이 밝혔듯 Chain은 자동 파이프라인에서 제외되는데, EnvRigger가 결합된 환경의 내부 상태를 관찰하기 어렵기 때문이다. 평가는 표준 단일 환경 테스트 인스턴스에서 한다.

Chain 환경에서만 나오는 skill (부록 F.3): 부록은 Chain 궤적에서 증류된 대표 skill 두 개를 싣는데, 둘 다 과제가 이어붙었을 때만 나타나는 행동이라는 점이 Table 5의 결과(성공률은 소폭 낮고 평균 스텝은 크게 개선)를 직접 설명한다.

  • "Manage shared step budgets across joined tasks" — 이어붙은 과제 구조를 하나의 유한한 예산으로 취급하고, 두 번째 과제에 충분한 자원을 남기기 위해 첫 과제에서는 "충분히 좋은" 해법을 우선한다. 부록이 든 실제 궤적: 에이전트가 첫 과제(pytest의 _makepath 이슈)를 효율적으로 해결해 두 번째 과제(scikit-learn의 RidgeClassifierCV)에서 마주친 상당한 환경 설정 난관(의존성 문제, 순환 import, 누락 속성)을 감당할 스텝을 보존했다. 부록의 표현 — "두 번째 과제를 희생하면서 첫 과제를 과최적화하지 않는 것의 중요성을 보여 준다."
  • "Re-orient environment after task handoff" — 새 과제를 받으면 즉시 환경 정찰(conda env list, which python)을 수행해 올바른 테스트 러너와 환경 설정을 확인한다. 저장소마다 다르기 때문이다. 실제 궤적: matplotlib에서 django로 전환할 때 이전 환경의 pytest·python 경로가 유효하다고 가정할 수 없음을 인식하고, django 저장소가 별도의 runtests.py와 다른 conda 환경 경로를 요구함을 알아내 "command not found" 에러를 피했다.

이 두 skill이 Table 5를 설명한다: 둘 다 성공률을 직접 올리는 요령이 아니라 낭비를 줄이는 요령이다 — 첫 과제 과최적화 방지와 핸드오프 직후 정찰은 모두 "쓸데없이 오래 걸리는 것"을 막는다. 그래서 Chain 단독 skill이 성공률은 49.63으로 원본(49.88)과 사실상 같은데 평균 스텝은 53.58에서 41.96으로 급감한다. 그리고 이 skill들은 단일 환경 테스트 인스턴스에서 평가되었을 때도 유효하다 — 이어붙은 과제에서 배운 예산 관리 습관이 단일 과제에도 옮겨 간다는 뜻이다.

⑶ 효율적인 환경 스케일링 — co-evolution

실험 의도: 이 논문의 가장 중요한 주장을 검증하는 실험이다. "환경을 더 많이 주면 더 좋아진다"는 환경 스케일링 계열의 전제가 어디까지 참인가를 묻는다. 동일 예산 아래 세 배분 전략을 비교한다 — EnvHarness 환경 / 무변형 벤치마크 환경 / SWE-smith 생성 환경.

고정한 것: 정책 모델, 환경 예산, skill 검색 프로토콜. 50개 환경 배치마다 skill bank 1개를 만들고(뱅크당 2~3개를 번갈아, 300개에서 총 15개 skill).

결정적 차이: 두 베이스라인은 환경 배치를 학습자와 무관하게 뽑는 반면, EnvHarness는 이전까지 축적된 skill을 장착한 정책을 겨냥해 각 배치를 합성한다 — 환경과 정책이 공진화(co-evolve)한다.

결과: EnvHarness는 47.67에서 54.79까지 오르며(+7.12점) 300개 지점에서도 여전히 상승 궤적을 유지한다. 같은 예산으로 원본 환경은 52.13, 생성 환경은 50.37에 그친다. 논문의 결론: "이 성능 격차는 학습자의 현재 능력 경계를 겨냥하는 것이 무조건적 환경 확장보다 근본적으로 더 효과적임을 확인한다."

부수적 관찰 (부록 F.2): 각 라운드의 skill이 초점을 옮긴다 — 기본 테스트 호출과 파일 편집 → 러너 자체가 망가졌을 때 테스트 루프를 살려 두기 → 인터프리터 해석과 편집 전 탐색. 그리고 라운드마다 이득이 줄어드는데, 남은 결함이 점점 더 국소적이 되기 때문이다.

⑷ 서로 다른 LLM 백본에 걸친 일반화

실험 의도: 이 루프가 특정 모델에서만 작동하는 것은 아닌가? SWE-bench Verified에서 네 모델을 시험한다 — Gemini 3.1 Flash-Lite, Qwen3.6 27B, Gemini 3.5 Flash, Claude Sonnet 4.6. open-weight와 proprietary를 아우르고 능력 스펙트럼이 넓다. 각 설정에서 정책과 EnvRigger에 같은 백본을 쓰고 추출 파이프라인과 프로토콜은 그대로 둔다.

결과: EnvHarness skill이 네 정책 모두에서 실제 환경 skill을 능가하며, 그 폭은 2.7 ~ 3.7 절대점이다 — skill 없는 성공률이 30.7에서 67.2까지 넓게 퍼져 있는데도 그렇다.

논문의 핵심 관찰: ##이 이득의 크기는 기저 정책이 얼마나 강한지와 대체로 무관하다 — 커스터마이징 루프는 가장 약한 모델에서 무너지지도, 가장 강한 모델에서 포화하지도 않으며, 같은 파이프라인·prompt·수용 기준이 내내 쓰인다. 정책의 능력 수준이 바꾸는 것은 루프의 적용 가능성이 아니라 진단의 내용인 것으로 보인다.##

단, 상대적으로는 약한 모델이 더 이득을 본다: 논문 자신이 밝힌다 — 두 가장 약한 정책이 skill이 아예 없는 것 대비 가장 큰 도움을 받는다 (EnvHarness는 +9.3, +11.1점, 무변형 환경은 +6.1, +7.4점, 반면 두 강한 모델은 5.5점 미만). 즉 skill 학습 자체의 가치는 모델이 강해질수록 줄지만, EnvHarness가 원본 환경 대비 더하는 몫(2.7~3.7점)은 유지된다. 이 두 진술이 서로 다른 것을 말한다는 점이 중요하다.

⑸ 요구에 따라 환경을 만들어 낸다

실험 의도: EnvRigger 루프는 표준 설정에서 행동 진단을 통해 자율적으로 학습 목표를 식별한다. 그런데 같은 기계가 명시적 사용자 정의 제약도 받아들일 수 있는가? 두 종류의 제약을 검증한다.

두 번째 제약 — 자연어로 서술한 능력 약점: 예컨대 "정책이 실패하는 테스트를 돌리지 않고 패치를 제출해서 수정이 검증되지 않은 채로 남는다"를 주면, EnvRigger가 테스트를 돌리지 않으면 코드 제출을 거부하는 Contract를 생성한다. 그 환경에서 수집한 궤적에서 증류된 skill은 §Contract의 그림에서 이미 본 Verification-Driven Development Loop다. 부록 G Table 13은 이런 사례 9개를 정리하며, 설계자가 지시 없이 스스로 컴포넌트 축을 골랐다 — Stage로 시작 상태를 꾸미고, Contract의 행동 필터로 지름길을 막고, Contract의 전이 훅으로 결과를 위조했다. 모든 컴포넌트가 소스 분포 안에 머물고 목표와 채점기는 건드리지 않는다.

비판적 분석

같은 계절의 두 "harness" — Life-Harness와 나란히 놓고 보기

2026년 여름 harness 연구가 급증하면서 같은 단어가 정반대 대상을 가리키게 되었다. 이 요약 시리즈의 앞선 논문인 Life-Harness (arXiv:2605.22166)와 이 논문을 나란히 놓으면 그 대칭이 선명해진다 — 그리고 두 논문 모두 "Contract"라는 단어를 쓰는데 뜻이 다르다.

강점

  1. verifier 보존을 정책이 아니라 구조로 달성한다. 이 논문의 가장 견고한 설계 결정이다. "설계자에게 $R$ 축을 노출하지 않는다"는 것은 규칙이 아니라 기계적 봉쇄이며, 그 결과 난이도 조절과 채점 신뢰도가 완전히 분리된다. 환경 생성 계열이 과잉 생성·필터링으로 사후 대응하는 문제를 발생시키지 않는다.
  2. 도메인 무관성이 수사가 아니라 구현으로 입증된다. 7개 Bridge가 4가지 서로 다른 런타임 클래스(인메모리 게임, TextWorld 엔진, Docker 컨테이너, Playwright 브라우저)를 흡수하고, Bridge 위의 모든 코드가 문자 그대로 공유된다. 그리고 이것이 가능한 이유가 명확히 서술된다 — get_env_state()가 런타임 핸들 없는 순수 데이터만 노출하기 때문이다.
  3. 같은 백본 통제. EnvRigger와 정책이 같은 모델이므로 이득이 "더 강한 외부 모델의 증류"에서 올 수 없다. 이 통제가 없는 self-improvement 논문이 흔한 점을 감안하면 중요한 미덕이다.
  4. 3회 실행의 평균과 표준편차를 전부 보고한다. Table 2·3의 모든 셀에 표준편차가 붙어 있다. 이는 harness·환경 연구에서 드물며, 독자가 직접 검정할 수 있게 해 준다 — §신뢰구간 재분석이 가능했던 이유다. 표준편차를 숨겼다면 그 재분석 자체가 불가능했다.
  5. 토큰 비용을 분해해 보고한다 (Table 11). "우리 방법이 더 좋다"는 주장에 "그리고 베이스라인과 같은 예산을 쓴다"(WebArena 137.3M vs 137.8M)를 붙인다. 더 쓰는 경우(ALFWorld 3.5배)도 그 차액이 무엇을 사는지(LLM 시뮬레이션 대신 실제 실행)를 설명한다.
  6. 두 학습 패러다임에서 검증한다. skill 기반 학습(§4)과 online RL(§5)에서 모두 작동함을 보인다. 재구성된 환경이 "더 나은 학습 자료"일 뿐 아니라 gradient가 흐르는 최적화 신호임을 보이는 것은 범주가 다른 주장이다.
  7. 불편한 결과를 숨기지 않는다. ALFWorld OOD의 RL 하락(−0.8), leave-one-out의 heat 회귀(−8.7), Chain 단독의 SR 하락(49.63 < 49.88)이 전부 표에 실려 있다. 부록 F.4는 한 발 더 나아가 "평균 스텝만으로는 품질을 알 수 없다"고 자기 지표를 비판한다.
  8. 부록의 재현성 자산이 이례적으로 충실하다. 설계자 prompt 전문, 클래스 구조, 인터페이스 프로토콜, Chain 구현 예시, 벤치마크 분할, 하이퍼파라미터, 9개 지정 약점 사례, 코드 명명 대응표까지. 코드도 google-research 조직에서 공개된다.

한계와 의문점

  1. $n=3$에서 14개 비교 중 6개만 신뢰구간이 0을 넘지 않는다. §신뢰구간 재분석에서 계산했듯 SWE-verified SR($+2.70 \pm 6.02$), OfficeQA EM·F1, WebArena Reddit·GitLab·Avg, 그리고 ALFWorld In-Dist($+2.90 \pm 4.51$)와 SpreadsheetBench Mean Score($+1.01 \pm 1.04$)까지 8개가 구간에 0을 포함한다. 부호가 14/14 양수라는 점이 강한 방증이므로 "효과가 없다"는 결론은 부당하지만, 개별 수치를 인용할 때는 주의해야 한다 — 특히 §환경 스케일링과 §크로스 모델이 전부 SWE SR로 논증한다는 점이 마음에 걸린다.
  2. "적용 가능한 모든 곳에서 특화 베이스라인을 능가한다"는 하위 도메인 수준에서는 성립하지 않는다. WebArena GitLab에서 EnvHarness(37.7)가 VeriEnv(38.9)보다 낮다. 평균(41.6 vs 39.6)에서는 이기지만, 논문의 서술("consistently outperforms")은 이 셀을 덮지 못한다.
  3. 합성 순서 문제가 정의되지 않았다. §2.2가 비가환성($w_1 \circ w_2 \neq w_2 \circ w_1$)을 명시하고 부록 E.3이 후보당 컴포넌트 수에 상한을 두지 않는데, 설계자가 순서를 어떻게 정하는지 서술이 없고 순서 ablation도 없다. $k$개 컴포넌트면 원리상 $k!$가지 환경이 가능하다. 부록 C.3이 체크포인트에 "innermost first" 순서를 기록한다고 밝히므로 순서는 분명히 상태의 일부다.
  4. "환경당 1회 비용"이 실제로는 "정책×환경당 1회"에 가깝다. §3.1이 스스로 밝히듯 컴포넌트 선택은 정책에 조건화된다. 부록 H의 완화 논거("학습 에피소드마다가 아니라 환경마다 한 번")는 같은 정책을 계속 학습시킬 때만 성립한다. 모델을 교체하면 루프를 다시 돌려야 하고, 이는 §Life-Harness 비교에서 본 "한 번 진화한 harness가 17개 백본에 전이" 같은 성질과 대비된다.
  5. 환경 수율(yield)이 한 번밖에 보고되지 않고, 그 한 번이 우려스럽다. 부록 E.3에 따르면 write–validate 루프가 5회 안에 수용되지 못하면 그 인스턴스는 아무 컴포넌트도 내지 않는다. 유일한 수치가 부록 F.2 라운드 3에 있는데 — ##학습 과제의 약 1/3에서 라운드 2 정책이 모든 베이스라인 rollout에 성공하자 EnvRigger가 "더 어렵게" 방향을 잡았지만, 그 후보들이 전부 validation에서 기각되어(성공률이 그대로거나 0으로 떨어져) 수정 예산을 소진했고 그 과제들은 라운드 3 뱅크에 아무 기여도 하지 못했다##. 즉 정책이 강해질수록 루프가 실패하는 실패 모드가 자기 부록에 기록되어 있다. 벤치마크·라운드 전반의 수율은 여전히 보고되지 않으므로 §Table 11의 토큰 비용을 성공한 환경당 비용으로 환산할 수 없다.
  6. Chain 실험이 자동 파이프라인 밖에 있다. §4.1이 밝히듯 EnvRigger가 결합 환경의 내부 상태를 관찰하기 어려워 Chain을 제외했고, §5의 Chain 실험은 두 base 환경을 무작위로 짝지은 것이다. 따라서 Table 5의 인상적인 결과(AS 41.96, 조합 시 SR 54.30)는 자동화된 방법의 성과가 아니라 사람이 설정한 조건의 성과다. 부록 H·I가 인정하는 "의미적 관련성을 알 방법이 없다"는 한계와도 이어진다.
  7. 목표가 겹치는 UED 계열과 실험적으로 비교하지 않았다. §6.1이 Dennis+ 2020(unsupervised environment design), Jiang+ 2021(prioritized level replay), Wang+ 2019(POET)를 인용하며 "손 설계 curriculum과 다르다"고 구별하지만, §4의 베이스라인은 전부 생성 계열(①③④)이다. "난이도를 학습자 경계에 맞춘다"는 목표는 UED 계열의 핵심 목표이기도 하므로, 같은 벤치마크에서의 비교가 있었다면 기여가 훨씬 선명했을 것이다.
  8. RL 실험이 단일 seed다. Table 2·3은 3회 반복 표준편차를 보고하는데 부록 F.1은 random seed = 0 고정 단일 실행이다. RL은 seed 분산이 크기로 악명 높으므로, Table 4의 WebShop SR +1.4 같은 차이는 근거로 삼기 어렵다. 환경 2개·모델 1개라는 규모도 §4의 5개 벤치마크와 층위가 다르다.
  9. skill 추출 파이프라인이 고정 변수다. 모든 결과가 ReasoningBank 방식의 추출을 통과한 뒤 관측된 것이다. 다른 추출 방식(또는 추출 없이 SFT)에서도 같은 이득이 나오는지는 검증되지 않았다. 이는 "환경 재구성의 기여"와 "특정 추출 방식과의 궁합"을 분리하지 못한다는 뜻이다.
  10. 보조 지표에는 분산이 없다. Table 2·3은 표준편차를 붙였지만 Table 4(RL), Table 10(leave-one-out), Table 12(목표 밴드)에는 없다. 특히 Table 10은 6개 중 4개 개선에 clean +16.4 하나가 평균을 만드는 구조라, 분산 없이는 해석이 어렵다.
  11. "학습용 환경"과 "평가용 벤치마크"의 긴장이 남는다. §Table 12에서 평균 성공률을 0.74에서 0.48로 낮춘 것이 개선으로 보고된다. 학습 신호 관점에서는 옳지만, 이는 재구성된 환경이 벤치마크로는 인용될 수 없음을 뜻하기도 한다. 논문은 평가를 항상 원본 과제로만 해서 이 충돌을 올바르게 회피하지만, "환경 공급"이라는 프레이밍이 평가 환경 공급으로 오독될 여지는 남는다.

Key Takeaways

  1. "환경 구축은 저작 문제가 아니라 감싸기 문제"라는 재프레이밍이 이 논문의 진짜 기여다. 새 환경을 만들면 새 verifier가 필요하고, verifier를 LLM이 만들면 신뢰가 깨지고, 그래서 과잉 생성·필터링이 필요해진다. 기존 환경을 감싸면 이 사슬이 통째로 사라진다. 성능 수치보다 이 구조적 통찰이 오래 남을 부분이다.
  2. 보상 축을 설계자에게 노출하지 않는 것이 정책이 아니라 아키텍처다. "테스트 라벨을 쓰지 마라"는 지시는 지켜질 수도 안 지켜질 수도 있지만, $R$을 조작할 수 있는 인터페이스가 존재하지 않으면 지표 해킹은 구조적으로 불가능하다. 자기 개선 시스템을 설계할 때 "금지"를 "불가능"으로 바꿀 수 있는 지점을 찾는 것이 일반적으로 적용 가능한 교훈이다.
  3. 난이도 조절이 양방향이어야 한다. 대부분의 curriculum은 "어려우면 쉽게"만 한다. EnvRigger는 정책이 완벽하게 성공하면 환경이 너무 관대하다고 진단하고 더 어렵게 만든다. 설계자 prompt의 문구가 이 원칙을 압축한다 — "불가능해서 나온 SR=0은 사소해서 나온 SR=1만큼이나 쓸모없다". 성공률 in-band 비율 6.0% → 80.0%가 이것이 작동함을 보인다.
  4. 환경 스케일링의 한계를 실측으로 보였다. 동일 예산에서 원본 환경 52.13, 생성 환경 50.37은 150개 부근에서 평평해지는데 EnvHarness만 54.79까지 계속 오른다. "데이터를 늘리면 좋아진다"의 에이전트 판본이 무조건 참은 아니며, 학습자의 현재 능력 경계를 겨냥해야 한다는 것 — 이것은 EnvHarness를 쓰지 않더라도 환경·과제 curation에 적용되는 교훈이다.
  5. 도메인 무관성이 실제로 성립하려면 무엇이 필요한지가 명확히 서술된다. 핵심은 get_env_state()가 런타임 핸들 없는 순수 데이터만 노출하고 컴포넌트 훅이 그것만 읽을 수 있다는 제약이다. 자체 에이전트 인프라를 설계 중이라면 이 한 줄이 이식성의 분기점이며, 인메모리 게임과 Docker 컨테이너에서 같은 코드가 도는 이유다.
  6. 이 논문은 harness 계열에서 방법론적 기준선을 올렸다. 3회 실행의 표준편차 전면 보고, 토큰 비용 분해, 부정적 결과 게재, 자기 지표에 대한 비판(부록 F.4 "평균 스텝만으로는 품질을 알 수 없다"), 코드–논문 명명 대응표까지. ##표준편차를 보고했기 때문에 독자가 직접 재분석할 수 있었다## — §신뢰구간 재분석이 가능했던 것 자체가 이 실천의 가치를 증명한다.
  7. 같은 계절의 Life-Harness와 정확히 반대편을 잡는다. Life-Harness는 환경을 고정하고 정책 쪽 인터페이스를 고쳐 추론 성능을 올리고, EnvHarness는 정책을 고정하고 환경 쪽 인터페이스를 고쳐 학습 신호를 만든다. ##두 방법은 원리상 조합 가능한데 어느 논문도 시도하지 않았다## — EnvHarness로 만든 환경에서 학습한 정책에 Life-Harness를 씌우는 것이 자연스러운 다음 실험이다. 단, "Contract"라는 같은 단어가 두 논문에서 거의 반대 방향을 가리키므로 문헌을 읽을 때 주의해야 한다.
  8. 비판적으로 — 헤드라인 수치의 절반은 $n=3$에서 확정되지 않는다. 보고된 표준편차로 계산하면 14개 비교 중 6개만 95% 구간이 0을 넘지 않으며, 특히 SWE-bench Verified 성공률($+2.70 \pm 6.02$)이 그중에 없는데 스케일링·크로스 모델 실험이 전부 이 지표로 논증한다. 14개가 모두 양의 방향이라는 점(부호 검정 $p \approx 0.00006$)이 강한 방증이므로 "효과가 없다"는 결론은 부당하지만, 이 논문을 인용해 의사결정을 할 때는 개별 수치가 아니라 방향과 기울기를 근거로 삼는 편이 안전하다. 그리고 환경 수율이 한 라운드에 대해서만 보고되고(부록 F.2: 약 1/3이 무기여) 전반적으로는 알 수 없어 실제 단위 비용을 계산할 수 없다는 점은 실무 도입 시 직접 측정해야 할 항목이다. 같은 부록이 정책이 강해지면 "더 어렵게" 후보가 전부 기각되는 실패 모드도 기록하고 있어, 도입 후 라운드를 거듭할수록 이 지점을 감시해야 한다.
