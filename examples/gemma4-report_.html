1. 하이브리드 어텐션 메커니즘 — 상세 분석

로컬 슬라이딩 윈도우와 글로벌 풀 어텐션을 교대로 배치합니다. 경량 모델의 속도를 유지하면서, 긴 컨텍스트에 대한 깊은 이해를 동시에 달성하는 핵심 설계입니다.

모델별 인터리빙 패턴

로컬 vs 글로벌 어텐션 — 내부 구조 비교

로컬과 글로벌 레이어는 단순히 윈도우 크기만 다른 것이 아니라, Query-KV 헤드 비율, 헤드 차원, RoPE 전략, K=V 통합 여부까지 근본적으로 다릅니다.

정보 전파 메커니즘

개별 로컬 레이어는 좁은 윈도우만 보지만, 여러 로컬 레이어를 쌓으면 정보가 점진적으로 전파됩니다. 그 사이 글로벌 레이어가 전체 시퀀스를 한 번에 종합합니다.

5:1
인터리빙 비율
5개 로컬 + 1개 글로벌 반복. E2B만 4:1. 로컬이 빠른 근접 처리를, 글로벌이 전체 맥락 종합을 담당.
8:1
글로벌 GQA 비율
글로벌 레이어는 8개 Query가 1개 KV 헤드를 공유. 로컬의 2:1 대비 4배 더 공격적으로 메모리 절감.
K=V
글로벌 Key-Value 통합
글로벌 레이어에서 Key=Value로 통합하여 KV 캐시를 추가 50% 절감. Key 차원을 256→512로 2배 확대해 품질 보상.
p-RoPE
비례 위치 인코딩
글로벌 레이어에서 p=0.25로 저주파 RoPE 차원을 가지치기하여, 장문 시퀀스에서의 회전 노이즈를 줄이고 품질 유지.
DEEP DIVE

2. Per-Layer Embeddings (PLE) — 상세 분석

E2B/E4B 모델의 핵심 혁신. Gemma 3n에서 처음 도입되어 Gemma 4에서 완성된 기법으로, 각 토큰이 모든 디코더 레이어에 대해 전용 저차원 벡터를 생성하여 적은 파라미터 오버헤드로 레이어별 특수화를 달성합니다.

해결하려는 문제: 기존 트랜스포머의 한계

PLE의 해결책: 레이어별 전용 경로

PLE 차원 및 메모리 구조

PLE 룩업 테이블은 파라미터 수가 크지만, 추론 시 한 번만 조회되므로 "비활성(non-effective)" 파라미터로 분류됩니다. 이것이 E2B에서 활성 파라미터 2.3B vs 전체 5.1B의 차이를 만듭니다.

PLE와 멀티모달 입력 처리

PLE는 토큰 ID에 의존하므로, 이미지/오디오 같은 소프트 토큰과의 상호작용에 특별한 처리가 필요합니다.

PLE 효과 요약

6x
작은 차원
PLE 256차원 vs 메인 1,536차원. 적은 비용으로 레이어 특수화를 가능하게 합니다.
1회
조회만 필요
추론 시작 시 한 번 lookup만 수행. 플래시 메모리에 저장되어 VRAM 부담 없음.
2.3B
활성 vs 5.1B 전체
E2B에서 PLE 룩업 테이블이 전체의 절반 이상을 차지하지만, 실제 연산은 2.3B만 사용.
35개
레이어별 전용 벡터
E2B의 35개 레이어 각각이 토큰별 전용 정보를 받아 역할에 맞게 특수화됩니다.

3. Mixture-of-Experts (MoE) — 26B A4B 모델

128개의 소형 전문가 중 토큰마다 8개(+공유 1개)를 선택 활성화합니다. 공유 전문가(Shared Expert)는 개별 전문가의 약 3배 크기로, 모든 토큰이 공통적으로 필요로 하는 일반 지식을 담당합니다. 전체 26B 파라미터 중 ~4B만 활성화하면서 31B Dense 모델의 ~97% 성능을 달성합니다.

DEEP DIVE

4. 비전 인코더 — 상세 분석

Vision Transformer(ViT) 기반으로, 2D RoPE와 가변 종횡비 지원, 공간 풀링을 통해 이미지를 유연하게 처리합니다. "이미지 한 장은 16×16 단어에 해당한다"는 ViT의 원칙을 따릅니다.

이미지 처리 파이프라인 (5단계)

토큰 예산 시스템 & 인코더 사양

토큰 예산에 따라 이미지 해상도가 동적으로 조절됩니다. 예산이 280이면 풀링 전 최대 9 × 280 = 2,520개 패치가 생성됩니다.

오디오 인코더 (E2B/E4B 전용)
USM 스타일 Conformer 아키텍처 사용. 음성 인식 및 번역 지원, 최대 30초 오디오 처리. Gemma 3n에서 도입된 동일 아키텍처 기반.
DEEP DIVE

오디오 인코더 파이프라인 — 상세 분석 (E2B/E4B 전용)

오디오 입력은 비전과 유사한 "소프트 토큰" 방식으로 처리되지만, 시간-주파수 도메인의 특성에 맞는 전용 파이프라인을 사용합니다. 3단계 전처리 후 Conformer 인코더가 맥락적 임베딩을 생성합니다.

오디오 처리 파이프라인 (4단계)

5. 공유 KV 캐시 & 글로벌 K=V 통합 — 상세 분석

Gemma 4의 메모리 최적화는 3가지 기법이 겹쳐 작동합니다: Grouped Query Attention(GQA), K=V 통합, 그리고 후반 레이어의 KV 공유입니다.

3중 최적화 스택

실제 메모리 영향 (31B 기준, bf16, 256K 컨텍스트)

61 GB
모델 가중치 (bf16)
비양자화 시 전체 가중치. NVFP4: 32.7GB, AWQ 4-bit: 20.5GB로 축소 가능.
~20.8 GiB
KV 캐시 (256K 풀)
31B 모델의 256K 컨텍스트 풀 활용 시. GQA + K=V 최적화 덕분에 이 수준.
~5.2 GiB
KV 캐시 (26B MoE)
26B A4B 모델은 30개 레이어 + 공격적 GQA(8:2)로 31B 대비 KV 캐시 75% 축소.
~95%
글로벌 레이어 캐시 절감
GQA 8:1(87.5%) + K=V 통합(50%) + 레이어 공유 = 글로벌 레이어 캐시 기존 Dense 대비 ~95% 절감.

1. Per-Layer Embeddings (PLE)

각 토큰이 레이어별 전용 벡터를 생성하여, 적은 파라미터 오버헤드로 레이어별 특수화를 달성합니다.

2. 공유 KV 캐시

마지막 레이어들이 이전 레이어의 Key/Value를 재사용하여 중복 계산을 제거하고 메모리를 절감합니다.

3. 듀얼 RoPE 전략

로컬 어텐션에는 표준 RoPE, 글로벌 어텐션에는 Proportional RoPE를 적용하여 긴 컨텍스트 품질을 유지합니다.

4. 가변 이미지 토큰 예산

70~1,120 토큰 범위에서 이미지 해상도를 유연하게 조절하여 속도와 품질의 최적 균형을 찾습니다.

5. 128 전문가 MoE

128개 소형 전문가 중 8+1개만 활성화하여, 4B 활성 파라미터로 1441 Arena ELO를 달성합니다.

6. 네이티브 멀티모달 Function Calling

특별한 문법 제약 없이 자연스러운 JSON 출력으로 에이전틱 워크플로우를 구현합니다.

7. 멀티모달 도구 응답 학습

TRL 통합으로 훈련 중 도구로부터 이미지를 받아 시각적 피드백 기반 강화 학습이 가능합니다.

왜 네이티브 Function Calling인가? — 프롬프트 기반 vs 토큰 기반

대부분의 LLM은 프롬프트에 "도구를 JSON으로 호출하세요"라고 지시하는 방식(프롬프트 엔지니어링)을 사용합니다. Gemma 4는 근본적으로 다른 접근법을 취합니다 — 사전학습 시 vocabulary에 특수 토큰을 추가하여, 모델이 "도구 호출"이라는 행위 자체를 언어 모델링의 일부로 학습합니다.

DEEP DIVE

7개의 특수 토큰 — 네이티브 Function Calling 완전 해부

Gemma 4는 프롬프트 엔지니어링에 의존하지 않고, 사전학습 시 vocabulary에 내장된 7개의 특수 토큰(3쌍 + 1개 인용 토큰)으로 함수 호출 라이프사이클을 구조화합니다. 추론 엔진이 결정론적으로 파싱할 수 있는 명확한 경계(hard boundary)를 제공합니다.

토큰 상세 해부 — 각 구성요소의 역할

<|tool> declaration:함수명{스키마} <tool|>
위치: system turn 내부에만 배치
생성자: 개발자(앱)가 작성
내부 포맷: declaration:이름{description:<|"|>설명<|"|>, parameters:{...}}
핵심: 모델에게 "이 도구가 존재한다"를 알려주는 선언. 여러 도구는 여러 블록으로 나열합니다.
<|tool_call> call:함수명{인자} <tool_call|>
위치: model turn 내부
생성자: 모델이 자율적으로 생성
내부 포맷: call:함수명{param1:값1, param2:값2}
핵심: 추론 엔진은 이 토큰을 감지하면 생성을 중단하고, 해당 함수를 실행한 뒤 결과를 tool_response에 넣어 다시 모델에 전달합니다.
<|tool_response> response:함수명{결과} <tool_response|>
위치: model turn 내부 (tool_call 뒤에 연속 배치)
생성자: 앱(오케스트레이터)이 주입
내부 포맷: response:함수명{key:value, ...}
핵심: 같은 model turn 안에 누적됩니다. 연속된 tool_call → tool_response 쌍이 한 턴에 여러 개 올 수 있습니다.
<|"|> — Universal String Delimiter
역할: 모든 문자열 값을 감싸는 인용 토큰
왜 필요한가: 일반 따옴표(")는 JSON 구문과 충돌합니다. 이 전용 토큰을 사용하면 문자열 내부에 어떤 문자가 와도 안전합니다.
규칙: 문자열 → 반드시 인용 | 숫자/불리언 → 인용 없음
예시: city:<|"|>서울<|"|> vs count:5

Jinja2 Chat Template — 내부 메시지 포맷 구조

Gemma 4는 HuggingFace의 apply_chat_template()를 통해 Jinja2 템플릿으로 메시지를 포맷합니다. OpenAI 호환 메시지 형식이 내부적으로 Gemma의 특수 토큰 형식으로 변환되는 과정을 이해하는 것이 중요합니다.

⚠️ 주의: tool role의 특수 처리
OpenAI의 "tool" role 메시지는 Gemma에서 별도의 턴이 아니라 직전 model turn 안에 tool_response로 누적됩니다. 연속된 assistant(tool_call) → tool(결과) 쌍은 하나의 model turn으로 합쳐집니다.
💡 Thinking 상태 관리 핵심 규칙
일반 턴 사이에서는 모델의 thought를 반드시 제거해야 합니다. 하지만 도구 호출이 포함된 단일 model turn 내에서는 thought를 제거하지 않아야 합니다 — 추론의 연속성이 유지되어야 하기 때문입니다.
📂 공식 Jinja2 템플릿 파일
에이전틱 워크플로우에는 google-gemma-4-*-interleaved.jinja 템플릿을 사용하세요. 이 템플릿은 도구 호출 + interleaved thinking을 모두 지원합니다. vLLM에서는 --tool-call-parser gemma4 플래그로 전용 파서를 활성화합니다.

에이전트 루프 — 다단계 자율 워크플로우 (상세)

Gemma 4는 단순 1회 호출이 아니라, "추론 → 도구 호출 → 결과 분석 → 추가 호출 또는 응답" 루프를 자율적으로 반복합니다. Thinking 모드와 결합하면 복잡한 다단계 작업을 계획하고 실행합니다.

병렬 호출 vs 순차 호출 — 실행 전략 비교

Gemma 4는 단일 턴에서 여러 도구를 동시에 호출하는 병렬 호출(Parallel Calling)을 지원합니다. 하지만 호출 수에 따라 신뢰성이 달라지므로, 상황에 맞는 전략 선택이 중요합니다.

도구 정의 방법 — 두 가지 접근법

도구를 Gemma 4에 알려주는 두 가지 방식: JSON Schema 직접 작성 또는 Python 함수의 docstring에서 자동 변환

권장 사항: 도구 개수 10~15개 이하
도구가 많아질수록 모델의 선택 정확도가 떨어집니다. 핵심 도구만 정의하고, 관련 도구는 그룹으로 묶어 제공하는 것이 최적입니다.

Thinking 모드 × Function Calling 통합

Gemma 4의 구성 가능한 사고 모드(Configurable Thinking)를 활성화하면, 도구 호출 전 내부 추론을 수행하여 더 정교한 계획 수립과 도구 선택이 가능합니다. Thinking 모드는 토큰 생성량을 2~5배 증가시키지만, 복잡한 도구 선택 결정의 정확도를 크게 향상시킵니다.

Thinking OFF 권장
단일 도구 호출, 빠른 응답 필요 시, 단순 질의, 저지연 엣지 디바이스. 토큰 소비 최소화.
Thinking ON 권장
다단계 계획 수립, 복잡한 추론, 다중 도구 연쇄 호출, 멀티모달 분석. 토큰 2~5배 증가.

에러 처리 & 장애 복구 패턴

실제 프로덕션 환경에서는 도구 호출 실패, JSON 파싱 오류, 무한 루프 등 다양한 문제가 발생합니다. 각 시나리오별 대응 전략을 이해하는 것이 필수입니다.

💡 Gemma 4의 핵심 경쟁력
단순 성능 수치에서는 클로즈드 모델에 밀리지만, 오픈 웨이트 + 엣지 배포 + 네이티브 토큰 기반이라는 조합은 유일합니다. 특히 26B MoE가 ~4B 활성 파라미터만으로 85.5%를 달성한 것은 효율성 측면에서 매우 인상적입니다. 데이터 프라이버시, 오프라인 환경, 커스텀 파인튜닝이 필요한 프로덕션 시나리오에서 강력한 선택지입니다.

Function Calling 학습 방법론 — 어떻게 훈련되었나

Gemma 4의 에이전틱 능력은 사전학습과 후속 학습(post-training) 양쪽에서 체계적으로 구축되었습니다.

⚠️ 에이전틱 워크플로우 보안 가이드라인 (상세)

에이전틱 AI 시스템에서 보안은 선택이 아닌 필수입니다. 모델이 자율적으로 도구를 호출하므로, 잘못된 호출이 실제 시스템에 영향을 미칠 수 있습니다.

1. 함수 이름/인자 반드시 검증
모델이 환각(hallucination)으로 존재하지 않는 함수를 호출하거나 잘못된 인자를 생성할 수 있습니다. 절대로 globals()를 사용한 동적 호출 금지. dispatch table(dict 매핑) 패턴을 사용하세요.
2. 고위험 작업은 확인 단계 추가
삭제, 결제, 전송 등 되돌릴 수 없는 작업은 실행 전 사용자 확인 절차를 반드시 포함하세요. Human-in-the-loop 패턴이 필수입니다.
3. 병렬 호출은 3개 이하
Gemma 4는 단일 턴에서 여러 도구를 동시 호출할 수 있지만, 3개 초과 시 안정성이 크게 저하됩니다. 4개 이상 필요하면 순차 체인으로 분리하세요.
4. 루프 횟수 제한 설정
에이전트 루프의 최대 반복 횟수를 설정하세요 (권장 5~8회). ~11회 이후 무한 루프에 빠지는 알려진 이슈가 있습니다. max_iterations 파라미터 필수.
5. 입력/출력 크기 제한
도구 응답이 과도하게 큰 경우(DB 전체 덤프 등) 컨텍스트가 빠르게 소모됩니다. tool_response에 넣기 전에 필수 필드만 추출하고 크기를 제한하세요.
6. 프롬프트 인젝션 방어
도구 응답에 악의적 지시문이 포함될 수 있습니다(예: 웹 검색 결과). tool_response 내용을 그대로 신뢰하지 말고, 모델의 system prompt에 방어 지침을 포함하세요.

Kanana LLM/MLLM 관점에서의 핵심 시사점

Gemma 4의 기술 혁신에서 우리가 캐치해야 할 포인트

1

PLE 전략 — "활성 파라미터" 개념의 혁명

Gemma 4의 E2B는 전체 5.1B 파라미터 중 2.3B만 추론에 사용합니다. PLE 룩업 테이블(2.8B)은 플래시 메모리에 저장되어 VRAM을 소모하지 않습니다. 이는 모바일/엣지 배포에서 파라미터 효율성의 새로운 패러다임입니다.

→ Kanana 소형 모델(2.1B, 3B)에 PLE를 적용하면, 동일 VRAM으로 레이어별 특수화를 크게 향상시킬 수 있습니다. 특히 한국어 토큰의 형태소 분석 초기 레이어와 의미 통합 후반 레이어의 차별화에 효과적일 수 있습니다.

2

MoE 설계 — 128 전문가, 8+1 활성화 전략

Gemma 4 26B-A4B는 128개 소형 전문가 중 8+1개만 활성화하여, 3.8B 활성 파라미터로 Arena ELO 1441을 달성합니다. Kanana-2-155b-a17b와 Kanana-1.5-15.7b-a3b도 MoE 아키텍처를 사용하므로 직접 비교 대상입니다.

→ 전문가 수를 늘리되 활성 수를 제한하는 "많은 소형 전문가" 전략이 효과적. Kanana MoE에서 한국어/영어/코드 등 도메인별 전문가 라우팅 전략을 세밀화할 여지가 있습니다. 또한 공유 전문가(shared expert) 1개의 효과도 검증할 가치가 있습니다.

3

하이브리드 어텐션 — 로컬/글로벌 이중 전략

5:1 로컬-글로벌 비율, 글로벌 레이어의 8:1 GQA + K=V 통합 + p-RoPE의 조합이 핵심입니다. 글로벌 레이어의 KV 캐시를 ~95% 절감하면서 256K 컨텍스트를 지원합니다.

→ Kanana에서 긴 한국어 문서 처리 시, 로컬 윈도우 크기를 한국어 평균 문장 길이에 최적화할 수 있습니다. 글로벌 레이어의 K=V 통합은 Kanana의 메모리 효율성을 크게 향상시킬 수 있는 즉시 적용 가능한 기법입니다.

4

비전 인코더 — MLLM을 위한 가변 토큰 예산

Gemma 4의 비전 인코더는 2D RoPE + 3×3 공간 풀링 + 가변 토큰 예산(70~1,120)으로, 동일 모델이 썸네일 분석부터 고해상도 문서 OCR까지 커버합니다. Kanana-v(멀티모달)와 Kanana-o(통합 멀티모달) 개발에 직접적인 참고 사항입니다.

→ Kanana MLLM에서 한국어 문서(세로 쓰기, 혼합 한자) OCR 정확도를 높이려면 2D RoPE가 효과적. 토큰 예산 시스템은 카카오톡 이미지 전송 시 저예산, 문서 스캔 시 고예산으로 자동 전환하는 유연한 배포를 가능하게 합니다.

5

네이티브 Function Calling — 에이전트 시대의 필수 역량

Gemma 4는 별도의 문법 제약 없이 네이티브 JSON 함수 호출을 지원합니다. 이는 단순 챗봇을 넘어 계획 수립 → 도구 호출 → 결과 분석 → 후속 행동의 자율 에이전트를 가능하게 합니다. 멀티모달 도구 응답(이미지를 받아 분석 후 다음 행동 결정)까지 지원합니다.

→ Kanana가 카카오 생태계(카카오톡, 카카오맵, 카카오페이 등)의 에이전트로 작동하려면 네이티브 함수 호출이 필수. 학습 시 함수 호출 데이터셋을 포함하고, 구조화된 JSON 출력 능력을 사전학습 단계부터 내재화해야 합니다. TRL의 멀티모달 도구 응답 학습 기법도 검토 대상입니다.

6

온디바이스 멀티모달 — 엣지 AI의 새로운 기준

E2B는 2-bit 양자화로 1.5GB 미만 메모리에서 텍스트+이미지+오디오를 동시 처리합니다. 128K 컨텍스트를 완전 오프라인으로 지원하며, Qualcomm NPU에서 3,700 tok/s prefill을 달성합니다.

→ Kanana 소형 모델의 온디바이스 배포 전략에서 PLE(플래시 저장) + 공격적 양자화(2-4bit) + NPU 가속의 조합을 검토해야 합니다. 카카오톡 인앱 AI, 카카오내비 음성 인식 등 오프라인/저지연이 필수인 시나리오에서 경쟁력 확보가 가능합니다.

7

Apache 2.0 + 140+ 언어 — 오픈소스 생태계 경쟁

Gemma 4의 Apache 2.0 전환은 오픈 모델 생태계 경쟁을 가속화합니다. 140+ 언어 사전학습, MMMLU 88.4%의 다국어 성능은 Kanana의 한국어 특화 전략과 직접 경쟁합니다. Kanana도 Apache 2.0으로 공개하고 있어 라이선스 경쟁력은 동등합니다.

→ Gemma 4가 다국어 범용에서 강하다면, Kanana는 한국어·한국 문화 특화에서 차별화해야 합니다. 한국어 벤치마크(KoBEST, KMMLU 등)에서의 우위 유지가 핵심이며, 카카오 서비스 데이터를 활용한 한국형 에이전트 파인튜닝이 차별점이 될 수 있습니다.
