목차

TL;DR

  • 문제: "vibe coding"의 진짜 약속은 비개발자가 자연어 의도만으로 완성된 앱을 처음부터 끝까지 만드는 것이다. 그러나 기존 코드 벤치마크는 함수 하나(HumanEval), 기존 저장소의 버그 수정(SWE-Bench), 웹 사이트 사용(WebArena)처럼 조각만 잰다. 자연어 명세에서 배포 가능한 웹 앱까지 가는 "zero-to-one" 능력을 재는 표준 벤치마크가 없다.
  • 해결: Vibe Code Bench(VCB)는 100개 웹 앱 명세(검증 50 / 테스트 50)와 964개 브라우저 workflow(10,131 substep)로 구성된다. 모델은 OpenHands 기반 샌드박스에서 브라우저·터미널·Supabase·MailHog·Stripe를 쓰며 최대 5시간 동안 앱을 만든다. 완성된 앱은 Browser Use 에이전트가 실제 사용자처럼 클릭하며 채점한다. substep의 90% 이상을 통과하면 workflow 통과이고, 앱 점수는 통과한 workflow의 비율이다.
  • 왜 작동하는가: 브라우저로 "보이는 동작"만 채점하므로 구현 방식(파일 구조, DOM, 프레임워크 세부)과 무관하게 이질적인 앱을 같은 잣대로 잴 수 있다. workflow 단위 90% 문턱은 한 기능이 깨진 것을 다른 기능의 성공으로 가리지 못하게 한다. 그 결과 SWE-Bench에서 2.8%p 차이였던 모델 쌍이 VCB에서는 42.7%p로 벌어질 만큼 변별력이 크다.
  • 비유: 기존 벤치마크가 "이 벽돌 한 장을 제대로 쌓았는가" 또는 "이미 지은 집의 수도꼭지를 고쳤는가"를 묻는다면, VCB는 설계 요구서만 주고 "집을 지어 열쇠를 넘겨라"라고 한 뒤 입주 검사관이 문을 열고 수도를 틀고 전등을 켜 보는 시험이다. 검사관은 벽 안의 배관이 어떻게 생겼는지 보지 않는다.

핵심 기여 (Key Contributions)

  1. 새 벤치마크 데이터셋: 개인용·1인 창업자용·기업 내부 도구 세 도메인에 걸친 100개 자연어 웹 앱 명세(검증 50 / 테스트 50)와 964개 브라우저 workflow. 난이도가 다양하고, 28%는 Stripe나 email 연동을 요구한다.
  2. 현실적인 생성 하네스: OpenHands를 포크해 여러 시간짜리 개발 세션을 지원하고, 컨테이너 안에서 브라우저·터미널 접근을 준다. Supabase·MailHog·Stripe를 격리된 컨테이너로 제공하고, Docker-in-Docker로 앱 스택을 띄운다.
  3. 자동 평가 파이프라인: 브라우저 에이전트가 end-to-end workflow를 실행하고 substep 수준의 pass/fail 신호를 낸다.
  4. 16개 최첨단 모델의 종합 평가: 9개 제공사의 모델을 비용·지연·오류 분석과 함께 평가했다. ##최고 모델(GPT-5.3-Codex)도 workflow의 61.77%만 통과##하며, SWE-Bench보다 훨씬 변별력이 크다(MiniMax M2.5와 Claude Opus 4.6의 격차: SWE-Bench 2.8% vs VCB 42.7%).
  5. 평가자 정렬 프로토콜과 분석: 모델 평가자 4종과 사람 평가자 3명의 쌍별 substep 일치율(31.8–93.6%)을 측정해, 평가자 선택이 결과를 실질적으로 바꾼다는 것을 보인다. 생성 쪽과 평가 쪽 분산도 분해한다.

배경 (Background)

B.1 Vibe coding과 "zero-to-one"

Vibe coding은 사용자가 코드를 직접 읽거나 쓰지 않고 자연어로 원하는 것을 설명하면 AI가 앱 전체를 만들어 주는 개발 방식을 가리킨다. Claude Code, Cursor, Codex, Replit Agent, Lovable 같은 상용 시스템은 이미 여러 시간짜리 개발 세션이 실무에서 가능함을 보여 준다. 저자들은 이 방식의 가장 중요한 약속을 "고립된 편집을 더 빨리 끝내는 것"이 아니라 "비기술 사용자가 자연어 의도에서 출발해 완성된 앱을 end-to-end로 만드는 것"으로 본다. 그것이 믿을 만해지면 누가 소프트웨어를 만들 수 있는지가 넓어지고, 명세에서 동작하는 프로토타입까지의 시간이 줄어든다.

"Zero-to-one"은 빈 디렉터리에서 출발한다는 뜻이다. 모델이 스스로 정해야 하는 것은 파일 구조, 프레임워크 설정, DB 스키마와 Row-Level Security(RLS, 행 단위 접근 정책), 인증 흐름, 외부 서비스 연동, Docker 배포까지 전부다. 기존 저장소를 고치는 SWE-Bench와 달리 기댈 기존 인프라가 없다.

직관적으로 말하면: SWE-Bench가 "이미 돌아가는 식당 주방에서 고장 난 오븐 하나를 고쳐라"라면, VCB는 "빈 상가를 주고 메뉴판만 건넨 뒤 개업일까지 식당을 열어라"이다. 오븐 수리를 잘하는 요리사가 식당 개업도 잘한다는 보장은 없다.

B.2 기존 벤치마크 지형 (§2, Table 2)

코드 생성 벤치마크: HumanEval과 MBPP는 docstring에서 함수를 생성하는 고립된 알고리즘 추론을 잰다. SWE-Bench와 그 변형(SWE-Bench Verified, SWE-Bench Pro)은 실제 GitHub 이슈 해결 능력을 재는데, 복잡한 코드베이스 이해를 요구하지만 상당한 기존 인프라를 전제한다. SWE-Lancer는 E2E(end-to-end) 테스트로 Upwork의 100만 달러 규모 프리랜스 과제로 경제적 근거를 주지만 여전히 범위가 정해진 수정이다. LiveCodeBench는 오염을 피하려고 계속 갱신되는 경쟁 프로그래밍 문제를 제공한다.

웹 에이전트 벤치마크: WebArena와 VisualWebArena는 웹 탐색·상호작용 과제로 에이전트를 평가하며, 복잡한 다단계 workflow에서 최대 60% 성공률을 보고한다. 이들은 기존 웹 앱을 사용하는 능력을 잴 뿐 만드는 능력은 재지 않는다. VCB의 평가 파이프라인은 이와 비슷한 브라우저 자동화 기법을 쓰되, 그 대상을 사람이 만든 앱이 아니라 AI가 만든 앱으로 바꾼다.

에이전트 코딩 시스템: OpenHands는 브라우저·터미널을 갖춘 AI 개발자 플랫폼이다. SWE-agent는 에이전트–컴퓨터 인터페이스를 도입했고(간소화된 100줄짜리 mini-swe-agent 변형도 있다), Agentless는 지속 상태 없는 더 단순한 접근이며, Terminal-Bench는 실제 명령줄 과제로 에이전트를 평가한다. 상용 시스템이 여러 시간짜리 세션을 가능하게 했지만, end-to-end 앱 개발 능력의 체계적 평가는 부족했다.

B.3 LLM-as-judge와 평가자 신뢰성

VCB는 채점 자체도 LLM(Large Language Model)이 조종하는 브라우저 에이전트에 맡긴다(LLM-as-judge). 이런 자동 평가는 규모를 키우기 쉽지만, 평가자가 틀리면 벤치마크 전체가 틀린다. 그래서 §5.3(같은 앱을 다시 채점했을 때의 흔들림)과 §6(사람 판정과의 일치)이 이 논문의 기여만큼 중요하다. 이 요약에서 쓰는 "일치율(agreement)"은 두 평가자가 같은 substep에 같은 pass/fail을 준 비율이다.

§1 서론

동기: 소프트웨어 구축은 아이디어를 경제적 가치로 바꾸는 지렛대가 큰 방법이지만, 아이디어를 구현하는 능력은 소수에게 집중되어 있다. 동시에 코드 생성은 생성 AI의 주요 용도가 되었고, 개발자용 도구가 일상 workflow에 빠르게 채택되고 있다(GitHub Copilot 생산성 연구, Stack Overflow 2024 설문). 기존 벤치마크는 함수 합성과 이슈 해결 같은 제약된 과제에서 모델의 능력이 커지고 있음을 시사한다.

공백: 코드 생성 평가 연구는 많지만, 다중 파일 코드·설정·배포·사용자 대면 workflow를 포함하는 "zero-to-one" 설정, 즉 자연어 명세에서 완성된 배포 가능 웹 앱을 만들 수 있는지를 재는 널리 쓰이는 벤치마크는 없다.

VCB 개요와 핵심 발견: VCB는 텍스트 명세만으로 완성된 동작 웹 앱을 생성하는 LLM 능력을 시험하는 첫 벤치마크다. 16개 최첨단 모델에서 end-to-end 앱 개발은 여전히 불안정하다. 최고 모델(GPT-5.3-Codex)도 workflow의 61.8%만 통과한다. 또 생성 중 자기 테스트 행동(브라우저 사용)과 최종 성능 사이에 강한 연관이 있고, 평가자 정렬 연구는 평가자 선택이 중요하다는 것을 보여 준다. 일부 평가자 쌍은 강하게 일치하지만 다른 쌍은 크게 갈린다.

§3 벤치마크 설계

설계는 세 목표를 최적화한다. ① 현실성: 과제가 비기술 사용자의 요청을 닮아야 한다. ② 재현성: 환경과 하네스를 표준화한다. ③ 구현 무관 평가: 특정 구현이 아니라 사용자에게 보이는 동작으로 앱을 판정한다.

3.1 데이터 구축

구성: 실제 소프트웨어 개발 시나리오를 대표하도록 설계한 100개 앱 명세를 서로 겹치지 않는 비공개 검증 세트 50개와 테스트 세트 50개로 나눴다(초록·§1·§3.1은 "private validation set"이라 쓰지만 Table 3의 행 이름은 "Validation (public)"이다. 이 불일치는 비판적 분석에서 다룬다). 명세는 세 도메인에 걸친다.

  • Individual (24개): 사용자가 개인용으로 vibe-code할 앱. 대부분 인증이 없다. 예: 습관 추적 앱.
  • Solo Founder (45개): 창업자가 직접 만들 법한 앱. 보통 간단한 email 기반 인증이고, 일부는 더 복잡한 인증이 필요하다. 예: 붐비는 지역의 주차 공간 검색·예약 앱.
  • Enterprise Tool (31개): 기업이 외부에서 사지 않고 내부에서 만들 법한 프로그램. 다중 역할이나 역할 위계를 포함하는 경우가 많다. 예: 구매 요청 추적·승인 앱.

제작 절차 (4단계):

① Idea generation : 소비자 앱 · YC(Y Combinator) 스타트업 아이디어 · 컨설팅 사례 · 흔한 기업 내부 수요에서 착안 ② Draft generation : 구조화 출력 GPT-5 파이프라인 → 명세 초안 + UI workflow 초안 6–23개 (핵심 기능 · 엣지 케이스 · 핵심 사용자 흐름) ③ Two-pass review : PM(Product Manager) 2인이 공유 rubric으로 편집·확정, 테스트마다 Accept/Modify/Reject + 완료 체크리스트 ④ Audit and freeze : PM이 workflow를 한 줄씩 검토(테스트하는 모든 요소가 명세에 있는가) → LLM 감사로 남은 명세/테스트 불일치 · 브라우저로 불가능한 단계 · 익명 인증 모순 · workflow 간 격리 위반 탐지 → 사람이 수정 후 동결

과제 형식: 각 앱에는 메타데이터(도메인, 난이도, 필요 서비스)와 모델에게 보여 줄 자연어 명세가 있다. 명세는 실제 vibe-coder의 사용을 흉내 내도록 간결하게, 비기술적 관점에서 썼다. 동시에 테스트 통과에 필요한 정보는 담아야 한다. 휴리스틱은 "테스트하는 기능은 반드시 명세에 직접 있거나, 숙련 엔지니어가 명세에서 분명히 도출할 수 있어야 한다"이다. 구체적인 email, username, 조직명, 폼 값도 명세에 있거나 평가 에이전트가 정할 수 있어야 한다(부록 H).

외부 서비스 연동: 전체 100개 중 28개가 최소 하나의 외부 서비스를 요구한다. Email만 9개(사용자 알림, 인증 메일, 보고서), Stripe만 6개(결제, 구독, 청구), 둘 다 13개(서비스 간 일관성이 필요한 workflow)다. 이를 의도적으로 넣은 이유는 두 가지다. 첫째, 순수 CRUD(Create–Read–Update–Delete) 앱이 포착하지 못하는 방식(비동기 webhook, 전달 확인, 다중 서비스 상태 일관성)으로 난이도를 올린다. 둘째, 결제와 알림이 흔한 실제 프로덕션 요구를 더 잘 근사한다. 모든 서비스는 생성 환경 안의 격리된 컨테이너에서 sandbox/test 모드로 돈다.

테스트 구조: 앱마다 UI workflow가 짝지어진다. workflow의 목표는 실제 사용자가 브라우저에서 앱을 처음부터 끝까지 클릭하듯 성능을 평가하는 것이다.

  • Task: 명세 하나와 같은 말이다. Application은 에이전트가 그 task를 풀려고 만든 실행 가능한 구현 하나다.
  • Workflow: 각 task에는 기능의 특정 측면을 평가하는 workflow(테스트)가 6–23개 있다. 예를 들어 소셜 미디어 플랫폼의 workflow는 계정 생성, 새 글 작성, 글에 댓글 달기, 로그아웃을 포함할 수 있다. 각 workflow에는 짧은 목적 설명과 substep 목록이 있다.
  • Substep: 평가자가 각 workflow에서 밟아야 하는 개별 단계다. 예: "이메일 X로 계정을 만들어라", "페이지 Y로 가서 버튼 Z를 눌러라".

브라우저 에이전트를 쓰는 이유는 구현에 무관하기 때문이다. 고정 selector 같은 깨지기 쉬운 DOM 결합 검사를 피하고, 단위 테스트나 Playwright 같은 프로그래밍식 E2E 테스트와 달리 내부 코드 계측이 필요 없다. 모델은 사용자에게 보이는 동작이 명세를 만족하는 한 UI 구조와 스타일을 자유롭게 정할 수 있다(부록 I).

3.2 생성 하네스

환경: 모델은 OpenHands를 개조한 완전한 개발 환경에서 일한다. OpenHands를 고른 이유는 견고한 컨테이너 구조, 브라우저 통합, 확장 가능한 도구 시스템, 커뮤니티의 폭넓은 채택이다.

  • 격리된 컨테이너: 모델마다 개발 작업공간 전체를 제어하는 격리 컨테이너를 받는다.
  • 터미널 접근: 의존성 설치, 빌드, 서버 기동, 임의 명령 실행이 무제한이다.
  • 브라우저: 문서 조회와 생성한 앱의 자기 테스트를 위한 웹 브라우징.
  • 서비스 연동: Supabase, MailHog, Stripe 엔드포인트를 제공한다. 하네스는 연결 정보와 자격 증명을 노출하지만, 모델이 앱과 workflow 안에서 그 서비스들을 직접 찾아 올바르게 써야 한다.

Supabase를 기본 백엔드로 쓰는 이유는 에이전트 도구와 깔끔하게 통합되면서 재현 가능하게 self-host할 수 있기 때문이다. PostgreSQL·인증·객체 저장소를 단일 로컬 스택 뒤에 묶어 과제 간 설정 편차를 줄인다. MailHog와 Stripe는 많은 제품 workflow가 발신 메일과 결제를 요구하기 때문에 넣었다. 이를 빼면 외부 서비스 연결·재시도·상태 동기화의 실패 모드가 사라져 실제 준비도를 과대평가하게 된다.

도구: 터미널 명령, 파일 편집, 웹 탐색, 과제 제출을 위한 OpenHands 핵심 도구와 Supabase·Tavily MCP(Model Context Protocol, 외부 도구 연결 규약) 서버가 노출하는 도구 전체다(Tavily는 OpenHands에 기본 통합되어 있다). 모두 22종이고 목록은 부록 E에 있다.

정규화: 모든 모델에게 앱당 같은 벽시계 예산, 최대 5시간을 준다. 그 안에 한 작업은 최종 산출물에 포함되고 이후 작업은 포함되지 않는다. 턴 수 대신 시간 기반 정규화를 쓴 이유는 실제 개발 제약을 반영하고, 턴 수를 셀 계측이 없는 하네스도 평가할 수 있기 때문이다.

시스템 프롬프트: 반복 테스트로 흔한 실패 모드를 다루는 상세 프롬프트를 만들었다(부록 G). 일관된 기술 스택(React + Vite 프론트엔드, Tailwind CSS, Supabase 백엔드)을 강제하고, 제출 전 배포를 테스트하라는 명시적 지시를 넣고, 환경 변수와 Docker 네트워킹에 대한 상세 안내를 준다. 기술 스택을 강제하지 않으면 생성된 앱이 너무 이질적이어서 규모 있게 일관되게 평가할 수 없었다. 또 Docker Compose를 강제해 각 제출이 이식 가능하고 평가자가 결정론적 진입점으로 띄울 수 있게 했다.

Docker-in-Docker: 에이전트는 격리된 과제별 작업공간 안에서 앱 전용 Compose 스택(프론트엔드, 백엔드, 보조 서비스)을 빌드하고 실행해야 한다. 바깥 컨테이너는 모델의 샌드박스이고, 안쪽 컨테이너는 에이전트가 띄운 앱 서비스다. 이 설계는 강한 과제 격리, 평가를 위한 재현 가능한 기동, 나중에 재생할 수 있는 이식 가능한 산출물을 제공한다.

직관적으로 말하면: 모든 수험생에게 같은 공구 세트(React·Supabase)와 같은 시험 시간(5시간)을 주고, 결과물은 "전원 버튼 하나(docker compose up)로 켜지는 상자"로 제출하게 한 것이다. 공구를 자유롭게 고르게 하면 채점관이 상자마다 여는 법부터 새로 배워야 한다.

3.3 자동 평가 파이프라인

왜 브라우저 에이전트인가: 생성된 앱을 DOM(Document Object Model) 특정 단언(assertion)이나 내부 단위 테스트가 아니라 사용자에게 보이는 브라우저 상호작용으로 평가한다. 그래야 이질적인 앱 전반에서 구현 무관 평가가 유지되고, 실제 사용자가 필요한 workflow를 끝낼 수 있는지를 더 잘 반영한다. 평가는 자율 웹 에이전트 Browser Use가 생성된 앱을 point-and-click으로 테스트하는 방식이다.

입력과 실행: 평가마다 두 입력을 받는다. ① 생성된 앱 번들(코드, Docker Compose, DB 상태) ② 자연어 단계 시퀀스로 쓴 workflow 정의. workflow와 substep은 미리 작성된 벤치마크 산출물이며, 평가자는 테스트 계획을 즉석에서 만들지 않고 고정된 정의를 실행한다. 각 앱의 평가는 격리된 환경에서 돈다.

평가자 설정: workflow마다 새 headless 브라우저 세션(1920×1200)을 띄우고 vision을 켠 Browser Use 에이전트를 실행한다. 이 벤치마크의 기준 평가자는 Claude Sonnet 4.5다(§6의 교차 평가자 검증과 인간 정렬 결과 참조, Table 10). 각 workflow 평가는 비용·시간을 묶어 두면서 여러 페이지 workflow를 허용하도록 최대 100 agent step으로 제한한다. 타임아웃과 watchdog 제한은 전역으로 고정한다(부록 F).

평가 workflow (4단계):

(1) Deployment verification : Docker Compose로 앱 스택을 띄우고 앱이 응답하는지 확인 (2) Workflow execution : 새 브라우저 세션에서 사용자 동작 수행 + substep마다 기대 결과 확인 → 구조화된 substep 수준 pass/fail 판정 (3) Workflow scoring : LLM-as-judge substep 판정으로, substep ≥ 90% 성공 시 workflow 통과 (4) Application aggregation : 앱 정확도 = 통과한 workflow의 비율

90% 문턱과 workflow 단위 채점의 이유: 90% substep 정확도 문턱은 사소한 비핵심 오류를 허용하면서도 거의 완결된 workflow 정확성을 요구한다. substep을 workflow 경계 없이 모아 세지 않고 workflow 단위로 평가하는 것은 cross-workflow masking을 막기 위해서다. 핵심 단계가 깨진 workflow가 무관한 다른 workflow의 성공 substep으로 점수를 받지 못하게 한다.

실패 의미론: 앱이 배포 확인에 실패하면 그 앱의 모든 workflow가 실패로 처리된다. workflow 실행이 구조화된 평가 출력을 반환하지 않으면(예: 타임아웃·종료) 그 workflow는 실패다.

격리: 두 수준에서 강제한다. ① 앱 수준 런타임 격리 ② workflow마다 새 브라우저 세션과 고유 계정·데이터 값을 써서 상태 누출을 막는다. workflow 정의도 workflow 간 의존성이 없도록 검증했다.

3.4 지표

각 앱(task)에 대해 세 가지를 보고한다.

  • Accuracy: 통과한 workflow의 비율. 모델 점수는 앱별 정확도의 평균 ± SE(standard error, 표준오차)로 보고한다. substep의 90% 이상이 성공하면 workflow 통과다.
  • Cost: 생성에 든 총 모델 API 비용. 모든 모델에 각 제공사의 할인 없는 정가를 쓰고, 캐싱을 반영한다.
  • Latency: 첫 턴부터 제출까지 생성의 end-to-end 벽시계 시간. 평가 시간은 포함하지 않는다.

벤치마크 전체 지표는 테스트 분할의 앱별 결과 평균이다. 앱별 정확도가 $\{a_{m,i}\}_{i=1}^{n}$인 모델 $m$에 대해 다음을 보고한다.

$$\bar{a}_m \pm \mathrm{SE}_m, \qquad \mathrm{SE}_m = \frac{s_m}{\sqrt{n}}$$

$s_m$은 앱 간 표본 표준편차이고 $n = 50$이다. 표준적인 불확실성 보고 관행(Miller, 2024)을 따른다. 원문은 이 식에 번호를 붙이지 않았다.

직관적으로 말하면: 학생 한 명이 50문제를 풀었을 때 평균 점수와 "다른 50문제를 뽑았다면 평균이 얼마나 흔들렸을까"를 함께 적는 것이다. 문제마다 0점과 100점을 오가는 학생일수록 그 흔들림(SE)이 크다.

도구 수준: Table 8의 도구 열은 각각 execute_bash, str_replace_editor, browser, execute_sql, apply_migration에 대응한다. 22개 도구가 있지만 모델들은 호출의 약 95%를 이 다섯 개에 쓴다. 이 다섯 개는 벤치마크의 핵심 루프, 즉 스캐폴딩·편집·DB 설정·앱 실행·브라우저 검증에 해당한다. Supabase 도구 중에서는 대체로 migration 헬퍼보다 raw SQL 실행을 선호했다. Tavily 검색은 드물게 쓰였다(18.8%의 모델만 사용).

궤적과 self-testing: Figure 6을 보면 상위 모델은 궤적이 더 길고(Opus 4.6은 예외), 실행과 브라우징에 시간을 더 쓰는 경우가 많다. 이는 자기 작업을 테스트하는 것으로 추론할 수 있다. 모든 모델이 시간의 큰 부분을 코드 작성에 쓴다.

핵심 발견: ##self-testing은 성공과 양의 상관을 보인다##. 16개 모델에서 앱당 browser 도구 호출 수와 정확도의 Pearson 상관은 r = 0.72이고, 생성 지연을 통제해도 유지된다(partial r = 0.72). 즉 단순히 시간을 더 쓴 것을 넘어 self-testing과 더 나은 결과 사이에 연관이 있다. 하위 모델은 일찍 끝내고 더 좁은 행동 범위를 보이는 경우가 많다. 지속적인 self-testing과 반복 수정이 더 강한 end-to-end 결과와 연관된다는 위의 도구 사용 발견과 일치한다. 하위 모델은 브라우징 단계도 짧다.

편집량은 예측력이 약하다: edit 호출과 정확도의 상관은 r = 0.09로 약하고, browser 호출 중앙값은 r = 0.67로 더 강하다.

GPT-5.2 vs GPT-5.2-Codex: self-testing은 같은 계열인 두 모델의 큰 격차도 설명한다. GPT-5.2는 앱당 browser 호출이 거의 3배(26.4 vs 9.4)이고, 이는 Table 8의 더 높은 browser 사용 비중(13.6% vs 8.4%)과 대응한다. 또 0점 앱이 더 적고(9 vs 14) 만점 앱이 더 많다(6 vs 1).

5.2 오류 분석

실패: 정확도 상위 5개 모델에서 앱의 12.8%가 0점이다. 하위 5개 모델에서는 이 비율이 73.2%로 크게 높다. 하위 5개 모델은 앱의 14.0%가 아예 기동되지 않았는데, 상위 모델에서는 이런 일이 없었다. 100점 앱은 드물어서 상위 5개 모델이 만든 앱의 8.8%에 불과했다.

히스토그램: 부록 Figure 7도 비슷한 분포 경향을 보인다. ##모델 향상은 주로 0점 앱의 수를 줄이는 데서 오며##, 모든 앱에서 조금씩 나아지는 방식이 아니다. 분포는 특히 상위 모델에서 강한 양봉(bimodal)인 경우가 많다.

오류 유형: 기동에 성공한 앱의 실패 workflow를 전 모델에 걸쳐 6범주 분류 체계로 나눴다.

  1. Authorization Issue (20.4%): 가입이나 로그인이 동작하지 않거나, 사용자가 올바른 역할을 얻지 못하는 등.
  2. Missing Feature (46.7%): 명세된 기능을 구현하지 않았다.
  3. Validation or Policy Block (14.8%): 허용되어야 할 동작이 막힌다. 가장 흔한 형태는 잘못 설정된 Row-Level Security 정책이다.
  4. UI Rendering or Navigation (6.0%): UI에 무언가가 렌더링되지 않거나 없거나, 에이전트가 필요한 페이지 사이를 이동할 수 없었다.
  5. Data Consistency and Backend Logic (1.9%): 앱이 DB에 잘못된 데이터를 쓰거나 백엔드가 연산을 올바르게 처리하지 못한다.
  6. Other (10.2%): 위 범주에 들지 않는 실패.

이 분해는 대부분의 실패가 기동 실패가 아니라 구현된 제품 표면의 능력 격차임을 보여 준다. 모델마다 특정 오류 유형이 더 흔하다. 예컨대 Grok 4.1 Fast Reasoning과 GPT-5.2-Codex는 인증 문제가 높고(행동 실패의 32.3%, 30.3%), Gemini 3.1 Pro는 기능 누락 비중이 가장 높다(58.5%).

§6 인간 정렬 (Q5)

자동 평가의 핵심 질문은 모델 기반 평가자가 사람의 판단과 맞는가이다. 이를 위해 사람–모델, 사람–사람, 모델–모델 일치를 계산한다.

6.1 방법

  • 앱: 도메인·난이도·연동이 다양하도록 과제 6개를 골랐다. 과제마다 소스 모델 3개(Gemini 3.1 Pro, GPT-5.2, Claude Sonnet 4.6)로 앱을 만들어 총 18개 앱, 1,401개 고유 substep을 평가한다.
  • 사람 평가자: 18개 앱 각각을 사람 3명 중 2명이 평가했다. 브라우저에서 앱을 열고 공유 rubric 지시에 따라 테스트 workflow의 각 substep을 직접 수행했다. 평가 전에 연습 문제로 보정했다. 사용자 대면 앱만 테스트했고 내부 코드·단위 테스트·브라우저 콘솔에는 접근하지 않았다. 각 substep을 pass 또는 fail로 표시했다. 한 전문가가 한 과제의 세 모델 생성물을 모두 검토했으며, 평가자는 어느 모델이 어느 앱을 만들었는지, 다른 평가자의 점수가 어떤지 모른다.
  • 모델 평가자: 앱마다 Browser Use 에이전트를 조종하는 평가자 모델 4종(Gemini 3.1 Pro, GPT-5.2, Claude Sonnet 4.6, Claude Sonnet 4.5)으로 한 번씩 평가했다.
  • 지표 — substep alignment: 두 평가자가 같은 substep에 같은 점수(둘 다 pass 또는 둘 다 fail)를 주면 일치로 본다. 전체 일치율은 일치한 substep의 비율이다. 모든 일치율은 두 평가자 사이의 쌍별 값이며, 평가자 간 판정 조정(adjudication)은 하지 않았다.

6.2 결과

쌍별 일치 행렬: 모든 평가자 쌍(모델 4 + 사람 3)에 대해 각 쌍이 공유한 라벨 substep만으로 일치율을 계산했다(Table 10).

  • 사람–사람: 일치율이 높아(88.6–93.6%) 수동 판정이 평가자 간에 비교적 일관되다. 사람 라벨이 평가자 품질의 외부 기준으로 쓸 만큼 안정적이라는 뜻이다.
  • 모델–모델: 이질적이다. Claude Sonnet 4.6과 4.5가 강하게 일치하고(87.8%), Gemini 3.1 Pro는 두 Sonnet 평가자와 가깝지만(86.4–86.5%), GPT-5.2는 다른 평가자들과 낮게 일치한다(33.1–38.8%). 평가자 출력은 서로 바꿔 쓸 수 없으며, 평가자 선택이 보고되는 결과를 실질적으로 바꿀 수 있다.
  • 모델–사람: 이것도 크게 다르다. 마지막 열의 사람 평균 일치는 86.4%(Claude Sonnet 4.5), 86.3%(Claude Sonnet 4.6), 84.7%(Gemini 3.1 Pro), 36.1%(GPT-5.2)다. 이 패널에서 Claude Sonnet 4.5가 인간 정렬 측면에서 가장 강한 평가자이고, Claude Sonnet 4.6과 Gemini 3.1 Pro가 바로 뒤에 있다.

결론: ##평가자 선택은 정렬 결과에 실질적인 영향을 준다##. 이 패널에서 Claude Sonnet 4.5, Claude Sonnet 4.6, Gemini 3.1 Pro는 GPT-5.2보다 사람 판단과 훨씬 일관된다. 일부 모델 구성은 더 비용 효율적일 수 있다. 예컨대 GPT-5.2는 workflow당 $0.093, Sonnet 4.6은 $1.48이다. 그러나 저자들은 비용보다 정렬 품질만을 우선해 Sonnet 4.5를 택했다.

§7 한계

  1. 설계·코드 품질 미측정: 기능 테스트를 통과한다고 해서 유지보수 가능하거나 안전하거나 문서화가 잘된 것은 아니다. 코드 가독성, 시각 디자인 품질, 보안 취약점은 평가하지 않았다.
  2. 단일 하네스: 모든 결과는 OpenHands 기반 공통 생성 하네스 하나로 측정했다. 다른 하네스에서는 성능이 오를 수 있다.
  3. 단일 기술 스택: React/Vite 웹 앱과 Supabase 백엔드에만 집중한다. 다른 프레임워크나 백엔드 기술로 일반화되지 않을 수 있다.
  4. 웹 앱만: 브라우저 기반 앱만 평가한다. 명령줄 도구, 데스크톱 앱, 모바일 앱 같은 다른 소프트웨어 유형의 "zero-to-one" 능력은 미탐구다.

§8 결론

저자들은 964개 브라우저 workflow로 평가하는 100개 웹 앱 명세 벤치마크 Vibe Code Bench를 소개했다. 16개 최첨단 모델 중 최고가 61.8%로, 신뢰할 만한 end-to-end 앱 개발은 미해결이다. 두 발견이 두드러진다. 모델 향상은 주로 완전 실패를 줄이는 데서 오며 점진적 개선에서 오지 않는다. 그리고 생성 중 self-testing은 성능과 강하게 연관된다(r=0.72). 인간 정렬 연구는 올바른 평가자를 쓰면 자동 평가가 신뢰할 만하다는 것을 보여 주므로, 평가자 선택은 일급 보고 사항이 되어야 한다. 저자들은 이렇게 맺는다. "질문은 더 이상 AI가 코드를 쓸 수 있느냐가 아니라 소프트웨어를 만들 수 있느냐이다. Vibe Code Bench는 그 기준을 향한 진척을 추적한다."

비판적 분석 (Critical Analysis)

강점

  • 측정 대상이 실제 사용 사례와 맞는다: 명세 → 배포 가능한 앱이라는 zero-to-one 과제를 실제 서비스(Supabase·Stripe·MailHog)와 5시간 예산 안에서 잰다. "기능이 실제로 동작하는가"를 사용자 관점에서 판정하므로 결과를 실무적으로 해석하기 쉽다.
  • 변별력이 크다: 상위 61.8%부터 하위 1.2%까지 넓게 퍼지고, SWE-Bench에서 비슷하던 모델들이 크게 갈린다. 포화된 벤치마크가 많은 상황에서 가치가 크다.
  • 평가자 자체를 검증한다: LLM-as-judge 벤치마크가 흔히 건너뛰는 인간 정렬(18개 앱, 1,401 substep, 사람 3명)과 생성/평가 분산 분해를 실제로 수행하고 보고한다. "GPT-5.2를 평가자로 쓰면 36%만 맞는다"는 결과는 다른 벤치마크 설계자에게도 경고가 된다.
  • 행동 분석이 실용적이다: self-testing ↔ 정확도(r=0.72, 지연 통제 후에도 유지), "향상은 0점 앱 감소에서 온다", 오류 6범주는 에이전트 설계자에게 바로 쓸 수 있는 통찰이다.
  • 재현 산출물: 하네스, 모든 궤적, 생성된 앱을 공개한다.

한계와 의문점

  • 평가자의 이해 상충 가능성: 기준 평가자가 Claude Sonnet 4.5이고, 피평가자 중 4개(Opus 4.6, Opus 4.6 Thinking, Sonnet 4.6, Haiku 4.5 Thinking)가 Anthropic 모델이다. 인간 정렬 패널의 소스 모델은 Gemini 3.1 Pro, GPT-5.2, Sonnet 4.6 세 개뿐이라, Sonnet 4.5가 "Anthropic 모델이 만든 앱"과 "OpenAI 모델이 만든 앱"을 다르게 관대하게 채점하는지(자기 선호 편향)는 검증되지 않았다. 소스 모델별 모델–사람 일치율 분해가 있어야 이 우려를 덜 수 있다.
  • GPT-5.2 평가자의 36% 일치는 설명되지 않는다: 무작위보다 낮은 일치는 체계적 편향(예: Browser Use와의 통합 문제, vision 처리 차이)을 시사한다. 원인을 밝히지 않으면 "GPT-5.2가 나쁜 평가자"인지 "이 하네스에서 GPT-5.2가 제대로 돌지 않았다"인지 구분할 수 없다. 후자라면 GPT-5.2가 생성자로 쓰일 때도 하네스 적합성 문제가 있을 수 있다.
  • 통계적 엄밀성: 모델당 단일 생성 run이다. §5.3이 생성 분산을 6개 앱 · 3개 모델로만 측정했는데 생성 SE가 3.5–5%p다. 상위 5개 모델(51.5–61.8)의 순위는 SE 범위 안에서 겹치며, 쌍체 유의성 검정이 없다. Opus 4.6 Thinking(53.50)이 Opus 4.6(57.57)보다 낮다는 "thinking 역효과"도 잡음일 수 있다.
  • 설정의 비대칭: GLM-5·MiniMax·DeepSeek는 vision 없이 평가되었고, Figure 5에서 vision이 최대 ~17%p 차이를 만든다. closed vs open-weight 격차의 일부는 모델 능력이 아니라 입력 모달리티 차이다. 또 OpenHands 하네스가 특정 모델 계열(도구 호출 형식 등)에 더 맞을 가능성도 한계 2에서만 언급된다.
  • 난이도 라벨의 순환성: Easy/Medium/Hard를 16개 모델의 평균 통과율로 사후 분류했기 때문에, "Hard에서 모델이 못한다"는 정의상 참이다. 사전 난이도 라벨(메타데이터에 있다고 §3.1이 언급)과의 비교가 없다.
  • 소표본 칸: 테스트 분할의 Stripe-only는 2개, Email-only는 4개 앱이다. Table 6의 연동별 비교에서 이 칸들은 앱 1개가 25–50%p를 움직인다.
  • 원문 내 작은 불일치: 검증 분할을 초록·§1·§3.1은 "private"이라 하는데 Table 3은 "Validation (public)"이라 적는다. Figure 3 축은 "median"이지만 Table 4는 평균인지 중앙값인지 명시하지 않는다. §5.1은 Table 8의 "SQL" 열을 execute_sql로 대응시키며 "모델들은 raw SQL을 선호했다"고 하지만, Table 8에서 SQL(1.3–14.4%)과 Migrate(1.3–11.1%) 비중은 모델마다 엇갈려 그 일반화가 강하지 않다.
  • "동작"만 재는 한계: §7이 인정하듯 보안·코드 품질을 재지 않는다. 오류 분석에서 RLS 오설정이 14.8%라는 사실은, 통과한 앱에도 반대 방향의 RLS 오류(권한이 너무 열린 정책)가 숨어 있을 수 있음을 시사한다. 기능 테스트는 "막혀야 할 것이 열려 있는" 보안 문제를 거의 잡지 못한다. Zeeter의 guest 제한 workflow처럼 일부 테스트만 이를 본다.

Key Takeaways — 이 논문에서 가져갈 것

  1. 코딩 에이전트에게 "직접 써 보게" 하라: 브라우저로 자기 앱을 테스트하는 빈도가 정확도와 가장 강하게 연관된다(r=0.72, 편집량은 r=0.09). 같은 계열에서도 테스트를 3배 더 한 GPT-5.2가 Codex 변형보다 15.6%p 높다. 에이전트 하네스를 설계할 때 self-testing 루프를 강제하는 것이 모델 교체만큼 효과적일 수 있다.
  2. 향상은 "0점 앱 줄이기"에서 온다: 분포가 양봉이므로 평균을 올리는 가장 빠른 길은 기동 실패·인증 실패 같은 치명적 실패를 없애는 것이다. 실무에서도 "켜지기만 하면 대부분 동작한다"는 앱 개발의 특성을 반영한다.
  3. 외부 서비스 연동과 권한 설정이 진짜 난관이다: email+Stripe 연동에서 평균 정확도는 34% → 13%로 떨어지고, 인증 문제와 검증·정책 차단(RLS 등)이 합쳐 실패의 35%다. vibe coding 도구가 가장 많이 도와야 할 곳은 UI가 아니라 백엔드 보안 설정과 서비스 연결이다.
  4. LLM 평가자는 반드시 사람과 맞춰 보라: 같은 앱을 어떤 모델이 채점하느냐에 따라 사람과의 일치가 86%에서 36%로 바뀐다. 평가자 선택과 그 정렬 수치는 벤치마크 결과와 함께 보고해야 할 일급 정보다.
  5. (비판적 관점) 상위권 순위를 과신하지 말 것: 상위 5개 모델은 SE 범위 안에서 겹치고, 생성 run은 1회, 기준 평가자는 피평가 계열과 겹치며, 하위 open-weight 일부는 vision 없이 평가되었다. 이 벤치마크는 "61.8% 대 57.6%"보다 "60% 대 15%"를 말할 때 믿을 만하다.
