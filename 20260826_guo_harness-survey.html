목차

TL;DR

  • 문제: LLM 에이전트 성능의 병목이 어디에 있는가 — foundation model인가, execution harness인가, 둘의 결합인가? 정적 벤치마크(MMLU, GPQA)는 프론티어에서 포화하는데 agentic 벤치마크(SWE-bench, WebArena, OSWorld, Terminal-Bench)는 여전히 크게 미해결이다. ##모델 스케일링만으로 그 격차가 닫히지 않는다면 무엇이 닫는가?##
  • 해결: model–harness 렌즈로 문헌을 재조직한다. LLM 에이전트를 $A_{LLM} = \langle M, H\rangle$로 형식화하고, harness를 6개의 결합된 런타임 책임으로 분해한다 — observation / context / control / action / state / verification·governance. 그리고 agent engineering의 역사를 4개 패러다임(prompt → context → harness → agent-native·co-evolution)으로 추적해 병목이 어떻게 이동했는지를 서술한다.
  • 왜 작동하는가: 이 분해가 운영적(operational)이기 때문이다. 기존 taxonomy는 "memory, planning, action" 같은 기능 모듈을 나열하는데, 이 분해는 런타임 책임을 나눈다 — 그래서 ##모델이 그대로인데 harness만 바꿔도 성능이 달라지는 현상##을 설명할 수 있다. 그리고 그 현상을 실제 수치로 뒷받침한다: Terminal-Bench 2.0에서 harness를 3개 이상 관측한 20개 모델의 모델 내 성능 범위 중앙값이 13.6%p, WebArena에서 GPT-4o는 13.1% → 54.6%다.
  • 비유: 모델은 운전자이고 harness는 차량과 계기판이다. 지금까지 우리는 운전자만 계속 훈련시켜 왔다(모델 스케일링). 그런데 같은 운전자를 서로 다른 차에 태우면 랩타임이 13~20초 차이 난다 — 백미러가 없거나, 계기판이 엉뚱한 숫자를 보여주거나, 브레이크가 없어서다. 이 survey는 차량 설계도를 6개 부품으로 나눈 정비 매뉴얼이다.

핵심 기여 (Key Contributions)

  1. evolution-first 종합: 정적 component taxonomy가 아니라 공학 패러다임의 이동으로 문헌을 조직한다 — prompt engineering → workflow·context engineering → harness engineering → agent-native training·co-evolution. 각 단계가 이전 단계가 노출한 한계에 대응해 등장했다는 구조를 세운다.
  2. 모델 중심 스케일링의 한계를 두 경계로 분리: (i) resource–performance boundary — LLaMA 3.1에서 70B → 405B로 가면 학습 compute가 ##7.0M → 30.84M H100 GPU-hour(4.4배)##인데 MMLU +2.6, MBPP EvalPlus +2.6, GSM8K +1.7에 그친다. (ii) measurement boundary — 프론티어 모델들이 MMLU-Pro·GPQA Diamond의 좁은 고득점 구간에 뭉치면서 벤치마크의 판별력이 떨어진다.
  3. harness의 형식적 분해: $H = \langle I_{obs}, C, L, I_{act}, S, V\rangle$. 그리고 기능적 agent 루프(perception·state·reasoning·action·feedback)와의 many-to-many 매핑을 제시해, "memory"나 "action" 같은 개념어가 실제 배포 시스템에서 여러 런타임 컴포넌트로 흩어져 구현된다는 점을 명시한다.
  4. 과제 성질 → harness 구성 규칙: 도메인 라벨(코딩/웹/의료)이 아니라 과제 압력 프로파일(horizon, 관측성, oracle 강도, 비가역성, 자율성)이 harness 구성을 결정한다는 매핑표를 만든다. 5개 도메인에서 ##주 병목이 컴포넌트 사이를 이동##하는 패턴을 보인다 — 코딩은 verification-dominant, 웹/GUI는 grounding-dominant, 연구는 synthesis-dominant, 의료는 safety-dominant, 임바디드는 control-dominant.
  5. harness 효과의 정량적 종합: 세 벤치마크에서 model–harness 증거를 모은다. SWE-bench Verified(Claude 3.5 Sonnet 기준 ##33.6% → 53.6%##), Terminal-Bench 2.0(Gemini 3.1 Pro ##59.4% → 80.2%##), WebArena(GPT-4o ##13.1% → 54.6%##). 동시에 모델 업그레이드가 harness 계열 전체를 끌어올린다는 반대 방향 증거도 함께 제시해 harness-only 해석을 배제한다.
  6. scaffold 복잡도 ≠ 성능: Opus 4.5에서 ##약 100줄 Python인 mini-SWE-agent가 76.8%, 완전한 샌드박스 런타임인 OpenHands+CodeAct 2.1이 77.6%##. 차이가 0.8%p다. 즉 harness 효과는 기능 개수보다 인터페이스 설계에서 온다.
  7. value-aware 평가 목적함수 제안: 성공률 단일 지표에서 벗어나 과제 가치·성공확률·과정 품질을 곱하고 비용·지연·위험·신뢰성을 제약으로 두는 최적화 형태를 형식화한다. 그리고 value density라는 정규화 목적함수 계열을 제시한다.
  8. 공개 로그의 증거 경계를 스스로 명시: Terminal-Bench 공개 저장소 75개 제출 / 32,604개 trial 중 48개만 현재 리더보드와 엄격히 일치하고, 토큰 필드는 45.0%, ##달러 비용 필드는 15.2%만 커버##된다고 밝힌다. 그래서 비용 기반 주장을 하지 않는다.

배경 (Background)

왜 지금 harness인가 — 두 벤치마크 곡선의 갈라짐

이 survey의 출발점은 하나의 관측이다. LLM 기반 에이전트는 수동적 질의응답에서 능동적 과제 수행으로의 전환을 표시한다 — 환경을 인지하고, 도구를 호출하고, 상태를 유지하며, 긴 지평에 걸쳐 행동한다. 대표 사례가 여러 도메인에 걸쳐 있다: 코딩 에이전트(Devin, Claude Code, Codex)는 저장소 전체에서 소프트웨어 이슈를 독립적으로 진단·해결하고, 범용 에이전트(Manus)는 리서치부터 데이터 분석까지 다단계 워크플로를 조율하며, 오픈소스 플랫폼(AutoGPT, OpenHands, OpenClaw)은 확장 가능한 프레임워크를 제공한다.

그런데 이 전환이 병목의 위치를 바꾼다. 질의응답(QA)에서는 모델 능력의 점진적 개선 — 더 큰 파라미터, 더 많은 학습 데이터, 더 나은 정렬 — 이 직접적이고 예측 가능한 이득을 낸다. 그러나:

  • 그 능력을 재는 전통적 벤치마크(MMLU, GPQA, HumanEval)는 프론티어에서 점점 포화하고 있으며, 오염(contamination) 위험이 해석을 더 복잡하게 만든다. 판별력을 회복하기 위해 Humanity's Last Exam 같은 더 어려운 평가가 제안되었다.
  • 더 결정적으로, 평가가 닫힌 형태의 QA에서 상호작용적 다단계 과제 수행으로 옮겨가면 프론티어 모델조차 상당한 신뢰성 격차를 드러낸다 — SWE-bench, WebArena, OSWorld, TheAgentCompany, Terminal-Bench 모두 agentic 과제에 상당한 여유가 남아 있음을 보인다.

이 갈라짐 — 정적 벤치마크는 포화에 가깝고 agentic 벤치마크는 미해결 — 이 자연스러운 질문을 낳는다. ##모델 스케일링만으로 agentic 과제의 격차가 닫히지 않는다면, 무엇이 닫는가?##

harness라는 용어의 계보

인터페이스 설계가 중요하다는 것을 처음 경험적으로 보인 것은 SWE-agent다 — agent–computer interface (ACI)를 재설계하면 고정된 base model 하에서 SWE-bench 성능을 실질적으로 개선할 수 있음을 보였다. 이후 이 개념이 harness engineering이라는 용어로 결정화되었다(Hashimoto, OpenAI). 이들은 에이전트를 model plus harness로 규정하고, 그 핵심 구성요소로 관측 형성(observation shaping), 행동 공간 설계, 실행 샌드박싱, 컨텍스트 관리, 검증 루프를 지목했다.

최근 연구는 harness를 조작 가능한 대상으로 밀고 나간다 — NLAH는 harness 논리를 편집 가능하고 이식 가능한 자연어 산출물로 형식화하고, Meta-Harness는 harness 구성 자체를 최적화 가능한 탐색 공간으로 취급한다.

이 계보가 중요한 이유: harness는 새 발명이 아니라 이미 모든 배포 시스템에 존재하던 것에 이름이 붙은 것이다. 이름이 붙는 순간 그것은 측정·비교·최적화의 대상이 된다. 이 survey가 하는 일의 상당 부분은 그 측정을 모아 놓는 것이다.

1. 정의와 형식화 (§2)

이 survey가 가장 먼저 하는 일은 두 추상 수준을 분리하는 것이다. 에이전트 문헌에서 이 둘은 자주 혼동된다.

1.1 기능적 관점 — 에이전트란 무엇인가

에이전트 개념은 LLM보다 앞선다. Wooldridge와 Jennings는 지능적 에이전트를 환경에 위치하고, 그 환경을 인지하며, 목표를 추구하며 환경에 작용할 수 있는 시스템으로 특징짓는다. 이 survey에서 결정적 성질은 구현 수단(기호 규칙, 강화학습, 언어모델)이 아니라 환경과의 목표 조건부 루프를 지속하는가다.

따라서 기능적 정의를 채택한다 — 에이전트는 과제 목표를 중심으로 다섯 개의 작동을 조직하는 시스템이다: perception(인지) · state maintenance(상태 유지) · reasoning and decision-making(추론과 결정) · action(행동) · feedback adaptation(피드백 적응). 목표와 환경은 특정 실행을 조건화하지만 에이전트의 내부 구성요소는 아니다.

이 닫힌 루프 성질이 에이전트를 단발 모델 호출, 정적 retrieval 시스템, 관측이 변해도 행동을 수정하지 않는 고정 자동화 스크립트로부터 구분한다.

1.2 구현 관점 — model plus harness

LLM 기반 에이전트에서 이 기능적 루프는 모델 추론 호출 하나로 구현되지 않는다. foundation model은 필요하다 — 개방형 과제 수행을 가능하게 하는 범용 인지 능력을 제공하기 때문이다. 그러나 충분하지 않다 — 모델 자체는 어떤 관측이 가용한지, 어떤 행동이 허용되는지, 장기 상태가 어디에 저장되는지, 실행이 어떻게 검증되는지, 실패가 어떻게 복구되는지를 정의하지 않는다.

따라서 LLM 기반 에이전트를 다음과 같이 쓴다.

$$A_{LLM} = \langle M, H\rangle = \langle M, I_{obs}, C, L, I_{act}, S, V\rangle \tag{1}$$

$M$은 모델 층이다. 가장 단순한 경우 $M$은 단일 foundation model이고, 배포된 다중 모델 시스템에서는 $M = \{M_1, \dots, M_k\}$로 능력·비용·컨텍스트 한계가 이질적인 백본 집합을 뜻한다. $H$는 $M$을 둘러싼 execution harness다.

이 형식화의 미묘한 지점: $|M| = 1$이면 익숙한 단일 백본 설정으로 환원되지만, $|M| > 1$이면 harness가 매 스텝 어느 모델이 행동할지 추가로 결정해야 한다. 즉 다중 모델은 harness에 새 책임(라우팅)을 부과하며, 이것이 §4의 Phase 3 후반부에서 "compositional runtime"이라 불리는 것이다.

1.3 harness — 런타임 substrate

harness는 개별 도구, 메모리 모듈, prompt 템플릿, 워크플로 스크립트보다 넓다. 그것은 어떤 관측이 모델에 도달하는지, 컨텍스트가 어떻게 조립되는지, 에이전트 루프가 어떻게 전진하는지, 행동이 어떻게 실행되는지, 상태와 산출물이 어떻게 지속되는지, 실패가 어떻게 감지·통제·복구되는지를 결정하는 조율 층이다.

$L$Control loopobserve–reason–act–feedback 사이클의 조율스텝 스케줄링, 정지 기준, 재시도, reflection, 위임, handoff, 다중 에이전트 조율. 다중 모델에서는 모델 라우팅과 역할 배정까지

이 분해가 기존 컴포넌트 taxonomy와 다른 점: 순수하게 기능적이 아니라 운영적(operational)이라는 것이다. 예를 들어 "memory"는 기능적 루프에서는 state로 나타나지만, 배포 시스템에서는 컨텍스트 선택, 산출물 저장, retrieval 인덱스, 세션 관리자, checkpoint 정책 중 어느 것으로도 실현될 수 있다. 마찬가지로 "action"은 추상적 행동 공간이 아니라 스키마, 권한, 샌드박스, 실행 API, 부작용 통제를 통해 매개된다.

##런타임 책임을 모델 자체로부터 분리했기 때문에, 이 분해는 "기반 모델이 그대로인데 harness 변경이 성능을 개선하는" 현상을 설명할 수 있다.## 이것이 §7의 정량 증거가 해석되는 틀이다.

2. 모델 중심 스케일링의 한계 (§3)

에이전트를 model + harness로 보면 foundation model 스케일링의 역할을 더 정확히 말할 수 있다. 스케일링은 LLM이 현대 에이전트의 인지 엔진 역할을 할 수 있는 주된 이유로 남는다 — scaling law는 언어모델링 손실이 모델 크기·데이터·compute에 따라 예측 가능하게 개선됨을 보였고, Chinchilla 계열 결과가 compute-최적 배분을 정교화했다.

그러나 모델 크기가 에이전트 성능의 완전한 설명은 아니다. long-horizon 과제 수행은 궤적 수준 성질이기 때문이다 — 에이전트는 반복적으로 관측하고, 컨텍스트를 구성하고, 행동을 선택하고, 상태를 보존하고, 피드백을 해석하고, 오류로부터 복구해야 한다. 따라서 관련 질문은 모델 중심 설명이 어디서 멈추고 런타임 설계가 어디서 시작되는가다. 저자들은 두 개의 경계를 제시한다.

2.1 resource–performance boundary

추가 자원으로 얼마나 많은 추가 능력을 얻는가에 관한 경계다. 모델 용량 증가는 프론티어 성능을 계속 개선하지만, 그 이득이 점점 비싸지고, 능력별로 고르지 않으며, 추론 지연과 배포 복잡도에 제약된다.

대표 사례가 LLaMA 3.1이다. 70B에서 405B로 옮기면 학습 compute가 7.0M → 30.84M H100 GPU-hour로 늘지만, 대표 벤치마크에서의 이득은 완만하다 — MMLU +2.6, MBPP EvalPlus +2.6, GSM8K +1.7. 그리고 더 큰 모델조차 MATH나 MMLU-Pro 같은 어려운 추론 벤치마크에서 완벽에 한참 못 미친다. Qwen3에서도 훨씬 큰 base model의 이득이 벤치마크마다 크게 다른 유사한 불균등이 관측된다.

에이전트에서 이 trade-off가 증폭되는 이유: 배포된 에이전트는 실행 궤적에 걸쳐 모델을 반복 호출하므로 호출당 비용과 지연이 누적되고, 작은 오류가 여러 스텝에 걸쳐 복합된다.

2.2 measurement boundary

두 번째 한계는 스케일링 주도 진보가 어떻게 측정되는가에 관한 것이다. 모델 중심 진보는 정적 벤치마크의 총합 이득으로 검증되어 왔다. 이것은 벤치마크가 모델 세대를 명확히 분리할 때는 정보를 주었지만, 프론티어 시스템들이 같은 지표의 상단에 뭉치면 판별력이 떨어진다. MMLU-Pro와 GPQA Diamond는 여전히 도전적이지만, 최근 GPT·Claude·Gemini 릴리스는 점점 좁은 점수 범위에 모인다.

두 경계의 관계: 첫 번째 경계는 "더 큰 모델을 만드는 것이 비싸다"이고 두 번째는 "만들어도 그 차이를 재기 어렵다"다. 둘이 겹치면 모델 중심 개선의 신호 대 잡음비가 나빠진다. 그래서 개선의 여지가 더 큰 곳 — 런타임 — 으로 관심이 옮겨간다는 것이 이 survey의 논지다.

3. agent engineering의 4개 패러다임 (§4)

저자들은 최근 문헌을 진화적 렌즈로 조직한다. 각 패러다임은 선행 패러다임이 노출한 한계에 대응해 등장했고, 각각 다른 성능 레버를 전면에 둔다. 이 네 단계는 엄격한 시간 분할이 아니라 개념적 렌즈이며, 오늘날 넷이 모두 공존한다.

3.1 Phase 1 — Prompt Engineering

모델에 보내는 단일 턴 지시를 최적화한다. few-shot 예시, chain-of-thought, self-consistency, tree-of-thought 탐색 같은 기법이 과제를 명확히 하고 출력 형식을 제약하며 모델의 잠재 능력을 끌어낼 수 있다.

한계: prompting은 근본적으로 표현 문제(expression problem) — "어떻게 물을까" — 를 다룬다. ##정보 문제(information problem)는 해결하지 못한다 — prompting만으로는 없는 지식을 공급할 수도, 동적으로 변하는 상태를 관리할 수도, 긴 행동 시퀀스에 걸쳐 일관성을 유지할 수도 없다.##

3.2 Phase 2 — Workflows and Context Engineering

최적화 단위가 단일 prompt에서 다단계 실행을 둘러싼 정보 생애주기로 옮겨간다. 핵심 규율은 어떤 정보가 언제 어떤 형태로 모델의 컨텍스트 창에 들어가는지를 큐레이션하는 것이다 — RAG, 장기 메모리 관리, 도구·API 정의, 점진적 skill 공개를 포괄한다.

형식적으로 컨텍스트를 prompt 문자열이 아니라 동적으로 조립되는 런타임 객체로 취급한다.

$$C = A(c_1, c_2, \dots, c_n) \tag{3}$$

$A$는 컨텍스트 구성요소 $c_i$(지시, retrieved 지식, 도구 설명과 출력, 메모리 레코드, 과제 상태, 중간 산출물, 현재 질의)를 최종 컨텍스트 $C$로 결합하는 고수준 조립 함수다.

이 관점에서 공학 문제가 바뀐다 — prompt의 문구를 최적화하는 것에서 실행 중 정보를 retrieve·select·compress·format·refresh하는 함수들을 최적화하는 것으로.

$$F^* = \arg\max_{F} \; \mathbb{E}_{\tau \sim T}\big[\mathrm{Reward}\big(P_\theta(Y \mid C_F(\tau)), Y_\tau^*\big)\big] \tag{4}$$

$F$는 컨텍스트 구성 함수들의 집합이다.

평가 기준도 따라 바뀐다: 질문이 더 이상 "단일 답이 맞는가"만이 아니라 "조립된 컨텍스트가 모델이 다단계 과제를 완수하게 하는가"가 된다.

한계: ##context engineering은 근본적으로 feedforward다.## 각 추론 스텝의 입력을 최적화하지만, 드리프트를 감지하거나 중간 결과를 검증하거나 오류로부터 복구하는 구조적 메커니즘을 제공하지 않는다.

3.3 Phase 3 — Harness Engineering (현재 프론티어)

이 단계는 루프를 닫는다. 올바른 컨텍스트를 조립하는 것을 넘어, harness가 피드백 주도 실행을 도입한다 — 모델이 행동하고, 환경 응답을 관측하고, 그 관측을 추론해 다음 스텝을 결정한다. 더 넓게는 런타임 인프라 전체를 일차 설계 대상으로 취급해 실행 샌드박싱, 상태 checkpoint, 검증 루프, 오류 복구, sub-agent 조율을 지배한다.

지배 질문이 바뀐다 — "모델에게 무엇을 보여줄까"에서 "시스템 전체를 어떻게 궤도에 유지할까"로: 드리프트 방지, 안정적 실행 유지, 오류 복구.

이 단계 안에서도 이미 추가 이동이 보인다:

  • 다중 모델 harness: 런타임이 계획·도구 사용·검증·코딩·도메인 특화 하위 과제를 위해 이질적 모델들을 라우팅·위임·구성한다.
  • 학습 가능한 harness: harness 모듈, 조율 논리, 런타임 정책이 일급 산출물로서 편집·탐색·최적화될 수 있게 된다.

이것은 에이전트 시스템으로 간주되는 것 자체를 바꾼다. 하나의 모델을 감싼 단일 prompt도 여전히 경량 에이전트로 기능할 수 있지만, ##신뢰할 만한 long-horizon 과제 수행은 점점 여러 모델 위의 구성적·최적화 가능한 런타임에 의존하며 prompt 기술만으로는 되지 않는다.##

산업계에서 반복되는 설계 원칙 (저자들이 여러 시스템과 논문에서 추출):

  • Legibility(가독성): 런타임은 올바른 추상 수준에서 올바른 상태를 노출해야 한다.
  • Mechanical enforcement(기계적 강제): 안전·정확성·재현성에 중요한 제약은 가능하면 prompt 순종에 맡기지 말고 런타임이 강제해야 한다.
  • Verification in the loop: 중간 점검 없는 long-horizon 자율성은 구조적으로 취약하다.
  • Explicit artifacts(명시적 산출물): plan, 로그, diff, 요약 등 중간 산출물은 재사용·감사·인수인계 가능한 검사 대상 객체로 존재해야 한다.

3.4 Phase 4 — Agent-Native Training and Co-Evolution (미래)

harness를 손으로 안정화한 런타임이 아니라 구성적이고 점점 학습 가능한 시스템으로 볼 때 시작된다. 중심 질문이 두 갈래다 — 어떤 agentic 행동을 모델 파라미터에 내재화할 것인가, 그리고 모델과 harness가 배포 과정에서 안전성·검사가능성을 희생하지 않고 어떻게 공진화할 것인가.

방향 1 — 상호작용 학습을 통한 내재화: prompt·워크플로·런타임 조율에만 의존하지 않고, 모델이 상호작용 환경에서 계획하고, 도구를 쓰고, 중간 상태를 검증하고, 오류로부터 복구하도록 학습된다. 두 경향이 있다 — (i) RL로 reasoning-to-action 행동을 강화(DeepSeekMath, DeepSeek-R1, DAPO), (ii) 배포에 가까운 환경에서 학습해 train–test 불일치를 줄임(ProRL, WebRL, ComputerRL, Environment Tuning, daVinci-Dev, Kimi-Dev).

##중요한 점: 내재화는 harness를 제거하지 않고 분업을 이동시킨다.## 더 많은 단기 지평 행동이 모델 파라미터로 옮겨갈 수 있지만, 런타임은 여전히 환경 접근·상태·안전 통제를 공급한다.

방향 2 — 공진화와 자기 개선: 모델, harness, 업데이트 정책이 모두 배포 과정에서 변할 수 있고, 실행 피드백으로 어떤 변경을 유지·수정·롤백할지 결정한다.

저자들은 "self-evolve"라는 말 아래 자주 혼동되는 세 층을 분리한다:

  1. Multi-model harness: 각 런타임 역할을 누가 수행하는가를 정의
  2. Learnable harness: 런타임 정책이 어떻게 최적화되는가를 정의
  3. Co-evolution: 모델·harness·개선 루프가 배포 경험으로부터 언제 어떻게 함께 갱신되는가를 정의

이 세 층은 교환 가능하지 않고 상보적이다 — 구성적 런타임이 특화와 위임이 가능한 구조를 만들고, 학습 가능한 harness가 런타임 적응을 명시화하며, 공진화가 검증·안전·비용 제약 하의 long-horizon 개선을 지배한다.

4. execution harness의 해부 (§5)

harness engineering은 최적화 대상을 고립된 prompt나 워크플로에서 에이전트 실행을 안정화하는 런타임으로 옮긴다. 이 런타임은 6개 컴포넌트로 분해된다. 이 분해는 소프트웨어 패키지 다이어그램이 아니다 — 모델 능력이 신뢰할 만한 과제 수행이 되는지를 반복적으로 결정하는 런타임 책임을 식별한 것이다.

각 절의 서술 구조가 일정하다: 무엇을 결정하는가 → 설계 공간 → 대표 시스템 → 지배적 trade-off → 열린 문제. 이 반복 구조가 survey의 가장 실용적인 부분이다.

4.1 Observation Interface ($I_{obs}$)

결정하는 것: 어떤 환경 신호가 모델에 노출되고 그 신호가 어떻게 렌더링되는가. 터미널 출력, 파일 diff, 스크린샷, 웹 DOM, API 응답, 이벤트 스트림, 로그를 현재 모델 호출이 소비할 수 있는 관측으로 변환한다.

설계 공간의 세 질문: 어떤 상태가 관련 있는가 / 어떤 추상 수준으로 표현할 것인가 / 관측을 언제 갱신할 것인가.

왜 중요한가: ##많은 long-horizon 실패는 추론만의 실패가 아니다 — legibility(가독성)의 실패다.## 필요한 상태가 부재하거나, 잡음에 묻히거나, 낡았거나, 다음 결정을 지원하지 않는 수준으로 표현되어 있다.

대표 증거: SWE-agent는 agent-computer interface 재설계가 고정된 base model 하에서 코딩 에이전트 성능을 실질적으로 개선함을 보였다. 웹·데스크톱에서 WebArena와 OSWorld는 성공이 시각적·구조적으로 복잡한 인터페이스 상태가 모델이 실제로 쓸 수 있는 형태로 변환되는지에 달려 있음을 드러낸다.

지배적 trade-off: 풍부함 vs 처리가능성. 풍부한 관측은 grounding을 개선하지만 컨텍스트 비용과 distractor를 늘린다. 압축된 관측은 처리하기 쉽지만 과제에 결정적인 증거를 버릴 수 있다. 원칙은 가용한 모든 상태를 노출하는 것이 아니라, 결정에 관련된 상태를 충실하고 사용 가능한 표현으로 노출하는 것이다.

4.2 Context Manager ($C$)

결정하는 것: 가용한 정보 중 어떤 것이 현재 모델 호출에 들어가며 어떤 형태로 들어가는가. 관측, 도구 출력, retrieved 증거, 메모리 레코드, 요약, 지시, 과제 산출물을 다음 스텝의 작업 컨텍스트가 되기 전에 선택·압축·정렬·갱신한다.

주요 설계 선택: 포함(inclusion) · 표현(representation) · 갱신 정책(refresh policy) · 활성 에이전트/sub-agent에 노출되는 공유 상태의 양.

구현 패턴: retrieval 기반 시스템은 외부 문서나 저장 상태를 온디맨드로 가져온다. MemGPT 같은 메모리 지향 시스템은 활성 컨텍스트와 더 큰 외부 메모리를 분리한다. 산업 harness는 점점 과제 상태를 명시적 산출물로 외부화하고 그 산출물을 선택적으로 다시 표면화하며, 끝없이 커지는 단일 대화 trace에 의존하지 않는다.

지배적 trade-off: 충실도 vs 관리가능성. 원시 이력은 세부를 보존하지만 확장성이 나쁘고, 요약과 retrieved 컨텍스트는 저렴하지만 중요한 상태를 누락·왜곡할 수 있다.

이 절의 핵심 문장: ##결정적 구분은 긴 prompt와 짧은 prompt 사이가 아니라 monolithic 컨텍스트와 managed 컨텍스트 사이다.## long-horizon 성능은 prompt 길이를 늘리는 것보다 시간에 걸쳐 일관된 과제 상태를 유지하는 것에 달려 있다.

4.3 Control Loop ($L$)

결정하는 것: 스텝·도구·handoff에 걸친 실행의 조직. 관측·추론·행동·피드백을 실행 가능한 프로세스로 바꾼다. 에이전트가 단순 perceive-act 사이클을 따르는지, ReAct 스타일 루프인지, plan-execute-verify 루틴인지, 계층적·다중 에이전트 워크플로인지를 결정한다.

주요 설계 질문: 제어가 모델과 런타임 사이에 어떻게 분할되는가 / plan이 언제 생성·수정되는가 / 위임이 언제 도입되는가 / 조율이 순차인가 병렬인가 / 실행이 언제 멈춰야 하는가.

최근 방향: 조율 자체를 최적화 대상으로 만든다 — NLAH는 harness 논리를 편집 가능한 산출물로, Meta-Harness는 harness 구성을 탐색 가능한 설계 공간으로 취급한다.

지배적 trade-off: 적응성 vs 안정성. 자유로운 루프는 예상 못한 상태에 대응할 수 있지만 드리프트·반복 실패·조율 오버헤드에 더 취약하다. 강한 조율은 신뢰성을 높이지만 효율을 떨어뜨리거나 탐색을 과도하게 제약할 수 있다.

##이 층은 단순히 스텝을 추가하는 것이 아니라 궤적에 얼마나 많은 구조를 부과할지 선택하는 것이다.##

4.4 Action Interface ($I_{act}$)

결정하는 것: 모델 출력을 실행 가능한 연산으로 매핑. 에이전트가 무엇을 할 수 있는지, 행동이 어떻게 명세되는지, 어떤 권한이 적용되는지, 행동 결과가 어떻게 후속 관측으로 반환되는지를 정의한다.

최근 진단 연구가 드러낸 것: 에이전트가 실패하는 것은 도구가 없어서가 아니라 — 도구가 잘못 선택되거나, 잘못 호출되거나, 실행 궤적에 제대로 통합되지 않아서다. ET-Agent는 tool-integrated reasoning의 행동 캘리브레이션을 연구하고, ToolTok은 도구를 토큰으로 표현해 GUI 에이전트의 효율과 일반화를 개선한다.

설계 공간: 도구 granularity(저수준 환경 vs 고수준 API) · 도구 명세(자유형 명령 vs 구조화 스키마) · 라우팅과 상호운용성(로컬 도구 vs MCP 같은 프로토콜 생태계) · 거버넌스(권한, 부작용 통제, 호출 제약).

정전적 예: SWE-agent가 observation-action 공동 설계의 정전적 사례다 — agent-computer interface를 재설계하면 모델이 보는 것과 행동하는 방식이 동시에 바뀌며, 고정 base model 하에서 이득이 발생한다.

지배적 trade-off: 유연성 vs 통제가능성. 저수준 도구는 범용이지만 견고하게 쓰기 어렵고, 고수준 도구는 신뢰성을 개선하지만 행동을 과도하게 좁힐 수 있다.

4.5 State and Artifact Store ($S$)

결정하는 것: 스텝·세션·하위 과제에 걸친 실행 상태의 지속. 활성 컨텍스트 창을 넘어 과제 진행 상황, trace, plan, checkpoint, diff, 생성 파일, 메모리 레코드, 재사용 가능한 산출물을 저장해 연속성을 제공한다.

핵심 관찰: ##long-horizon 에이전트는 상태가 저장되지 않아서 실패하는 것이 아니라 — 잘못된 상태가 보존되거나, 올바른 상태를 retrieve할 수 없거나, 낡은 상태가 현재처럼 취급되어서 실패한다.##

지배적 trade-off: 완전성 vs 사용가능성. 풍부한 상태는 연속성·감사가능성·인수인계를 개선하지만 retrieval 부담, 잡음, 낡은 메모리의 위험을 늘린다. 실무적 과제는 더 많이 저장하는 것이 아니라 무엇이 지속될 자격이 있고, 무엇을 압축하고, 무엇을 버릴지 결정하는 것이다.

4.6 Verification and Governance ($V$)

결정하는 것: 런타임 중 실행을 점검·제약·수리한다. Verification은 테스트, assertion, verifier 모델, judge 신호 등 실행이 올바르게 진행되는지 추정하는 메커니즘을 포함한다. Governance는 승인 게이트, 샌드박싱, 예산 통제, rollback, 재시도, 에스컬레이션, 안전 종료를 포함한다.

두 역할의 결합: ##verification은 실행에 대한 증거를 생산하고, governance는 harness가 그 증거로 무엇을 하도록 허용·요구되는지 결정한다.## 따라서 거버넌스는 배포 제약이 아니라 에이전트 실행 내부의 명시적 결정 층이다.

최근 다중 에이전트 거버넌스 연구가 이 관점을 반영한다 — AI Committee는 웹 출처 데이터의 검증과 교정에 다중 에이전트를 사용하고, act-or-refuse 학습은 안전한 다단계 도구 사용 중 에이전트가 진행할지, 보류할지, 중단할지를 연구한다.

6. 평가와 경험적 분석 (§7)

평가는 model–harness 상호작용을 직접 관측 가능하게 만든다. 따라서 벤치마크 점수는 model–harness 쌍의 결과로 해석되어야 한다 — 같은 모델이 컨텍스트 정책, 도구 인터페이스, 제어 루프, 검증 절차, 재시도 예산에 따라 다르게 행동한다.

저자들은 세 상호작용 레짐에서 세 질문에 답한다: 얼마나 많은 성능이 강한 백본으로 설명되는가 / 모델을 조건화한 뒤에도 얼마나 많은 변동이 남는가 / 런타임 비용·지연·타임아웃·trace 가용성이 과제 성공의 해석을 어떻게 바꾸는가.

6.5 벤치마크 통찰 — 네 가지 교훈 (§7.6)

  1. harness 설계는 벤치마크 oracle과 맞아야 한다. 벤치마크가 강한 자동 피드백을 주면(테스트가 있는 코딩) 효과적 harness는 verifier 루프, 패치 정제, rollback을 활용한다. Terminal-Bench가 명령줄 환경에서 같은 원리를 강화한다 — 유용한 harness는 명령 출력·파일·완료 점검을 종료·재시도·수리를 위한 실행 가능 피드백으로 바꾼다. oracle이 약하거나 지연되면(연구, 업무 과제) provenance 추적·중간 검토·보수적 정지에 더 의존해야 한다.
  2. 자율성과 복잡도는 단조로운 선(善)이 아니다. 완전 개방형 루프는 넓게 탐색하지만 컨텍스트·드리프트·비용을 누적한다. 목표가 좁고 성공이 기계적으로 점검 가능하면 ##localization–repair–validation 같은 구조화된 파이프라인이 더 agentic한 루프를 능가할 수 있고, 컴팩트한 scaffold가 풍부한 런타임과 맞먹을 수 있다.## 핵심 설계 질문은 harness가 얼마나 많은 자율성을 노출하는가가 아니라 어떤 자유도가 모델이 벤치마크의 피드백 구조를 활용하도록 돕는가다.
  3. model–harness 호환성이 중요하다. 강한 모델도 잘못된 행동 공간을 노출하거나 컨텍스트 창을 과부하시키는 harness 아래에서는 나쁘게 수행할 수 있다. 반대로 경량 scaffold가 모델의 선호 상호작용 패턴과 벤치마크 피드백 구조에 맞으면 효과적일 수 있다. ##따라서 호환성은 구현 세부가 아니라 model–harness 쌍의 경험적 성질이다.##
  4. 점수는 런타임 구성에 조건부다. 도구 권한, 컨텍스트 정책, 재시도 예산, 샌드박스 제약, 완료 기준이 모두 측정 성능을 형성한다. 따라서 벤치마크 점수는 그것을 만든 런타임 구성과 함께일 때만 해석 가능하다. 리포트는 최소한 모델 버전, harness 정체, 도구 권한, 재시도·타임아웃 정책, 실행 환경, 가능하면 토큰/API 사용량, trace 또는 verifier 메타데이터를 포함해야 한다.

7. 전망과 향후 방향 (§8)

저자들은 세 개의 결합된 방향을 제시한다: value-aware 평가 · agent-native 학습 · harness 일반화.

7.1 점수에서 value-aware 최적화로 (§8.1)

문제: 현재 에이전트 리더보드는 대체로 점수 중심이다 — 시스템이 과제 성공률로 순위 매겨지고 API 비용, 지연, 안전, trace 품질은 부차적이거나 누락된다. 프론티어 비교에는 유용하지만 배포에는 불완전하다.

형식화: 과제 인스턴스 $\tau \sim D$, 모델 $M$과 harness $H$가 확률성 $\omega$ 하에서 생성한 실행 trace를 $z = \mathrm{Run}(\tau; M, H, \omega)$라 하자. trace $z$에 대해 $S(z) \in \{0,1\}$은 과제 성공, $C(z)$는 실행 비용, $L(z)$는 지연, $R(z)$는 안전·컴플라이언스 위험을 나타낸다. $V(\tau) \geq 0$은 과제 효용(사용자 가치, 과학적 가치, 우선순위, 위험 조정 중요도)이다.

model–harness 쌍의 성공 확률은 반복 실행으로 추정된다.

$$P_{succ}(\tau; M, H) = \mathbb{E}_\omega\big[S(\mathrm{Run}(\tau; M, H, \omega))\big] \tag{5}$$

$Q_{proc}(z) \in [0,1]$을 과정 품질(trace 검사가능성, verifier 사용, 복구 행동, provenance 품질, 정책 준수)이라 하고, $\mathrm{Rel}_k(\tau; M,H)$를 $k$회 반복 실행으로 추정한 신뢰성이라 하자. 성공만 최대화하는 대신 value-aware 최적화를 쓸 수 있다.

$$\max_{M,H} \; \mathbb{E}_{\tau \sim D}\Big[V(\tau)\, P_{succ}(\tau;M,H)\, \bar Q_{proc}(\tau;M,H)\Big] \tag{6}$$ $$\text{s.t.} \quad \mathbb{E}_{\tau,\omega}[C(z)] \leq B_C, \quad \mathrm{Quantile}_p(L(z)) \leq B_L, \quad \mathbb{E}_{\tau,\omega}[R(z)] \leq \epsilon, \quad \mathbb{E}_\tau[\mathrm{Rel}_k] \geq \rho$$
이것이 무엇이 아닌지가 중요하다: 저자들이 명시하듯 이것은 보편적 리더보드 점수가 아니다. 과제 가치를 비용·지연·위험·신뢰성과 결합해 배포 목표를 명시적으로 만드는 장치다. trade-off는 과제 의존적이다 — 고가치·고위험 과제는 더 강한 검증을 정당화하고, 일상적 고빈도 과제는 더 싼 모델·짧은 궤적·엄격한 정지 정책을 선호한다.

보완적 목적함수 — value density: $\tilde C(z) = C(z)/B_C$, $\tilde L(z) = L(z)/B_L$, $\tilde R(z) = R(z)/\epsilon$를 정규화 비용·지연·위험이라 할 때

$$VD_{\alpha,\beta,\gamma} = \mathbb{E}_{\tau,\omega}\Big[V(\tau)S(z)Q_{proc}(z)D(z)^{-1}\Big], \quad D(z) = (1+\tilde C(z))^\alpha (1+\tilde L(z))^\beta (1+\tilde R(z))^\gamma \tag{7}$$

$\alpha, \beta, \gamma$가 비용·지연·위험에 대한 페널티를 통제한다. 이는 고정 지표가 아니라 배포별 효용 함수의 계열이다.

같은 trace가 더 단순한 리포트도 지원한다 — 유효 성공당 비용(cost per effective success), 성공 과제당 지연. 이 지표들은 비슷한 성공률을 갖지만 런타임 프로파일이 다른 시스템을 구분한다.

결론적 관점: ##이 관점에서 harness engineering은 자원 배분 문제다.## harness가 모델, 컨텍스트, 메모리 접근, 도구, 재시도, verifier, 정지 규칙, 사람 에스컬레이션을 선택한다. 모델 라우팅·컨텍스트 압축·캐시 재사용·verifier 선택·복구 정책·조기 정지가 구현 세부가 아니라 단위 비용당 유용한 진전을 결정한다.

7.2 검증·복구·적응을 학습하기 (§8.2)

value-aware 관점은 에이전트 학습의 경로도 시사한다. 실행 trace는 평가 기록만이 아니다 — 결과, 비용, 도구 호출, verifier 신호, 재시도, 정책 위반, 피드백을 담고 있다. 미래 에이전트는 계획하고 행동하는 것만이 아니라 중간 상태를 검증하고, 실패를 진단하고, 국소 오류로부터 복구하고, 과제에 걸쳐 적응하는 것도 학습해야 한다.

제약된 자기 진화 루프(constrained self-evolution loop): 반복 $t$에서 모델 파라미터를 $\theta_t$, harness 구성을 $\phi_t$라 하자. $D$의 과제에 에이전트를 실행하면 trace $Z_t$가 생기고, 여기서 결과·실패 모드·verifier 결과·비용 프로파일·안전 이벤트를 담은 증거 집합 $E_t$를 추출한다. 업데이트 연산자 $U$가 모델, harness, 또는 둘 다를 바꿀 수 있다.

$$(\theta_{t+1}, \phi_{t+1}) = \mathrm{VerifyRetain}\big(U(\theta_t, \phi_t, E_t)\big) \tag{8}$$

$\mathrm{VerifyRetain}$은 held-out 과제, 회귀 테스트, 과정 점검, 안전 제약을 통과할 때만 업데이트를 유지하고, 그렇지 않으면 거부하거나 롤백한다.

##이 식은 고정된 알고리즘이 아니다 — 제어 구조를 명시하는 것이다: 신뢰할 만한 자기 진화는 경험 추출, credit assignment, 수정, 검증을 결합해야 한다.##

7.3 harness 일반화 vs 명세 (§8.3)

이 절이 이 분야의 근본 긴장을 다룬다. 범용 harness는 재사용성을 높이고 엔지니어링 비용을 낮추지만 목표 병목에 대한 귀납 편향이 약할 수 있고, 특화 harness는 최고 성능을 높이지만 이식성을 떨어뜨리고 벤치마크 특이적 표면에 과적합할 수 있다.

실무적 방향 — 계층화 설계: 범용 substrate + 도메인 특화 adapter.

  • substrate: 로깅, 격리, 권한 통제, 지속성, 비용 계정, 표준화된 도구 접근, 감사가능성
  • adapter: 관측, 행동, verifier, 메모리 정책, 재시도·rollback·정지·에스컬레이션 규칙

MCP와 A2A 같은 프로토콜이 커넥터 파편화를 줄이고 상호운용성을 개선하지만, ##프로토콜 표준화는 harness 일반화와 같지 않다## — harness는 여전히 무엇을 노출할지, 어떤 행동을 허용할지 결정해야 한다.

비판적 분석 (Critical Analysis)

강점

  • 어휘를 만든다 — 그리고 그것이 이 survey의 실질적 산출물이다. $H = \langle I_{obs}, C, L, I_{act}, S, V\rangle$라는 6-튜플과 운영적 vs 기능적 구분(그림 6)은 "memory를 개선했다" 같은 서술이 왜 재현·비교 불가능한지를 설명하고, 그 자리를 대체할 언어를 준다. survey의 가치는 흔히 참고문헌 목록에 있는데, 이 논문은 말하는 방식을 바꾸려 한다.
  • 양방향 증거를 나란히 제시한다. §7의 방법론적 미덕이 여기 있다 — harness 효과를 강조하면서도 harness를 고정하면 모델 세대가 30%p를 만든다는 반대 증거(Codex CLI에서 49.6% → 82.2%)를 함께 제시한다. 그래서 "harness만 중요하다"는 과잉 주장에 빠지지 않는다. ##이 균형이 없으면 §7 전체가 harness 옹호론이 되었을 것이다.##
  • 자기 증거의 경계를 필드 단위로 공개한다. Terminal-Bench 공개 로그 75건 중 48건만 엄격히 일치하고, 토큰 필드 45.0%, 달러 비용 15.2%라고 밝힌 뒤 그래서 cross-harness 비용 주장을 하지 않는다고 명시한다(그림 18). survey에서 "우리 데이터로는 이 주장을 할 수 없다"고 쓰는 경우는 드물며, 이 절제가 나머지 수치의 신뢰도를 높인다.
  • 도메인 라벨을 압력 프로파일로 환원한다. §6이 이 survey에서 가장 이식성 높은 부분이다 — 코딩/웹/의료라는 라벨 대신 horizon · 관측성 · oracle 강도 · 비가역성 · 자율성이라는 5개 축으로 구성 규칙을 세운다. 새 도메인(예: 금융 백오피스, 반도체 공정)을 만났을 때 도메인 사례가 없어도 압력 프로파일만 알면 harness를 설계할 수 있다.
  • 반직관적 관측을 발굴한다. (i) 약 100줄 Python인 mini-SWE-agent가 완전한 샌드박스 런타임과 4문항 차이(그림 17). (ii) 더 많은 컨텍스트가 더 빠르다 — Meta-Harness가 Terminus 2보다 9.5배 큰 컨텍스트로 타임아웃을 18.2% → 7.9%로 줄인다. (iii) 모델 제작사 자체 CLI(Gemini CLI 59.4%)가 서드파티 harness(TongAgents 80.2%)에 20.8%p 뒤진다. 이 셋은 각각 "복잡할수록 좋다", "토큰을 아끼면 빠르다", "제작사가 자기 모델을 가장 잘 안다"는 통념을 깬다.
  • value-aware 목적함수를 지표가 아니라 계열로 제시한다. Eq. 6~7을 "새 리더보드 점수"로 팔지 않고 배포별로 인스턴스화되는 효용 함수 계열이라고 명시한다. 그리고 더 단순한 대안(유효 성공당 비용, 성공 과제당 지연)도 함께 제시해 실무 채택 문턱을 낮춘다.
  • "self-evolve"의 세 층을 분리한다. multi-model harness(누가) / learnable harness(어떻게) / co-evolution(언제)의 구분(그림 9)은 유행어가 뭉개는 서로 다른 질문을 갈라놓는다. 이 구분은 후속 연구가 자기 기여를 정확히 위치시키는 데 바로 쓰인다.

한계와 의문점

  • 핵심 수치가 통제된 실험이 아니라 관찰적 종합이다. 저자들이 이를 명시하지만, 그 한계는 결론의 강도에 실질적으로 영향을 준다. Table 7의 행들은 모델 스냅샷·reasoning 설정·재시도 예산이 정렬되어 있지 않고, Table 9의 WebArena 결과는 대부분 완전한 에이전트 시스템이라 prompt·탐색 예산·학습 데이터 차이가 harness 효과에 섞여 있다. ##즉 "harness가 X%p를 만든다"는 문장은 엄밀히는 "harness를 포함한 시스템 구성 전체가 X%p를 만든다"이다.## 가장 깨끗한 것은 Terminal-Bench 뿐인데, 그마저 공개 제출이라 prompt·버전·예산이 다르다.
  • Table 7의 가장 흥미로운 패턴을 논평하지 않는다. 이 문서가 계산한 바(그림 16) 모델이 강해질수록 harness span이 줄어든다 — Claude 3.5 Sonnet 20.0%p → 3.7 Sonnet 10.4 → Sonnet 4 7.5 → Opus 4/4.5 4.4. 이것이 사실이라면 survey의 중심 주장에 중요한 단서가 붙는다: harness의 상대적 중요성이 모델 세대와 함께 감소할 수 있다. 저자들은 이 추세를 언급하지 않으며, 각 행의 harness 조합이 다르므로 확정할 수도 없다 — 그러나 제기되지 않은 것이 문제다.
  • Meng et al.과의 차별화가 얇다. Table 1에서 Meng et al.(2026.04)이 이미 "6-컴포넌트 튜플"로 harness를 형식화했다고 스스로 밝힌다. 이 survey의 $\langle I_{obs}, C, L, I_{act}, S, V\rangle$가 그것과 얼마나 다른지, 어디가 개선인지에 대한 구체적 비교가 없다. 저자들은 "우리 기여는 또 하나의 taxonomy가 아니라 병목 이동의 분석"이라고 하지만, §5 전체(6페이지)가 컴포넌트 해부에 쓰인다.
  • "병목이 이동한다"는 중심 서사가 정량적으로 검증되지 않는다. §6의 도메인별 병목 할당(코딩=$V$, 웹=$I_{obs}$…)은 대표 시스템에 대한 정성적 독해이지 측정이 아니다. 예컨대 "코딩에서 $V$가 주 병목"이라는 주장을 검증하려면 $V$만 제거하거나 약화한 ablation이 필요한데, 그런 연구는 인용되지 않는다. 그림 12의 매트릭스는 설득력 있지만 가설의 시각화이지 증거의 시각화가 아니다.
  • 비용 축이 사실상 비어 있다. value-aware 평가를 §8의 중심 제안으로 삼으면서, 정작 §7에서 비용 데이터는 거의 쓰지 못한다(달러 필드 15.2%). Table 7에 비용이 있는 행은 Claude 3.5 Sonnet 4개뿐이고(Agentless $1.19, AutoCodeRover $4.50, OpenHands $0.78, PatchPilot $0.99), 이마저 4배 가까운 차이가 나는데 논평이 없다. ##"비용을 보고하라"고 주장하는 survey가 자기 표에서 비용을 분석하지 않는 것은 논지의 약점이다.##
  • 안전·거버넌스가 컴포넌트로만 다뤄진다. $V$가 6개 중 하나로 등장하고 의료 도메인에서 "safety-dominant"로 언급되지만, harness가 안전 실패의 원인이 되는 경로(과도한 권한, 잘못된 샌드박스 경계, 감사 부재)에 대한 체계적 분석은 없다. OS-Harm이 Table 6에 한 줄로 있을 뿐이다. 배포 시스템에서 harness가 안전의 유일한 통제점이라는 점을 고려하면 불균형하다.
  • 2020~2026 범위인데 사실상 2024~2026이다. Scope에서 2020년부터라고 밝히지만 인용과 분석은 압도적으로 최근 2년에 몰려 있다. 이는 분야 특성상 자연스럽지만, "evolution-first"를 표방하면서 초기 단계(Phase 1)의 서술이 얇다는 불균형을 낳는다 — prompt engineering에 반 페이지, harness engineering에 여러 페이지다.
  • 일부 수치의 출처 추적이 어렵다. Terminal-Bench의 Claude Code 58.0%, Gemini CLI 59.4%, TongAgents 80.2% 같은 값은 본문에서 언급되지만 Table 8에는 없다(Table 8은 토큰·시간이 있는 행만 담는다). 독자가 검증하려면 리더보드를 직접 봐야 하고, 리더보드는 시간에 따라 변한다 — 저자들이 지적한 "24건이 이름 불일치로 제외" 문제가 이 survey 자신의 인용에도 적용된다.
  • harness 설계의 비용이 다뤄지지 않는다. "harness가 20%p를 만든다"는 매력적이지만, 그 20%p를 얻는 데 드는 엔지니어링 시간은 논의되지 않는다. mini-SWE-agent(100줄)와 OpenHands(대규모 시스템)의 성능이 비슷하다는 관측은 이 질문을 직접 제기하는데도 저자들은 "인터페이스 설계가 중요하다"로 넘어간다. 실무자에게는 "어느 harness를 쓸까"만큼 "harness에 얼마나 투자할까"가 중요하다.

Key Takeaways — 이 survey에서 가져갈 것

  1. 어휘를 먼저 가져가라 — 그것이 이 survey의 가장 큰 산출물이다. 자기 시스템을 $\langle I_{obs}, C, L, I_{act}, S, V\rangle$로 서술할 수 있게 되면 재현·비교·ablation이 가능해진다. "memory를 개선했다"가 아니라 "$S$에 checkpoint를 추가하고 $C$의 요약 정책을 교체했다"고 말하는 순간, 그 변경은 측정 대상이 된다. 팀 내부 설계 문서와 실험 리포트의 템플릿을 이 6개 기호로 바꾸는 것이 가장 값싼 첫 조치다.
  2. 진단 체크리스트: 6개 실패 모드로 자기 에이전트를 훑어라. $I_{obs}$ legibility 실패(필요 상태가 부재/묻힘/낡음) · $C$ monolithic 컨텍스트(끝없이 커지는 단일 trace) · $L$ 드리프트와 반복 실패 · $I_{act}$ 도구 오사용(없어서가 아니라 잘못 선택·호출됨) · $S$ 낡은 상태를 현재로 취급 · $V$ 검증 없는 자율성. ##특히 $S$와 $I_{act}$의 실패 모드가 반직관적이다 — 저장이 없어서나 도구가 없어서가 아니다.##
  3. 과제 압력 프로파일을 먼저 그리고 그다음에 harness를 설계하라. 도메인 라벨이 아니라 5개 축(horizon · 관측성 · oracle 강도 · 비가역성 · 자율성)이 구성을 정한다. 실무 규칙 세 개: (i) 강한 자동 oracle이 있으면 verifier 루프·수리 사이클에 크게 투자하라 — 닫힌 루프 최적화가 가능하다. (ii) oracle이 약하면 병목이 상류(provenance·중간 검토·보수적 정지)로 이동한다. (iii) 행동이 비가역이면 $V$가 주변 add-on이 아니라 주 병목이다.
  4. 복잡한 harness를 짓기 전에 인터페이스를 고쳐라. 약 100줄 Python인 mini-SWE-agent가 완전한 샌드박스 런타임과 500문항 중 4문항 차이다(76.8% vs 77.6%). 저자들의 결론대로 scaffold 효과는 기능 개수가 아니라 인터페이스 설계에서 온다. 그리고 SWE-agent의 원래 교훈이 그것이었다 — agent-computer interface 재설계만으로 고정 모델에서 이득이 났다.
  5. 토큰을 아끼는 것과 시간을 아끼는 것은 같은 방향이 아니다. Meta-Harness는 Terminus 2보다 9.5배 큰 컨텍스트(755.0K vs 79.4K)를 쓰면서 타임아웃을 18.2% → 7.9%로 줄인다. 해석하자면 컨텍스트를 아끼는 harness는 필요한 상태를 다시 발견하기 위해 추가 명령을 실행하고, 그 재발견 루프가 wall-clock을 늘린다. 자기 시스템에서 컨텍스트 압축을 도입할 때 타임아웃률을 함께 측정할 것.
  6. 벤치마크 점수를 인용·보고할 때 harness 구성을 함께 적어라. 최소 항목: 모델 버전 · harness 정체 · 도구 권한 · 재시도/타임아웃 정책 · 실행 환경 · 토큰 사용량 · trace 메타데이터. 이것 없이는 점수가 해석 불가능하다. 그리고 남의 비교표를 볼 때 이 항목이 없으면 model–harness 시스템 비교이지 모델 비교가 아니다라고 읽을 것.
  7. 평가 목적함수를 명시하면 순위가 바뀐다. 그림 22의 계산대로, 리더보드 최하위(Terminus 2, 64.7%)가 토큰 정규화 후 value density 1위가 될 수 있다. ##"어떤 harness가 최고인가"는 $\alpha,\beta,\gamma$를 정하기 전까지 답이 없는 질문이다.## 무거운 형식화가 부담이면 저자들이 제안하는 단순 대안부터 쓸 것 — 유효 성공당 비용, 성공 과제당 지연.
  8. "self-evolving agent"를 세 층으로 갈라 읽어라. multi-model harness(각 역할을 누가) / learnable harness(런타임 정책이 어떻게 최적화되는가) / co-evolution(모델·harness·개선 루프가 언제 어떻게 함께 갱신되는가). 이 셋은 교환 가능하지 않다. 자기 로드맵을 이 축으로 나누면 지금 하려는 것이 어느 층인지가 분명해진다.
  9. 비판적으로: 이 survey의 수치를 "harness가 X%p를 만든다"로 인용하지 말 것. 세 벤치마크의 span은 비교 기준이 서로 다르다 — WebArena 41.5%p는 harness 유무, SWE-bench 20.0%p는 시스템 구성 전체, Terminal-Bench 13.6%p만이 같은 조건의 harness 간 차이다. 가장 안전한 인용은 Terminal-Bench 모델 내 중앙값 13.6%p, 20개 모델 중 14개가 10%p 이상 변동이다. 그리고 이 문서가 발견한 미논평 추세 — 모델이 강해질수록 harness span이 줄어든다(20.0 → 4.4%p) — 를 함께 기억할 것. 사실이라면 harness 투자의 한계 효용이 모델 세대와 함께 감소한다는 뜻이다.
