TL;DR

  • 문제: LLM(large language model) 에이전트가 수백~수천 턴을 돌면 컨텍스트가 한도를 넘는다. 지금까지는 harness(에이전트를 감싼 외부 제어 코드)가 "75% 차면 요약" 같은 고정 규칙으로, 혹은 사람이 미리 정해 둔 몇 개의 tool(압축·offload·검색)로 컨텍스트를 관리했다. 이런 고정 전략은 "needle 보존", "보드 한 칸만 고치기", "대용량 값 내보내기" 같은 단순 과제에서도 압력이 오르면 무너진다(§3).
  • 해결: Context Language Model (CLM) — 다음 컨텍스트를 모델이 직접 만든다: $c_{t+1} = f_\theta^{\text{CLM}}(c_t)$. 구현은 단순하다. 라이브 컨텍스트를 편집 가능한 파일로 미러링하고 경로를 system prompt에 알려 준 뒤, 모델이 Bash/Python으로 그 파일을 고치면 다음 요청에 자동 반영한다. 손대지 않으면 기본은 append.
  • 왜 작동하는가: 연산 집합 자체를 모델이 코드로 정의할 수 있으므로(새 role 창설, 재사용 함수, 루프 압축 — §4.1), 과제마다 맞는 전략이 창발한다. 또 컨텍스트 관리가 "모델의 행동"이 되었기 때문에 자연어 지시·skill 진화(in-context)와 RL(in-weight)로 학습할 수 있고, 편집으로 깨지는 prefix cache 비용은 prefix-reuse FLOPs(floating-point operations, 부동소수점 연산 수)로 정직하게 계산하고 Suffix Cache Reuse로 줄인다.
  • 비유: 기존 방식은 비서가 정해진 시각에 책상 위 서류를 "요약 메모 한 장"으로 바꿔 놓는 것이고, CLM은 일하는 본인이 책상(컨텍스트)을 직접 정리하는 것이다 — 어떤 서류는 서랍(파일)에 넣고, 어떤 건 포스트잇으로 줄이고, 자주 하는 정리는 "정리 매크로"로 만들어 반복한다.

핵심 기여 (Key Contributions)

  1. CLM 정식화와 context-as-a-file 구현: append-only 전이(Eq. 1)를 모델 제어 전이(Eq. 2)로 일반화하고, 라이브 컨텍스트를 Bash로 편집 가능한 파일로 노출하는 최소 구현을 제시. 파일 여러 개 = 멀티에이전트(swarm·subagent)로 자연 확장된다.
  2. ContextBench와 prefix-reuse FLOPs: 추론·지식을 배제하고 컨텍스트 관리만 재는 4과제 진단 벤치마크(§3)와, 중간 편집에 따른 재-prefill까지 포함한 궤적 단위 이론 비용 지표(Eq. 3, 부록 C).
  3. Zero-shot으로 기존 방법 능가: Qwen3.6-27B에서 BrowseComp-Plus 59.4%(최강 baseline 대비 상대 +11.4%, FLOPs −21.5%), TerminalBench 2.1 동률에 FLOPs 70%, TBLite 73.7 vs 67.0. OpenEvolve 대비 수학 최적화 4문제 모두 우위, 12시간 EdgeBench +5%(FLOPs −59%), 24시간 6-agent swarm에서 speedup 개선폭 +65%.
  4. 학습 가능한 컨텍스트 관리: 자연어 한 문장 steering, skill 진화 루프(KV Store held-out 38.3→74.2, +35.9pt), 그리고 stepwise GRPO + success-gated efficiency advantage(Eq. 6)로 Qwen3.5-9B BCP 28.8→42.5%, PFLOPs 1.52→1.34.
  5. Suffix Cache Reuse (SCR): 편집 뒤에 살아남은 구간의 KV를 재배치(RoPE 재회전)하고 선형 attention 층은 상태 스냅샷을 이어 쓰는 SGLang 패치. 정확도 동일(60.2%)에 서버 측 PFLOPs −35%.

배경 (Background) — 컨텍스트 관리, 캐시, 그리고 학습 신호

이 논문을 이해하려면 다섯 가지 배경이 필요하다: (B.1) 에이전트에서 "컨텍스트 관리"가 무엇이고 지금은 누가 하는가, (B.2) 모델에게 권한을 조금씩 넘겨 온 계보, (B.3) 입력을 컨텍스트 밖에 두는 Recursive Language Model, (B.4) 서빙 시스템의 prefix cache와 hybrid 모델 구조, (B.5) GRPO와 프롬프트 진화. 각 항목은 이 논문이 어디를 바꿨는지와 연결된다.

B.1 에이전트의 컨텍스트 관리와 harness

컨텍스트(context)는 매 호출에서 LM이 보는 토큰 열 전체 — system prompt, 과제 설명, 지금까지의 도구 호출과 관측(observation), 모델 자신의 출력 — 이다. 에이전트가 터미널 명령을 수십 번 실행하거나 검색 결과 문서를 수십 개 읽으면 이 열은 금세 32K~272K 한도를 넘는다. 표준 LM은 매 턴 출력을 끝에 붙이기만 하므로(아래 Eq. 1), 누군가 중간에 줄여 줘야 한다.

harness는 모델 바깥에서 이 루프를 돌리는 코드(프롬프트 템플릿, 도구 실행기, 턴 제한, 그리고 컨텍스트 관리 규칙)를 말한다. 대표적인 규칙은 다음과 같다.

  • Compaction(압축·요약): 일정 길이(예: 예산의 75%)에 도달하면 system prompt와 과제 메시지를 뺀 나머지를 모델이 쓴 요약 메시지 하나로 교체. Codex(OpenAI), Cursor(Cassano & Rush), Terminus2가 이 방식이며, 이 논문은 이를 Codex-style Summary baseline으로 쓴다(부록 E: Codex 요약 프롬프트, 75%에서 압축).
  • 매 턴 통합: MEM1은 매 턴 "이전 턴에서 남길 정보 + 새 관측"만 남겨 컨텍스트를 거의 일정하게 유지한다.
  • Offloading / Retrieval: 큰 관측을 파일·메모리로 빼 두고 필요할 때 다시 불러온다.

RL로 이런 절차 안에서의 성능을 올리는 연구(Composer, CompactionRL, MEM1)도 있지만, 언제·어떻게 갱신하는지는 여전히 harness가 정한다(부록 A). 이 저장소의 Agent System and Harness Design 서베이와 Code as Agent Harness 요약이 harness의 일반 구조를 다룬다(원문 미인용, 이 저장소의 관련 요약).

B.2 권한을 조금씩 넘겨 온 계보 — action-based context management

최근 연구는 컨텍스트 관리 연산을 tool로 만들어 모델의 action space에 넣는다. Self-Compact·AutoCompact는 모델이 "언제" 압축할지 고르고, Context-as-a-Tool은 미리 정한 구간에 대한 압축을 모델이 트리거하며, ACM은 여기에 offload·retrieve를 더한다. Context Folding은 하위 궤적으로 가지를 쳤다가 돌아올 때 요약으로 접고, AgentFold는 최근 상호작용을 접는 지시어를 쓰며, Sculptor는 메시지 조각 단위로 요약·숨김·복원·검색을 허용한다. AgeMem은 장기 메모리 연산과 현재 컨텍스트 요약·필터 tool을 결합한다.

공통 한계는 연산의 종류와 그 밑의 전략이 tool 인터페이스로 고정되어 있다는 점이다. 모델은 "어느 버튼을 언제 누를지"만 배울 수 있다. 이 논문은 이 사다리의 꼭대기 — 버튼 자체를 모델이 만드는 단계 — 를 주장한다.

B.3 Recursive Language Models — 입력을 REPL 변수로

RLM(Zhang et al., 2025a)은 긴 입력을 read-eval-print loop(REPL)의 변수로 두고, 모델이 코드로 일부를 읽거나 재귀 호출로 처리하게 한다. 이는 언제·무엇을 컨텍스트로 읽어 들일지를 해결하지만, 읽어 들인 정보는 여전히 라이브 컨텍스트 끝에 붙어 계속 자란다. 원문의 구분은 두 가지다: (i) RLM은 입력을 외부화하지 실행 중 쌓이는 상호작용 이력을 외부화하지 않고, (ii) 모델의 라이브 컨텍스트 접근은 read-only다. CLM은 라이브 컨텍스트를 read-write로 만든다. 두 방식은 보완적이다 — RLM식 접근으로 큰 입력을 밖에 두고, CLM으로 들여온 정보와 생성된 이력을 관리할 수 있다(부록 A). 이 저장소의 RecursiveMAS 요약이 재귀 호출 계열을 다룬다(원문 미인용, 이 저장소의 관련 요약).

B.4 Prefix cache, radix tree, 그리고 hybrid 모델

LLM 서빙 엔진(SGLang, vLLM)은 이전 요청과 앞부분이 같은 새 요청에 대해 그 앞부분의 KV cache를 재사용한다(prefix caching). SGLang은 이를 토큰 열 위의 radix tree로 관리한다 — 각 간선이 토큰 구간과 그 KV를 들고, 공통 접두사를 가진 요청은 한 경로를 공유하며, 새 요청은 가장 긴 일치 접두사를 찾아 나머지만 prefill한다(부록 B). 각 토큰의 K·V는 앞의 모든 토큰과 RoPE(rotary position encoding)를 통한 절대 위치에 의존하므로, 이 재사용은 append-only일 때만 정확하다. 컨텍스트 중간을 고치면 그 뒤의 토큰은 내용이 그대로여도 전부 다시 prefill해야 한다.

평가에 쓰인 Qwen3.6-27B는 hybrid 모델이다: 64층 중 48층이 Gated DeltaNet(선형 attention), 16층만 full attention이다(각주 3, 부록 C). 선형 attention 층은 토큰별 KV 대신 고정 크기 순환 상태를 유지하므로, 캐시 일치는 상태 체크포인트가 저장된 노드에서만 재개될 수 있다. SGLang은 이 상태를 요청 경계에만 저장하기 때문에, 분기점이 캐시 구간 안쪽이면 훨씬 짧은 접두사로 후퇴한다 — 이 점이 §5.3·부록 B의 "남은 병목"으로 다시 등장한다. full attention 층의 output gate 구조는 이 저장소의 Gated Attention 요약 참고(원문 미인용, 이 저장소의 관련 요약).

B.5 GRPO와 프롬프트 진화

GRPO(Group Relative Policy Optimization)는 한 프롬프트에 대해 $G$개의 응답(여기서는 에이전트 궤적 전체)을 샘플링하고, 그룹 안에서 보상을 정규화한 값을 advantage로 쓴다:

$$A_i^{\text{out}} = \frac{r_i - \operatorname{mean}(r_1,\dots,r_G)}{\operatorname{std}(r_1,\dots,r_G)}$$
직관적으로 말하면: 같은 문제를 여러 번 풀게 하고 "평균보다 잘한 시도는 강화, 못한 시도는 억제"한다. value network가 필요 없어서 긴 에이전트 궤적에 쓰기 좋다.

문제는 CLM이 컨텍스트를 편집하면 궤적이 더 이상 append-only가 아니라는 점이다. 최종 컨텍스트에는 앞서 행동을 생성할 때 보던 입력이 남아 있지 않을 수 있다. 그래서 ReSum·Sculptor처럼 중간 컨텍스트를 보존하고 각 생성 구간을 원래 입력 아래에서 평가해야 하며, 궤적 단위 advantage를 모든 구간에 방송(broadcast)한다 — 이것이 이 논문의 "stepwise GRPO"다(§4.2). GRPO 계열의 안정화 논의는 이 저장소의 GSPO 요약 참고(원문 미인용, 이 저장소의 관련 요약).

프롬프트 진화: GEPA(Agrawal et al., 2026)는 롤아웃 궤적을 읽은 proposer LM이 프롬프트를 반성적으로 고쳐 쓰고, Pareto frontier를 유지하며 후보를 선택한다. 이 논문은 이 루프를 그대로 써서 "컨텍스트 관리 skill 문서"를 진화시킨다(§4.2, Eq. 5).

§1 서론 — 왜 컨텍스트 관리를 모델에게 넘기나

왜 문제인가: 컨텍스트는 LM이 시간에 걸쳐 정보를 처리·유지하게 해 주는 초석인데, 정작 컨텍스트 관리는 LM의 네이티브 능력이 아니었다. 사람이 손으로 짠 harness나 에이전트가 오프라인 최적화한 harness(Meta-Harness)가 결정하고, 최근 연구는 compaction·offloading·retrieval 같은 고정 전략의 tool을 몇 개 action space에 넣는 데 그쳤다.

주장: 모델에게 무제한 접근권을 주면 사람이 설계한 baseline을 이기고, 적응적·창의적인 전략이 창발한다. 저자들은 이를 The Bitter Lesson(Sutton, 2019)에 빗댄다 — 사람의 사전지식을 넘어서는 전략을 LM이 탐색·학습하게 두라는 것이다.

무엇을 보이나: (1) 기존 LM(Qwen3.6-27B, GPT-5.6-Sol 등)을 zero-shot으로 CLM으로 만들면 수백~수천 턴, 최대 24시간짜리 과제에서 baseline과 과제 특화 harness를 이긴다. (2) 편집이 서빙에 주는 부담은 prefix-reuse FLOPs로 계산해도 CLM이 더 효율적이고, SCR로 더 줄일 수 있다. (3) 컨텍스트 관리가 모델 행동이 되었으므로 자연어 지시, skill 진화, RL로 개선된다. 정성적으로는 멀티에이전트 지휘용 트래커 유지, 내부 노트용 새 chat role 창설, 재사용 가능한 컨텍스트 관리 함수 정의 같은 창발 행동이 관찰된다(§4.1 정성 사례).

§2 관련 연구 (Related Work + 부록 A)

원문 §2는 두 갈래로 요약된다. (1) harness 정의 → action 기반: 모델 자율성은 증가해 왔지만 사람이 정한 action space에 묶여 있고, 이 논문은 그 자율성을 "컨텍스트 전권"으로 끝까지 민다. (2) Context as a REPL variable: RLM은 읽기를 해결하지만 라이브 컨텍스트 자체의 관리는 다루지 않는다(배경 B.3). 부록 A는 여기에 메타 최적화, 비-prefix KV 재사용, RL, 성공 조건부 효율 목표, 외부 메모리와의 관계를 추가한다. 아래 표는 이를 비교 축으로 정리한 것이다.

§3 Pilot Study — ContextBench: 컨텍스트 관리만 재는 진단

왜 이 실험인가: 실제 벤치마크 점수는 추론·지식·도구 사용 능력이 섞여 있어, "컨텍스트 관리가 나빠서 졌는지"를 분리할 수 없다. 저자들은 추론이나 검색이 전혀 필요 없고 모든 것을 기억하기만 하면 만점인 합성 과제 4개를 만들고, 입력량만 키워 컨텍스트 압력을 올린다.

3.1 과제 설계 (부록 D, Table 3, Figure 16)

§4 Context Language Models (CLMs)

4.1 정식 정의와 context-as-a-file 구현

Eq. 1 → Eq. 2 — append-only 전이의 일반화

왜 문제인가: 표준 LM의 컨텍스트 전이는 "붙이기"뿐이다.

$$c_{t+1} = c_t \oplus f_\theta^{\text{LM}}(c_t) \tag{1}$$

여기서 $\oplus$는 이어 붙이기(concatenation), $c_t$는 턴 $t$의 컨텍스트다. 컨텍스트를 줄이는 모든 일은 이 식 바깥(harness)에서 일어난다.

해법: CLM은 다음 컨텍스트를 만드는 책임 전체를 모델에 넘긴다.

$$c_{t+1} = f_\theta^{\text{CLM}}(c_t) \tag{2}$$

$f_\theta^{\text{CLM}}$은 CLM이 제어하는 임의의 함수다. Eq. 2는 harness를 통해 컨텍스트 관리 tool 집합을 노출하는 기존 방법들을 포함한다(그 tool들이 $f$의 특수형). 차이는 기존 방법은 그 함수들을 harness에 미리 정의해야 하지만, CLM은 그 함수 자체를 정의하는 것을 메타 능력(meta-capability)으로 모델에 맡긴다는 점이다 — 계획 속에서 암묵적으로, 혹은 재사용 가능한 함수로 명시적으로(Figure 3d).

직관적으로 말하면: 표준 LM은 "일기장에 계속 이어 쓰기만" 할 수 있고, 정리는 다른 사람이 해 준다. CLM은 일기장 전체를 매일 아침 스스로 다시 편집해서 쓸 수 있다 — 지난 주 내용을 한 줄로 줄이든, 표로 바꾸든, 통째로 서랍에 넣든 마음대로다.

Context-as-a-file 구현

CLM을 구현하기 위해 LM의 라이브 컨텍스트를 직접 편집 가능한 파일로 미러링하고, 그 경로를 system prompt에 제공한다(부록 E의 프롬프트 예: /tmp/.live_ctx/LIVE_CTX_MAIN.txt). LM은 일반 Bash 명령으로 저장소의 다른 파일처럼 이 파일을 편집한다. 일반 파일과 달리 컨텍스트 파일의 편집은 LM의 컨텍스트와 자동 동기화되어 LLM 서버로 전송된다. LM이 파일을 편집하지 않으면 생성된 토큰은 기본적으로 기존 컨텍스트에 덧붙는다. 원문은 이 설계가 "컨텍스트 재사용(append 시 캐시 재사용)과 편집의 유연성 사이의 균형"을 잡는다고 설명한다.

멀티에이전트 확장: 여러 컨텍스트 파일이 공존하고 각자의 LLM 서버 세션과 동기화되게 하면 된다. agent swarm은 작업 공간을 여러 컨텍스트 파일로 초기화하는 것이고, subagent는 컨텍스트 파일을 생성·삭제해서 시작·종료한다.

"less-is-more" 설계 원칙(각주 2): 심층 검색(deep research)에는 검색 도구가 필요하지만, 고정된 도구 인터페이스로 학습시키는 대신 검색 도구를 in-context skill로 노출한다. harness 수준에 가능한 한 적게 하드코딩해 도구를 추론 시점에 자유롭게 정의·추가·수정할 수 있게 하려는 것이다.

효율 지표 — prefix-reuse FLOPs (Eq. 3)

왜 문제인가: 서빙의 흔한 최적화인 prefix-cache 재사용은 일치하는 접두사의 캐시만 재사용하고, 첫 불일치 지점 이후의 토큰은 모두 재-prefill해야 한다. 중간 편집은 정확히 이 상황을 만든다. 컨텍스트 길이만 재면 편집의 비용을 과소평가한다.

해법: 궤적 전체의 이론적 추론 FLOPs를 다음처럼 센다(세부 계산은 부록 C, Eq. 7–9).

$$\text{FLOPs}_{\text{prefix-reuse}} = \underbrace{\text{FLOPs}_{\text{prefill}}\big(\text{unmatched context suffix}\big)}_{\text{tokens from the first prefix mismatch onward}} + \underbrace{\text{FLOPs}_{\text{decode}}\big(\text{generated tokens}\big)}_{\text{new output tokens}} \tag{3}$$
직관적으로 말하면: "이번 턴에 서버가 새로 계산해야 하는 것"만 센다. 앞부분이 지난번과 같으면 공짜, 첫 불일치부터 끝까지는 다시 읽어야 하고, 새로 쓰는 토큰은 decode 비용을 낸다. 컨텍스트를 짧게 만드는 편집도 "편집 지점 뒤를 다시 읽는 값"을 치러야 하므로, 정말 이득인지 이 지표로 판정한다.

원문은 논문 전체에서 표준 서빙 하의 prefix-reuse FLOPs를 보고하고, SCR로 인한 추가 절감은 §5.3에서 따로 보고한다. 이는 CLM에 불리한 쪽으로 보수적인 선택이다.

4.2 In-context 학습과 강화학습

컨텍스트 관리를 LM 네이티브 능력으로 만들었으므로, 더 나은 전략을 컨텍스트 안에서(in-context) 혹은 가중치 안에서(in-weight) 배울 수 있다.

Steering — 지시나 skill 문서로 조종

$s$를 in-context 지시나 skill 문서라 하면, CLM은 $s$를 추가 컨텍스트로 받아 조종된다.

$$c_{t+1} = f_\theta^{\text{CLM}}(c_t;\, s) \tag{4}$$
직관적으로 말하면: harness 코드를 고치는 대신 "16K 넘으면 4K로 줄여" 같은 한 문장을 덧붙이면 정책이 바뀐다. 컨텍스트 관리 규칙이 코드가 아니라 자연어 문서가 된다.

Evolving — 최적화 루프로 skill 진화

과제 인스턴스 $x$에 대해 Eq. 4가 유도하는 궤적을 $\tau(x;s)$, 궤적 단위 보상을 $R(\tau)$라 하면, 다른 모든 것을 고정한 채 다음을 최적화한다.

$$s^* = \arg\max_{s}\; \mathbb{E}_{x\sim\mathcal{D}}\big[R(\tau(x;s))\big] \tag{5}$$

구현은 프롬프트 진화 루프(GEPA, Agrawal et al., 2026)다: 매 라운드 에이전트가 train split에서 롤아웃을 만들고, proposer 모델이 그 궤적을 읽어 후보 skill을 생성하며, dev split에서 평가해 다음 라운드 skill을 고른다. 진화가 끝나면 선택된 skill을 held-out test split에서 한 번만 평가한다. optimizer는 더 강한 외부 모델(assisted evolution)이거나 agent 모델 자신(self-evolution)일 수 있다.

직관적으로 말하면: 가중치 대신 "컨텍스트 정리 요령서"를 경사 없이 진화시킨다. 선배(proposer)가 후배의 작업 로그를 보고 요령서를 고쳐 주고, 시험(dev)에 붙은 요령서만 살아남는다.

RL — stepwise GRPO와 success-gated efficiency advantage

왜 stepwise인가: 컨텍스트 편집은 턴마다 입력을 바꾼다. 그래서 프롬프트마다 완전한 에이전트 궤적을 그룹으로 샘플링하고, 궤적 단위 결과 보상으로 표준 GRPO advantage를 계산한 뒤, 그 advantage를 궤적을 이루는 모든 segment(모델 호출)에 할당한다. 모든 모델 호출이 전체 궤적의 결과로 학습되며, 컨텍스트 편집을 미분해 통과하지는 않는다(부록 A).

왜 효율 보상이 따로 필요한가: 결과 보상은 컨텍스트 편집에 대해 약한 지도 신호다 — 성공 궤적에도 비효율적 편집이, 실패 궤적에도 유용한 편집이 들어 있다. 그렇다고 편집 횟수나 제거한 컨텍스트 양을 보상하면, 모델이 중요한 정보를 버리거나 prefix 재사용을 해치는 불필요한 편집으로 reward hacking을 할 수 있다.

해법: 성공 궤적 중 prefix-reuse FLOPs가 낮은 것을 추가로 보상한다. $c_i$를 궤적 $\tau_i$의 prefix-reuse FLOPs, $\mathcal{G}_g^+$를 그룹 $g$의 성공 궤적 집합, $\bar{c}_g = \frac{1}{|\mathcal{G}_g^+|}\sum_{k\in\mathcal{G}_g^+} c_k$라 하면

$$A_i^{\text{eff}} = \begin{cases} \operatorname{clip}\!\left(\dfrac{\bar{c}_g - c_i}{\bar{c}_g},\, -1,\, 1\right), & i \in \mathcal{G}_g^+, \\ 0, & i \notin \mathcal{G}_g^+. \end{cases} \tag{6}$$

그룹의 성공 궤적이 2개 미만이면 모든 궤적의 $A_i^{\text{eff}} = 0$이다. 최종 advantage는 $A_i = A_i^{\text{out}} + w_{\text{eff}}\, A_i^{\text{eff}}$이며, 부록 E에서 $w_{\text{eff}} = 0.25$를 컨텍스트 관리 토큰에 적용하고, 실패한 tool 호출·잘못된 형식 출력에 대한 패널티를 함께 쓴다.

직관적으로 말하면: "정답을 맞힌 사람들끼리만" 계산 비용으로 순위를 다시 매긴다. 틀린 답은 아무리 싸게 틀려도 보너스가 없으니, 컨텍스트를 마구 지워 싸게 실패하는 꼼수가 막힌다. 그리고 효율 보너스 크기는 최대 0.25라서 "맞힘 vs 틀림"의 순서는 절대 뒤집히지 않는다.

4.3 (더) 효율적인 CLM 서빙 — Suffix Cache Reuse

왜 문제인가: CLM이 B를 B′로 바꾸면 표준 prefix-cache 재사용은 첫 불일치 뒤의 모든 토큰(B′와 C)을 재-prefill해야 한다. C는 내용이 바뀌지 않았는데도.

해법: SCR은 살아남은 모든 토큰(C 포함)의 캐시 상태를 재사용하고, 새로 삽입·추가된 토큰(B′)만 재-prefill한다. 살아남은 suffix C는 이전 prefix를 인코딩한 "낡은(stale)" 캐시 상태를 그대로 갖게 되는데, 원문은 이것이 과거의 더 풍부한 정보를 담고 있어 경우에 따라 오히려 이로울 수 있다고 본다(Memento가 비슷한 관찰을 보고, 부록 A).

구현 (부록 B):

  • Full attention 층: 새 프롬프트가 오면 세션의 이전 프롬프트와 diff해 살아남은 구간을 찾고, 그중 최대 $K$개를 큰 순서로 재배치한다(본문 $K = 6$). 각 구간의 K·V를 재사용하되 key의 RoPE를 새 위치로 재회전해 B′ 뒤에 이어 붙인다. 재배치된 항목은 세션 전용 캐시 슬롯에 두므로 공유 radix tree에는 옮겨진 항목이 절대 들어가지 않으며, 슬롯을 할당하지 못하면 표준 재-prefill로 fallback한다.
  • Linear attention 층(Gated DeltaNet 48층): 토큰 단위 캐시가 없으므로 편집 전 순환 상태를 스냅샷해 그 상태에서 이어 간다. 편집은 토큰 단위 컨텍스트를 가진 16개 full-attention 층에만 반영된다. 즉 B′는 선형층에서 재계산되지 않지만, full-attention 층의 표현은 다시 계산되어 이후 선형층 입력으로 간접 영향을 준다.
  • 여러 생존 구간: 재배치마다 편집 전 컨텍스트로 계산한 상태를 쓰므로 근사가 들어가고, 한 번에 많이 재배치하면 모델이 다음 턴에 적응하기 전에 근사가 누적될 수 있다. 그래서 편집당 재배치 구간을 $K$개(가장 긴 것부터)로 제한하고 나머지는 재-prefill한다 — 생존 구간이 많은 병리적 편집에 덜 취약해진다.
  • 각주 1 · reasoning token stripping: Qwen3.6-27B의 기본 chat template이나 stateless Chat Completions API로 서빙되는 GPT-5.6 Sol처럼, 이전 턴의 reasoning 토큰을 다음 턴 전에 제거하는 설정에서는 에이전트가 편집하지 않아도 뒤의 보존 구간이 재-prefill된다. SCR은 이 경우도 "또 하나의 편집"으로 보고 재사용한다.
직관적으로 말하면: 문서 중간 한 문단을 고쳤다고 그 뒤 50쪽을 다시 타이핑하지 말고, 뒤쪽은 복사해 붙이되 쪽 번호(RoPE 위치)만 새로 매기자는 것이다. 다만 뒤쪽 내용이 "옛 문단을 읽고 쓴 메모"를 품고 있다는 근사는 감수한다.

5.1.1 코딩과 심층 검색 (Q1)

왜 이 실험인가: 컨텍스트 관리가 정말 "모델의 행동"이라면, harness 코드나 파라미터를 건드리지 않고 지시 한 문장으로 바꿀 수 있어야 한다. 세 행동을 시험한다: 지정 길이에서 압축 시작, 의미적 하위 질문 경계에서 압축, 압축 전 컨텍스트 백업. 각 행동은 과제 프롬프트 뒤에 붙인 문장 하나로 유도하며, 같은 질문의 무지시 대조군과 비교한다(BCa — bias-corrected and accelerated — bootstrap 신뢰구간, paired).

  • 임계값: 48K 예산·200턴, 무지시 턴 수 60퍼센타일 이상인 긴 질문 30개. "컨텍스트가 Y 토큰을 넘으면 즉시 약 4,000토큰으로 압축하라"(Y ∈ {16K, 24K, 32K}). 첫 압축 시점의 컨텍스트 크기 중앙값을 보고.
  • 경계: 4개 질문을 이은 세션, 24K 예산·1,000턴, 조건당 189세션(131개가 세션 내 경계 포함). "하위 과제 경계에서만 압축하고, 끝난 하위 과제의 컨텍스트는 버려라." 경계 후 2턴 이내 압축률을 보고.

§6 논의와 향후 과제

모델이 편집 가능한 컨텍스트의 안전 함의: 라이브 컨텍스트 쓰기 권한은 더 유연한 즉석 관리를 가능하게 하지만 새 안전 문제도 만든다. 편집 가능한 컨텍스트는 prompt injection이나 자기 생성 지시가 턴을 넘어 지속되는 통로가 될 수 있다. 실제로 compaction 요약에서 모델이 승인되지 않은 지시를 자기 요약에 삽입해 이후 과제 행동에 영향을 준 사례가 보고되었다(OpenAI, 2026b). 편집 가능한 컨텍스트가 널리 쓰이면, 이 새로운 공격 표면을 규명하고 모델 제어 컨텍스트의 유연성을 유지하면서 무결성을 지키는 방어가 필요하다.

향후 방향 — CLM RL 확장과 harness 증류: CLM이 효과적인 관리 전략을 탐색·학습하도록 RL을 확장하고, 기존 harness의 전략을 CLM에 증류하는 harness-to-CLM 파이프라인을 만들 수 있다. 표준 LM은 입력 토큰을 다음 토큰 분포로 사상할 뿐이지만 harness는 컨텍스트를 어떻게 구성·갱신할지를 정한다. 많은 harness 연산이 컨텍스트 변환으로 표현될 수 있으므로, 이를 CLM 행동으로 번역하고 결국 가중치에 내재화할 수 있다. 이 관점에서 ##harness는 외부에서 개발된 뒤 CLM에 흡수될 수 있는 절차적 기억(procedural memory) 혹은 과제 특화 skill##이다.

부록 C — prefix-reuse FLOPs 계산

턴 $t$에서 프롬프트가 $P_t$ 토큰, 생성이 $G_t$ 토큰이고, 서버가 이전 턴 프롬프트에도 있던 선두 메시지들의 가장 긴 접두사 $R_t$ 토큰을 재사용하며, 나머지 $U_t = P_t - R_t$만 prefill한다고 하자. 표준 prefix caching에서 편집은 편집된 메시지 이후의 캐시를 무효화하고, 응답은 생성 시 decode되는 것과 별도로 나중 프롬프트에 처음 나타날 때 다시 prefill된다.

$L$층, hidden $d$, MLP 폭 $d_{\text{ff}}$ 모델에서 $L_{\text{attn}}$개 full-attention 층(query head $h_q$, output gate 포함, KV head $h_{kv}$, head 차원 $d_h$)과 $L_{\text{lin}}$개 Gated DeltaNet 층(key head $h_k$, value head $h_v$, 차원 $d_k$, $d_v$, value head당 스칼라 gate 2개)이 있다. 선형 연산의 토큰당 비용은 컨텍스트 길이와 무관하며, 곱-덧셈 하나를 2 FLOPs로 세면

$$C_{\text{token}} = \underbrace{6Ld\,d_{\text{ff}}}_{\text{MLP}} + \underbrace{L_{\text{attn}}\big[2d(2h_qd_h + 2h_{kv}d_h) + 2h_qd_hd\big]}_{\text{full-attention projections}} + \underbrace{L_{\text{lin}}\big[2d(2h_kd_k + 2h_vd_v + 2h_v) + 2h_vd_vd\big]}_{\text{Gated DeltaNet projections}} \tag{7}$$

길이 의존 비용은 full-attention 층에서만 생긴다. query–key 쌍마다 head 차원당 score 1회, 가중 value 1회의 곱-덧셈이므로

$$C_{\text{attn}} = 4L_{\text{attn}}h_qd_h \tag{8}$$

하위 경계 항을 무시하면 한 턴의 비용은

$$F_t = C_{\text{token}}\,(U_t + G_t) + C_{\text{attn}}\Big[\tfrac{1}{2}\big(P_t^2 - R_t^2\big) + G_tP_t + \tfrac{1}{2}G_t^2\Big] \tag{9}$$

괄호의 첫 항이 prefill 중 attention, 뒤 두 항이 decode 중 attention이다. 궤적 비용은 $\sum_{t=1}^{T} F_t$이며, embedding·출력층, Gated DeltaNet 순환 상태 갱신, 정규화·활성화·softmax는 생략한다.

직관적으로 말하면: 비용 = (새로 처리하는 토큰 수 × 토큰당 고정비) + (새 토큰이 앞의 모든 토큰을 쳐다보는 비용). 앞부분 $R_t$가 캐시되면 두 항 모두에서 그만큼이 빠진다.

Qwen3.6-27B 대입: $L = 64$, $d = 5120$, $d_{\text{ff}} = 17{,}408$; full-attention 16층은 $h_q = 24$, $h_{kv} = 4$, $d_h = 256$; Gated DeltaNet 48층은 $h_k = 16$, $h_v = 48$, $d_k = d_v = 128$. 그러면 $C_{\text{token}} = 48.70 \times 10^9$ FLOPs/토큰(MLP $34.23\times10^9$, full-attention 투영 $3.36\times10^9$, Gated DeltaNet 투영 $11.12\times10^9$), $C_{\text{attn}} = 3.93 \times 10^5$ FLOPs/쌍이다. 검산: MLP $= 6 \cdot 64 \cdot 5120 \cdot 17408 = 3.42\times10^{10}$, $C_{\text{attn}} = 4\cdot16\cdot24\cdot256 = 393{,}216$.

부록 G — 기존 LM의 컨텍스트 길이 인식

왜 이 분석인가: CLM에게 중요한 능력은 컨텍스트 길이 인식 — 예산을 얼마나 썼는지 추정하고 언제 편집·offload할지 판단하는 능력 — 이다. 이 인식이 없으면 외부 시스템 개입에 자주 의존하게 되고, 편집 후 미래 턴에 낡거나 중복된 정보가 남을 수 있다.

진단: 길이가 다른 프롬프트 50개를 주고 현재 컨텍스트의 토큰 수를 추정하게 한 뒤, provider가 보고한 실제 길이와 비교한다. 힌트 없음, 혹은 입력의 25/50/75% 지점에 토큰 수 앵커를 준 조건을 비교한다.

오차는 평균 절대 오차(MAE, mean absolute error, 토큰 단위)로 잰다.

결과: 긴 컨텍스트에서 모델들은 6.2K, 9.8K, 10.4K 같은 반복되는 버킷 값을 예측하는 경향이 있다(저자들은 사전학습·사후학습에서 본 토큰 계산 패턴의 반영이라고 추측). Claude 4.6 Sonnet은 과소추정 경향이 있고 GPT-5.4가 세 모델 중 가장 잘 맞는다. 토큰 수 힌트는 추정을 개선하며, 추정 지점에 가까운 힌트일수록 효과가 크다. 따라서 기존 LM은 긴 컨텍스트에서 길이 인식이 제한적이고 환경 힌트가 크게 도움이 된다 — 이것이 §5.1에서 CLM에 "예산 2,048토큰 전 리마인더"를 준 이유이며, 향후 CLM 학습이 이런 신호를 포함할 수 있다.

비판적 분석 (Critical Analysis)

강점

  • 개념의 단순함과 범용성: "컨텍스트를 파일로 노출"이라는 최소 구현으로 단일 에이전트, subagent, swarm, 서로 다른 모델 패밀리(Qwen, Claude, GPT)를 모두 다룬다. 새 tool을 설계하지 않고도 기존 tool 기반 방법을 특수형으로 포함한다(Eq. 2).
  • 비용을 정직하게 센다: 편집이 prefix cache를 깨는 문제를 숨기지 않고 prefix-reuse FLOPs로 계산하며, 본문 수치는 SCR 이득을 뺀 보수적 값이다. 부록 C의 산식이 완전히 공개되어 재현 가능하다(이 문서의 수치 예제로 원문 1.41/5.74/10.81×10¹⁴을 그대로 재현).
  • 진단 벤치마크의 설계 품질: ContextBench는 추론을 배제하고, 예산 규칙으로 풀 수 있음을 보장하고, 방법별 skill을 동일 상세도로 제공해 "도구 사용법을 몰라서"라는 교란을 줄였다.
  • 학습 경로를 둘 다 보인다: in-context(지시·진화)와 in-weight(RL) 모두에서 개선을 보였고, 효율 보상을 "성공 내 재정렬"로 설계해 reward hacking 경로를 구조적으로 차단했다.
  • 서빙 공동 설계: SCR이 CLM뿐 아니라 reasoning token stripping이라는 일반 서빙 문제에도 이득(5.3pt / 7.8pt)을 준다는 분해는 실무적으로 가치가 크다.

한계와 의문점

  • 반복 수와 통계: 수학 최적화는 방법당 1 run, Software World는 단일 swarm run, BCP·TB2.1 주 결과에도 seed 반복이나 신뢰구간이 없다. Heilbronn +16.8%를 제외하면 수학 문제의 차이는 1% 미만이고 swarm의 개선폭도 4.4% vs 2.6%라, "65% greater"는 작은 절대값의 비율이다.
  • 작은 모델에서의 역전이 본문에서 약하게 서술됨: 부록 Figure 17을 읽으면 9B에서는 BCP의 Self-Compact, TBLite의 Summary가 CLM보다 높다(벡터 역산 기준). 본문은 9B BCP에서 CLM이 Summary보다 높다는 점만 언급한다. CLM의 zero-shot 우위는 27B급 이상의 강한 모델에 의존한다.
  • RL 곡선과 서술의 불일치: Figure 21에서 Summary harness에 FLOPs 보상을 건 run은 step 40에 정확도 ≈1%로 붕괴한 것으로 보이지만, 본문은 "어느 쪽도 뚜렷한 정확도 손실 없이"라고 쓴다. 또 Figure 21의 step 0 값이 Table 2의 학습 전 값과 1–2pt 다르다. RL은 9B 하나, 70 step, 단일 run이다.
  • baseline 공정성의 미묘한 지점: BCP에서 CLM의 편집 턴은 100턴 제한에 세지 않고, 예산 초과 시 롤백·재시도(최대 6회)가 허용된다. 다른 방법에 같은 재시도가 있는지는 명시되지 않았다. 또 CLM만 "예산 2,048 전 리마인더"를 받는다. 비용(FLOPs)에는 편집 턴이 포함되지만 턴 예산에서는 유리하다.
  • 이론 FLOPs ≠ 실제 지연: prefix-reuse FLOPs는 이론값이며 wall-clock, 메모리, 배치 효율, 도구 실행 시간을 반영하지 않는다. SCR의 35%도 "서버 측 계산" 기준이다. 12시간 EdgeBench처럼 시간 예산이 고정된 과제에서는 FLOPs 절감이 성능으로 어떻게 전환되는지 분리되지 않는다.
  • SCR의 근사: 살아남은 구간이 낡은 상태를 쓰는 근사가 정확도를 해치지 않는다는 근거는 830문항 BCP 한 벤치마크와 64문항 K 실험뿐이다. 코딩처럼 편집 전후 의미가 크게 달라지는 과제에서의 검증이 없다.
  • 안전성: 저자들도 인정하듯, 모델이 자기 컨텍스트를 쓸 수 있으면 prompt injection과 자기 생성 지시가 지속되는 통로가 된다. 편집 이력의 감사(audit) 수단(예: §5.2의 백업 지시)이 기본 설계에 포함되지 않았다.
  • 정성 사례의 대표성: Figure 3의 창발 행동이 얼마나 자주 나타나는지, 실패한 편집(중요 정보 삭제)이 얼마나 되는지의 통계가 없다.
  • 재현성의 시점 의존: Claude Fable 5.1, Opus 5, GPT-5.6-Sol 등 API 모델에 의존하는 실험(수학, swarm, 진화)은 모델 버전이 바뀌면 재현이 어렵다.

Key Takeaways — 이 논문에서 가져갈 것

  1. 컨텍스트 관리를 tool이 아니라 "편집 가능한 파일"로 노출하라: 구현 비용이 매우 낮고(경로 하나 + 자동 동기화), 강한 모델(≈27B 이상)에서는 사람이 설계한 compaction보다 정확하고 싸다. 기존 에이전트 프레임워크에 바로 시험해 볼 수 있는 설계다.
  2. 편집 기반 방법은 반드시 prefix-reuse FLOPs로 평가하라: 컨텍스트 길이만 보면 편집의 재-prefill 비용을 놓친다. hybrid 모델에서는 비용이 대부분 "새로 처리하는 토큰 수"로 결정되므로, 편집 위치와 빈도가 핵심 변수다(부록 C).
  3. 효율 보상은 "성공한 것들끼리만" 비교하라: Eq. 6의 success-gated 설계는 길이·비용 보상을 거는 모든 에이전트 RL에 재사용할 만한 패턴이다 — 실패에 효율 보너스를 주지 않고, clip과 작은 가중치로 정답 순서를 보존한다.
  4. Suffix 캐시 재사용은 CLM 밖에서도 이득이다: reasoning token stripping만으로도 재사용분의 2/3가 나온다. reasoning 모델 서빙 인프라라면 SCR류 최적화와, hybrid 모델의 순환 상태를 메시지 경계마다 저장하는 개선이 즉시 쓸모 있다.
  5. 컨텍스트 관리 정책은 문서로 진화시킬 수 있다: 한 문장 지시로 압축 시점·경계·백업 정책이 바뀌고, GEPA식 진화로 held-out +35.9pt를 얻었다. harness 코드를 고치기 전에 skill 문서부터 최적화해 볼 가치가 있다.
  6. (비판적 관점) "모델에게 전권"의 이득은 모델 능력에 묶여 있다: 9B에서는 zero-shot CLM이 단순 baseline에 지고, 길이 인식(MAE 수천 토큰)도 약하다. 주 결과의 반복 수가 적고 일부 그림과 본문 서술이 어긋나므로, 작은 모델·비용 민감 환경에서는 RL 내재화나 리마인더 같은 보조 장치 없이 그대로 쓰면 오히려 손해일 수 있다.
