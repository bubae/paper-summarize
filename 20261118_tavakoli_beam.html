목차

TL;DR

  • 문제: LLM(Large Language Model)의 컨텍스트 창은 1M 토큰까지 커졌지만, "긴 대화를 기억하는 능력"을 재는 벤치마크는 (1) 서로 다른 사용자의 짧은 세션을 이어 붙여 서사가 끊기고, (2) 개인 생활 위주의 좁은 도메인에 머물며, (3) 단순 사실 회상(recall)만 묻는다. 그래서 "1M 창이 있으면 기억도 해결된 것인가"라는 질문에 답하지 못한다.
  • 해결: 두 가지를 제안한다. ① BEAM — 대화 계획(plan)을 먼저 세우고 그것을 사용자 발화 → 어시스턴트 발화로 펼쳐, 한 사용자와의 하나로 이어진 대화를 128K·500K·1M·10M 토큰까지 자동 생성하는 프레임워크와, 그로 만든 100개 대화·2,000개 사람 검증 질문(10개 기억 능력, 그중 Contradiction Resolution·Event Ordering·Instruction Following은 새로 도입). ② LIGHT — 인지과학에서 빌린 세 메모리(검색용 episodic memory, 최근 대화 working memory, 매 턴 핵심을 적어 두는 scratchpad)를 LLM에 붙이는 추론 시점 프레임워크.
  • 왜 작동하는가: 긴 대화에서 답의 근거는 대부분 앞쪽에 흩어져 있고(부록 B.5), 1M 창 모델도 그 거리를 제대로 활용하지 못한다. LIGHT는 원문 턴을 검색으로 끌어오고(정확한 원문), 흩어진 사실·지시·갱신·날짜를 scratchpad에 미리 정규화해 두며(요약된 상태), 질문에 무관한 노트는 걸러내어 작은 창(Qwen 32K)에서도 필요한 재료만 읽게 한다.
  • 비유: 몇 달치 상담 기록을 통째로 외우려는 상담사(long-context LLM)는 기록이 길어질수록 헷갈린다. LIGHT 상담사는 서랍 속 일지를 색인 카드로 찾아보고(episodic), 방금 나눈 몇 마디는 책상 위에 펼쳐 두며(working memory), 상담 때마다 "예산 ＄60K로 변경", "항상 팀원 수를 알려 달라" 같은 핵심을 수첩에 적어 둔다(scratchpad). BEAM은 이런 상담사를 시험하기 위해 줄거리가 있는 몇 달치 상담 기록과 시험 문제를 자동으로 만들어 주는 출제 기계다.

핵심 기여 (Key Contributions)

  1. 계획 기반 장기 대화 생성 프레임워크: seed(도메인·제목·테마·subtopic) → 서사 15–20개 → 사용자 프로필(MBTI(Myers–Briggs Type Indicator) 6유형 합성, 8,008개 고유 프로필 가능)·관계 그래프·타임라인 → sub-plan으로 분해된 대화 계획 → 사용자 질문 → 질문 감지·follow-up 감지 모듈이 있는 어시스턴트 응답 생성. 10M 대화는 Sequential Expansion / Hierarchical Decomposition으로 10개의 맞물린 계획을 만든다 (§2.2).
  2. BEAM 벤치마크: 19개 도메인, 100개 대화(128K–10M 토큰), 2,000개 사람 검증 probing 질문, 10개 기억 능력(Contradiction Resolution·Event Ordering·Instruction Following 신규). 평가는 nugget 기반 LLM 채점(0/0.5/1)과 Event Ordering용 Kendall τb (§2.3–2.4, 부록 B·D).
  3. LIGHT 메모리 프레임워크: $y = \pi(x, E, W, S_x)$ — episodic retrieval $E$, working memory $W$, 질문으로 필터링된 scratchpad $S_x$를 결합. 백본 무관(오픈소스·상용 모두)이며 학습이 필요 없다 (§3).
  4. 대규모 실증: 4개 백본(Qwen2.5-32B-AWQ, Llama-4-Maverick, Gemini-2.0-Flash, GPT-4.1-nano) × {long-context, RAG(Retrieval-Augmented Generation), LIGHT} × 4개 길이. 1M 창 모델도 대화가 길어질수록 붕괴하며, LIGHT는 16개 (백본, 길이) 조합 중 15개에서 최고 평균. ablation·검색 예산·retriever·임베딩·인덱스·ReadAgent 비교까지 (§4, 부록 C).

배경 (Background)

"긴 컨텍스트"와 "장기 기억"은 같은 문제가 아니다

LLM의 컨텍스트 창은 GPT-2/3 시절 512–2K 토큰에서 Claude-3·GPT-4-Turbo·Gemini 2.0·GPT-4.1의 128K–1M 토큰, Llama 4 Scout의 10M 토큰까지 커졌다(§5, 부록 A). 이 성장은 효율적 attention(Longformer·BigBird 같은 sparse attention, Linformer·Performer 같은 선형 근사, FlashAttention 같은 메모리 효율 커널), 위치 인코딩 개선(Transformer-XL의 상대 위치, RoPE(Rotary Position Embedding)와 YaRN·NTK 스케일링, ALiBi), 장문 학습 전략(LLaMA-2-Long, LongRoPE의 continued pre-training·curriculum), 추론 최적화(PagedAttention, H2O·SnapKV 같은 KV-cache 압축, Ring Attention)가 함께 만든 결과다.

그러나 "창에 넣을 수 있다"와 "넣은 것을 쓸 수 있다"는 다르다. 대화 메모리는 단순히 긴 문서를 읽는 것과 달리 ① 같은 사용자가 시간에 따라 사실을 바꾸고(예산 ＄50K → ＄60K), ② 서로 모순되는 말을 하며, ③ "앞으로 항상 X 해 달라" 같은 지속되는 지시를 남기고, ④ 사건의 순서와 날짜 간격이 의미를 갖는다. 이런 능력은 "바늘 찾기(needle-in-a-haystack)"식 회상만으로는 측정되지 않는다.

직관적으로 말하면: 긴 컨텍스트는 "책상이 넓어진 것"이고, 장기 기억은 "그 책상 위 서류 중 지금 유효한 것이 무엇인지 아는 것"이다. 책상이 넓을수록 오히려 낡은 서류와 새 서류가 섞여 헷갈릴 수 있다.

기존 장기 대화 메모리 벤치마크와 그 한계

원문 부록 A와 Table 2가 정리하는 기존 벤치마크는 다음과 같다.

  • MSC(Multi-Session Chat, Xu et al., 2021)·DuLeMon(Xu et al., 2022): 사람–사람 다중 세션 잡담. 세션 경계를 넘는 기억을 보지만 세션이 짧고(∼1K) 의존 관계가 얕다. DuLeMon은 대화 수준 기억과 망각 곡선에 초점.
  • MemoryBank(Zhong et al., 2024): 300세션, 194개 질문으로 회상과 시간 추론을 본다.
  • PerLTQA(Du et al., 2024): 개인 장기 기억의 분류·검색.
  • LoCoMo(Maharana et al., 2024): 50개 대화, 평균 약 9K 토큰·35세션. 단일·다중 hop, 시간, 적대적(답 없음) 질문과 사건 요약을 포함.
  • DialSim(Kim et al., 2024a): TV 대본 기반 다자 대화로 350K 토큰까지 늘리지만 주제 다양성이 낮다.
  • LongMemEval(Wu et al., 2024): 500개 질문으로 정보 추출·다중 세션 추론·시간 추론·지식 갱신·abstention을 본다. 115K와 1M 두 설정(세션들을 이어 붙여 길이 확보).
  • MemBench(Tan et al., 2025): LLM 에이전트 메모리를 정보 추출·multi-hop·지식 갱신·선호 따르기·시간 추론으로 평가.
  • MemoryCode(Rakotonirina et al., 2025): 템플릿 기반 지시 seed로 다중 세션 대화를 만들지만 단일 도메인.

왜 문제인가: 원문(§1)은 세 가지를 지적한다. 첫째, 대부분 다른 사용자의 짧은 세션을 이어 붙여 길이를 늘리므로 주제가 갑자기 바뀌고, 각 구간이 쉽게 분리되어 진짜 장거리 추론이 필요 없어진다. 둘째, 도메인이 개인 생활에 치우쳐 코딩·수학·법률·재무 같은 실제 사용 영역이 빠진다. 셋째, 단순 회상 위주라 모순 해결, 변화하는 정보 인식, 지시 따르기를 재지 않는다.

기존 메모리 향상 방법: long-context, RAG, 그리고 메모리 에이전트

긴 이력을 다루는 방법은 크게 세 갈래다(부록 A). ① 아키텍처 수정: Transformer-XL의 segment 재귀, Compressive Transformer의 오래된 상태 압축, RWKV·Mamba·Hyena 같은 state-space 모델(선형 비용, 이론상 무한 기억), Memformer·RETRO·RMT 같은 외부 메모리 슬롯, AutoCompressor 같은 학습된 컨텍스트 압축. ② RAG(Retrieval-Augmented Generation): REALM과 RAG가 dense retrieval을 개척했고, RETRO는 검색을 Transformer 안에 넣었으며, HippoRAG는 지식 그래프를 붙였다. 대화에 적용하면 "각 턴을 문서로 색인 → 질문과 비슷한 턴 top-k를 검색 → LLM에 넣기"가 된다. ③ 메모리 에이전트: 원문이 부록 C.5에서 비교하는 ReadAgent(Lee et al., 2024)는 긴 텍스트를 페이지로 나눠 각 페이지의 요지(gist)만 기억하고, 필요할 때 원 페이지를 다시 펼쳐 보는 방식이다.

각 방법의 한계: long-context는 창 안에 넣어도 중간·먼 위치의 정보를 잘 못 쓰고 비용이 길이에 비례한다. RAG는 유사도 기반이라 시간 순서를 잃고(같은 항목의 옛 값과 새 값이 순서 없이 섞임), 질문과 표면적으로 닮지 않은 지시·선호를 놓친다. 요지 기반 에이전트는 세부 수치를 잃는다. LIGHT는 이 셋을 "검색(정확한 원문) + 최근 창(순서) + 정규화된 노트(갱신·지시·날짜)"로 섞는 절충안이다(§3).

이 저장소의 관련 요약(원문 미인용, 이 저장소의 관련 요약): MemFold는 긴 대화 이력을 질의 맞춤 텍스트 메모리로 쓴 뒤 256개 soft 벡터로 접어 개인화에 쓰고 LoCoMo·LongMemEval로 전이를 평가한다 — LIGHT의 scratchpad가 "학습 없는 텍스트 메모리"라면 MemFold는 그것을 학습된 압축으로 대체하는 방향이다. Context Language Models는 컨텍스트 관리(압축·offload)를 고정 규칙이 아닌 모델의 행동으로 만든다 — LIGHT의 "30K 넘으면 15K로 요약" 같은 고정 규칙이 정확히 그 비판 대상이다. MSA는 100M 토큰 메모리를 end-to-end 학습 가능한 sparse attention으로 다뤄, BEAM 같은 10M급 벤치마크가 필요한 모델 측 시도에 해당한다.

평가 도구: nugget 평가와 Kendall τb

Nugget 평가는 TREC 정보검색 평가 전통에서 온 방법으로(원문은 Pradeep et al., 2024; 2025를 인용), 이상적 답변을 "원자적이고 자기완결적인 정보 단위(nugget)"로 쪼갠 뒤 시스템 응답이 각 nugget을 충족하는지 판정한다. 긴 서술형 답(요약 등)을 정답 문자열 일치로 채점할 수 없기 때문에 쓰인다. 원문은 nugget마다 LLM 판정자가 0(불충족)/0.5(부분)/1(충족)을 주고 이를 평균한다(§2.4).

Kendall τb(Kendall, 1945)는 두 순위 사이의 순서 일치도를 재는 상관계수로, 동순위(tie)를 보정한 변형이다. 모든 쌍 중 순서가 같은 쌍(concordant) $n_c$와 반대인 쌍(discordant) $n_d$를 세어

$$\tau_b = \frac{n_c - n_d}{\sqrt{(n_0 - n_1)(n_0 - n_2)}},\quad n_0 = \tfrac{n(n-1)}{2}$$

로 정의된다($n_1, n_2$는 각 순위 안의 동순위 쌍 수). −1(완전 역순)~+1(완전 일치) 범위다. 이 식은 원문에 명시되지 않은 표준 정의이며, 원문은 "순서와 존재(presence)를 함께 반영한다"고만 서술한다.

직관적으로 말하면: nugget 평가는 "정답 체크리스트 몇 칸을 채웠나", Kendall τb는 "줄 세운 순서가 얼마나 맞나"를 잰다. Event Ordering만 후자를 쓰는 이유는 사건을 다 맞혀도 순서가 틀리면 틀린 답이기 때문이다.

1. 서론 — 왜 새 벤치마크와 새 메모리가 필요한가 (§1)

LLM은 오픈 도메인 대화 에이전트, RAG 기반 질의응답·팩트체킹, 긴 문서·코드 분석, 과학·법률 연구 등에 쓰이며, 이 중 다수가 긴 입력을 요구해 Gemini처럼 1M 토큰 창을 가진 모델이 등장했다. 특히 대화 시스템은 사용자가 여러 세션에 걸쳐 장기적으로 상호작용하므로 긴 이력에 대한 일관된 기억이 필수다.

원문은 기존 벤치마크의 한계(배경 절 참조)를 짚은 뒤 다음을 제시한다: (a) 사용자–어시스턴트 간 일관된 긴 대화를 10M 토큰까지 다양한 도메인에서 자동 생성하는 프레임워크 — 고수준 대화 계획(특정 도메인의 서사 + 생성된 속성을 가진 가상 사용자)을 세우고, 이를 재귀적으로 sub-plan으로 분해하고, 시간순 사용자 턴을 만든 뒤 어시스턴트 응답으로 확장하며, 사실감을 위해 양쪽의 follow-up·명확화 질문을 주입한다. (b) 10개 기억 차원을 겨냥하고 복잡한 multi-hop 추론에 초점을 둔 probing 질문을 자동 생성하고 사람이 검증한다. (c) 이렇게 만든 ##BEAM: 100K–10M 토큰의 다양한 대화 100개와 probing 질문 2,000개##. (d) 인지과학에서 영감을 얻은 LIGHT — episodic memory, working memory, scratchpad의 세 상보적 메모리.

결과 요약으로, 긴 창을 가진 LLM도 대화가 길어질수록 성능이 크게 떨어지고, LIGHT는 백본과 길이에 따라 최강 베이스라인 대비 평균 3.5%–12.69% 개선한다고 밝힌다. 코드·데이터·평가 스크립트는 공개되었다.

2. BEAM: 장기 기억 벤치마크 만들기 (§2)

2.1 문제 정식화

대화 모음 $\mathcal{D} = \{\mathcal{T}_i\}_{i=1}^{|\mathcal{D}|}$에서 각 대화는 발화(턴)의 열 $\mathcal{T} = \{t_i\}_{i=1}^{|\mathcal{T}|}$이다. 평가할 기억 능력 집합 $\mathcal{M}$의 각 능력 $m$마다 probing 데이터셋 $\mathcal{Q}_m = \{(x_i, y_i)\}_{i=1}^{N}$을 만든다($x_i$: 질문, $y_i$: 정답 집합). 질문은 대화의 $(|\mathcal{T}|+1)$번째 턴으로 덧붙여지고, 시스템은 $\hat{y} = \pi(x; \mathcal{T})$를 생성하며, 능력별 채점 함수 $\mu_m$이 점수 $s = \mu_m(x, y, \hat{y})$를 낸다.

직관적으로 말하면: 몇 달치 대화를 다 나눈 뒤 "그런데 내가 처음에 예산을 얼마라고 했지?"를 마지막 턴으로 던지고, 능력마다 다른 채점표로 답을 매긴다. $\mu_m$이 능력별로 다르다는 점(Event Ordering만 Kendall τb)이 §2.4의 설계로 이어진다.

2.2 열 가지 기억 능력과 생성 파이프라인 개요

BEAM은 10개 능력을 잰다 — 7개는 선행 벤치마크에서, 3개(Instruction Following, Event Ordering, Contradiction Resolution)는 새로 도입했다.

  • Abstention: 근거가 없으면 답을 보류하는가.
  • Contradiction Resolution (CR): 멀리 떨어진 턴들의 모순된 진술을 감지하고 조정하는가(전역 일관성).
  • Event Ordering (EO): 대화에서 변해 가는 정보의 순서를 인식·재구성하는가.
  • Information Extraction (IE): 긴 이력에서 엔티티와 사실 세부를 회상하는가.
  • Instruction Following (IF): 사용자가 지정한 제약을 긴 맥락 내내 지키는가.
  • Information (Knowledge) Update (KU): 새 사실이 나오면 저장된 사실을 고치는가. (원문은 본문에서 "Information Update", 표에서 "Knowledge Update"로 혼용한다.)
  • Multi-hop Reasoning (MR): 인접하지 않은 여러 구간의 근거를 통합하는가.
  • Preference Following (PF): 변해 가는 선호에 맞춰 개인화된 응답을 하는가.
  • Summarization (SUM): 대화 내용을 추상화·압축하는가.
  • Temporal Reasoning (TR): 명시적·암묵적 시간 관계를 추론하는가.

파이프라인 개요: 벤치마크는 ① 사용자–어시스턴트 대화, ② 핵심 능력을 겨냥한 probing 질문, ③ 응답 평가 방법론의 세 요소로 이뤄진다. 먼저 구조화된 대화 계획이 상호작용의 흐름을 정하고, 계획에 따라 사용자·어시스턴트 턴을 만든다. 현실 대화에는 "질문 → 답" 외에도 명확화·심화 follow-up이 있으므로 두 상호작용 제어 모듈을 둔다 — 질문 감지 모듈은 어시스턴트 응답에 사용자의 답이 필요한 반문이 있는지 판단해 있으면 사용자 응답을 생성하고, follow-up 감지 모듈은 사용자가 자연스럽게 되물을 시점을 판단해 추가 질문을 만든다. 대화가 완성되면 능력별 probing 질문 후보를 자동 생성하고, 사람이 유효한 것을 골라 평가 rubric을 작성한다.

2.2.1 대화 계획 생성 (§2.2.1, 부록 B.3.2)

왜 계획이 필요한가: LLM에게 "1M 토큰짜리 대화를 써라"라고 하면 같은 내용을 반복하거나 줄거리가 사라진다. 기존 벤치마크가 세션을 이어 붙인 것도 이 때문이다. BEAM은 대화의 뼈대(scaffold)인 대화 계획을 먼저 만들어 시간순으로 전개되는 일관된 줄거리를 강제한다.

Seed와 부가 정보: 계획은 다음을 조건으로 LLM이 생성한다.

  • seed: 도메인(예: 스포츠·재무·프로그래밍·수학), 제목(고수준 주제), 테마(제목의 구체화), subtopic 목록(세부 주제 다양성 확보). 사람이 목표 도메인을 지정하면 GPT-4.1이 후보 제목·테마·subtopic을 만들고(Listing 22), 사람이 비슷한 제목을 지우고 다양한 것을 골라 정제한다.
  • 서사 집합(narratives): 대화에서 변해 가는 측면(예: 경력 발전, 목표, 관계)과 그 범위·궤적 설명. 대화마다 15–20개를 비용 절감을 위해 오픈소스 LLaMA-3.3 70B로 생성(Listing 23).
  • 사용자 프로필: 이름·나이·성별·지역·직업·성격. 성격은 중복을 피하려 MBTI(Myers–Briggs Type Indicator) 6개 유형을 무작위로 골라 설명을 주고 LLM이 복합 성격을 합성하게 하여 ##8,008개의 고유 프로필##을 만들 수 있다. (16개 유형에서 6개를 고르는 조합 수 $\binom{16}{6} = 8{,}008$과 정확히 일치한다 — 요약자 확인.)
  • 관계 그래프: 사용자를 가족(부모·배우자·자녀)·친구·지인과 연결하되 그럴듯한 나이 차 같은 제약으로 사실성 유지.
  • 타임라인: 대화가 걸치는 시간 범위(시작·끝).

계획의 구조: 대화 계획은 $N$개의 sub-plan(대화의 서로 다른 단계)으로 이뤄지고, 각 sub-plan은 $M$개의 bullet을 가진다. 각 bullet은 하나의 서사와 "그 서사가 줄거리에서 어떻게 전개되는지"의 서술로 정의되며, sub-plan마다 구체적 날짜·기간인 시간 앵커가 붙는다. 128K·500K·1M 대화는 계획 하나를 생성한다(Algorithm 1 line 4, Listing 24; 코딩·수학은 Listing 25·26). sub-plan 수는 도메인과 목표 길이에 따라 달라지는데, 예컨대 코딩 도메인은 같은 토큰 예산을 채우는 데 더 적은 턴이 필요하다(코드 블록이 길기 때문으로 보인다 — 요약자 추정).

10M 대화: 10개의 맞물린 계획: 계획 하나로는 10M의 범위와 연속성을 담을 수 없어, 메인 seed에서 10개의 seed를 파생하고 계획을 10개 만든다. 두 전략이 있다.

  • Sequential Expansion: 메인 seed가 연대기의 첫 지점이 되고, 나머지 seed는 사용자의 "인생 다음 단계"를 나타낸다(예: 해외여행 → 귀국 후 구직 → 이후 이정표). Listing 28로 메인 seed·프로필·타임라인에서 시간 정렬된 seed열을 만들고, 각 계획은 직전 계획에 조건화되어 순차 생성된다(Algorithm 1 line 12, Listing 30).
  • Hierarchical Decomposition: 메인 seed를 시간·주제 구간 10개로 분해한다(예: 해외여행이면 앞 3개는 준비(예약·서류), 다음 5개는 여행 중 사건, 마지막 2개는 귀국 후 회고). Listing 29로 생성.

2.2.3 어시스턴트 발화 생성 (§2.2.3, 부록 B.3.4·B.3.5)

왜 role-play인가: 실제 대화는 사용자 질문 → 어시스턴트 답으로 끝나지 않는다. 어시스턴트가 "예산이 얼마인가요?"라고 되묻거나, 사용자가 "테스트 단계도 넣을 수 있을까요?"라고 덧붙인다. 이런 양방향성이 없으면 대화가 일방적 Q&A 목록이 되어 기억 부담이 비현실적으로 단순해진다.

해법: 한 LLM은 어시스턴트, 다른 LLM은 사용자 역할을 맡는 반복적 role-play다. sub-plan마다 어시스턴트 LLM은 seed, 앞선 sub-plan들, 최근 $M$턴의 요약, 그 이전 턴들의 압축 요약(Listing 37)에 조건화되며, 10M 대화에서는 이전 계획들의 요약도 추가된다.

  1. 어시스턴트가 최신 사용자 질문에 답한다(Algorithm 3 line 9).
  2. 질문 감지 모듈 $\phi$(Listing 35, 응답을 입력받아 yes/no)가 반문 여부를 판정한다(line 11). 있으면 사용자 LLM이 현재·이전 sub-plan, 관련 이력, 요약을 바탕으로 줄거리에 맞는 답을 생성하고(Listing 38, line 14), 어시스턴트가 다시 답한다. 반문이 없거나 임계값 $\delta_1 = 2$에 도달할 때까지 반복한다. 원문은 $\delta_1 \in \{2, 3, 5\}$를 시험해 가장 사실적인 대화를 만든 2를 택했다.

2.3 Probing 질문 생성 (§2.3)

설계 원칙: 자동 합성 + 사람 검증. probing 질문은 대화 계획과 대화 본문 양쪽에서 파생되어 ① 특정 능력을 겨냥하고, ② 대화 턴에 근거하며, ③ 명시적 provenance(출처 턴 id)를 갖도록 한다.

  1. 후보 bullet 선택: 계획을 GPT-4.1-mini에 넘겨 능력별로 적합한 bullet을 고른다(프롬프트 1–9, 능력당 하나). 예컨대 Knowledge Update는 "초기 사실"과 "나중 수정" bullet의 쌍이, Summarization·Event Ordering은 여러 bullet이 필요하다. 각 bullet은 사용자·어시스턴트 턴 생성 때 부여된 인덱스로 실제 대화 구간에 연결된다. Abstention은 후보 선택 없이 계획에서 직접 만든다(Listing 14).
  2. 질문 합성: 선택된 bullet과 정렬된 대화 조각으로 GPT-4.1-mini가 질문, 후보 답, 답을 담은 메시지의 source id를 생성한다(프롬프트 10–19). 10M 대화는 10개 계획에 sliding window를 적용해 한 번에 몇 개만 처리해 주제 국소성과 확장성을 유지한다.
  3. 사람 검증: 평가자가 대화와 일치하는 유효한 후보를 고르고, 무효·근거 없는 질문은 폐기하며 사소한 불일치는 수정한다.

2.4 평가: nugget 채점과 Kendall τb (§2.4, 부록 D)

각 질문은 사람이 검증하며(무효·근거 없는 질문 폐기, 경미한 불일치 수정), 검증된 집합에서 대화마다 능력당 2문항을 골라 대화당 20문항을 만든다. 그 뒤 각 질문에 대해 rubric nugget을 만든다 — nugget은 시스템 응답이 만족해야 하는 원자적·자기완결적 기준이며, 주석자가 이상 답변을 최소 의미 단위로 분해한다.

채점: LLM 판정자(Listing 20)가 응답을 nugget별로 0(불충족)·0.5(부분 충족)·1(완전 충족)로 채점하고, nugget 점수를 평균해 능력 수준 지표를 만든다. 판정 프롬프트는 의미 기준 판단(동의어·바꿔 말하기 허용, 대소문자·구두점 무시, "＄68,000"="68k"처럼 수치 동치 정규화)과 스타일 중립(어조·길이·hedging은 rubric이 형식을 명시하지 않는 한 감점하지 않음)을 지시하고, 복합 rubric은 "전부 = 1.0, 일부 = 0.5, 없음 = 0.0"으로, 부정형 제약은 "금지 요소 부재 + 응답성"으로 판정한다. 출력은 score와 reason의 JSON이다.

$$\text{score}(x) = \frac{1}{|\mathcal{N}_x|}\sum_{n \in \mathcal{N}_x} J(\hat{y}, n),\quad J \in \{0, 0.5, 1\}$$

(이 식은 원문 서술 "Scores are averaged across nuggets"를 요약자가 기호로 옮긴 것이며 원문에 번호 붙은 수식은 없다.)

Event Ordering 예외: 품질이 회상과 순서 모두에 달려 있으므로 Kendall τb를 쓴다. LLM 동치 판정기(Listing 21: "두 조각이 같은 사건/사실이면 YES, 아니면 NO")가 응답 속 사건을 nugget과 정렬하고, 정렬된 순서열에 τb를 계산해 회상과 순서 충실도를 함께 잡는다.

직관적으로 말하면: 채점관이 정답 체크리스트를 한 줄씩 읽으며 "있음/반쯤/없음" 도장을 찍고, 도장 평균이 점수다. 그래서 4줄짜리 체크리스트(Contradiction Resolution)에서 한 줄만 맞히면 아무리 그 한 줄이 정확해도 0.25점이다.

3. LIGHT: LLM의 기억 능력 향상 (§3)

3.0 개요 — 세 메모리의 결합

왜 문제인가: long-context는 전체 이력을 넣지만 길수록 성능이 붕괴하고(§4.2), 10M은 아예 들어가지 않는다. 일반 RAG는 질문과 표면적으로 닮은 턴만 가져와 ① 흩어진 사실의 통합(multi-hop·요약), ② 질문과 닮지 않은 지속 지시·선호, ③ 시간 순서(갱신·순서·날짜 계산)를 놓친다.

해법: 인지과학(Sridhar et al., 2023; Binder & Desai, 2011)에서 사람은 두 기억 메커니즘 — 특정 개인 경험을 맥락과 함께 떠올리는 episodic memory와 최근 사건 정보를 짧게 유지·조작하는 working memory — 를 쓰고, 여기에 외부 기록인 scratchpad(메모)가 장기 회상을 돕는다. LIGHT는 이 셋을 흉내 낸다. 질문 $x$와 대화 $\mathcal{T} = \{t_i\}_{i=1}^{|\mathcal{T}|}$가 주어지면:

$$E = R(x, k, \mathcal{T})$$ $$W = \{t_{|\mathcal{T}|-i}\}_{i=0}^{z}$$ $$S_x = f(S_{|\mathcal{T}|}, x)$$ $$y = \pi(x, E, W, S_x)$$

retriever $R$이 관련 구간 $k$개를 꺼내 episodic recall을 흉내 내고($E$), 가장 최근 $z$개 대화 쌍이 working memory($W$)가 되며, 미리 구축된 scratchpad $S_{|\mathcal{T}|}$(최대 $m$개의 핵심 노트)에서 필터 함수 $f$가 질문에 관련된 항목만 남긴다($S_x$). LLM $\pi$는 질문과 세 메모리를 함께 조건으로 답한다(Listing 44). (원문은 이 식들에 번호를 붙이지 않았다. 또한 $z$와 $m$의 실제 값은 원문에서 찾을 수 없으며, $k$는 기본 5로 보인다 — Table 9의 K=5 열이 Table 1의 LIGHT 값과 일치.)

직관적으로 말하면: 시험장에 세 가지를 들고 들어간다 — 질문 키워드로 찾아 펼친 일기장 몇 쪽($E$), 방금까지의 대화 메모($W$), 그리고 평소 써 둔 요점 노트 중 이 문제와 관련된 쪽만($S_x$). $E$는 "정확하지만 단편적", $S_x$는 "요약됐지만 전체를 꿰는", $W$는 "최신이지만 짧은" 재료라 서로의 약점을 메운다.

3.1 대화에서의 검색 — episodic memory (§3.1)

색인 구축: 각 사용자–어시스턴트 턴 뒤에 Qwen2.5-32B-AWQ(AWQ = Activation-aware Weight Quantization, 4비트 가중치 양자화)가 Listing 40 프롬프트로 key–value 쌍과 그 교환의 요약을 추출한다. key는 엔티티, value는 속성·세부 서술이며, 사건 수준의 세밀한 색인이 된다(원문은 해마의 기억 흔적에 비유). 이 key–value와 요약을 BAAI/bge-small-en-v1.5 임베딩 모델로 벡터화해 벡터 DB(FAISS)에 key로 저장하고, 원 대화 구간은 value로 보관해 생성 시 원문에 충실하게 한다.

검색: 질문 $x$를 같은 임베딩 모델로 임베딩해 저장된 key와 비교하고, top-$k$ 최근접 이웃에 해당하는 원 대화 구간을 돌려준다.

RAG 베이스라인과의 차이: RAG 베이스라인(§4.1)은 각 턴 쌍의 원문 자체를 임베딩한다. LIGHT는 원문 대신 추출된 key–value·요약을 검색 키로 쓴다. 긴 코드 블록이나 장황한 답변이 섞인 턴도 "Tweepy 버전 → v4.12.1" 같은 짧은 키로 검색되므로 엔티티 중심 질문(IE·KU)의 매칭이 쉬워진다는 것이 설계 의도로 보인다(원문은 이 효과를 따로 ablation하지 않음).

직관적으로 말하면: 도서관 책(턴 원문)을 통째로 스캔해 비슷한 책을 찾는 대신, 책마다 "등장인물–사건" 색인 카드를 만들어 카드로 찾고, 찾은 뒤에는 원래 책을 펼쳐 읽는다.

3.2 Scratchpad 구성과 활용 (§3.2)

구성: 개별 대화 사건을 넘어 정보를 보존하는 상위 표현이다. 의미 지식(사실·개념), 자전적 세부(생애 사건), 전향적 기억(미래 의도), 맥락 메타데이터(시간·장소·획득 맥락)를 통합한다(Binder & Desai, 2011). 대화 쌍마다 Qwen2.5-32B-AWQ가 Listing 41로 현재·직전 턴을 추론해 핵심 내용을 추출하고, 결과를 이전 scratchpad에 반복 병합한다. 내용이 ##30K 토큰 임계값을 넘으면 GPT-4.1-nano가 15K 토큰 요약으로 압축##한다(Listing 42). 압축 프롬프트는 관련 정보 군집화 → 중복 제거 → 우선순위화 → 압축 4단계를 지시하고, KEY ENTITIES & RELATIONSHIPS / CORE DECISIONS & PREFERENCES / PROCESSES & WORKFLOWS / USER PREFERENCES / USER INSTRUCTIONS / IMPORTANT DATES / CRITICAL CONTEXT / ACTIONABLE ITEMS / IMPORTANT DEVELOPMENTS의 9개 섹션으로 정리하며, "새 값이 있으면 옛 값을 제거"하고 "목표 길이보다 크게 짧으면 세부를 더하라"고 요구한다. episodic 색인과 달리 scratchpad는 검색 DB에 저장되지 않고 추론 시 맥락 입력으로 직접 제공된다.

필터링 (함수 $f$): 추론 시 scratchpad를 LangChain의 SemanticChunker(고정 토큰 창이 아닌 의미 기준 가변 길이 분할)로 청크화하고, 각 청크를 Qwen2.5-32B-AWQ가 Listing 43으로 질문 관련성 yes/no 판정해 관련 청크만 남긴다. 결과는 응답 생성기로 전달되는 압축된 scratchpad다.

직관적으로 말하면: scratchpad는 "지금 유효한 사실" 장부다. "Instagram 스프린트 마감 → 4/5로 연장"처럼 갱신을 덮어쓰고, "항상 팀원 수를 말해 달라" 같은 지시를 별도 칸에 남기며, 날짜를 정규화해 둔다. 검색이 놓치는 것(질문과 안 닮은 지시, 옛 값/새 값의 선후)을 장부가 잡는다 — 부록 F가 바로 이 네 가지 사례를 보여 준다.

5. 관련 연구 (§5, 부록 A)

원문 §5는 부록 A의 압축판이다. ① 컨텍스트 확장: 512–2K(GPT-2/3) → 128K–1M(Claude-3, GPT-4-Turbo, Gemini 2.0) → 10M(Llama 4)로 커졌고, 효율적 attention(sparse·linear·메모리 최적 커널), 위치 인코딩(상대·스케일된 rotary·ALiBi), 장문 학습(continued training·curriculum), 추론 최적화(paged attention, KV-cache 압축, 분산 attention)가 이를 가능하게 했다. ② 지속 메모리 메커니즘: 재귀·압축(Transformer-XL, Compressive Transformer), state-space(RWKV, Mamba, Hyena), 외부 메모리(Memformer, RETRO, RMT), 컨텍스트 요약(AutoCompressor), RAG(REALM, RAG, HippoRAG). ③ 벤치마크: DialSim, MSC, LoCoMo, MemoryBank, DuLeMon, PerLTQA, LongMemEval, MemBench는 회상·시간 추론·다중 세션 추론을 보지만 좁은 도메인, 얕은 의존성, 세션 이어 붙이기의 한계가 있고, MemoryCode는 단일 도메인이다. BEAM은 10M까지, 다양한 주제로, 모순 해결·사건 순서·지시 따르기를 새로 넣고, 서사 연속성을 보존하는 단일 사용자 대화를 만든다. (배경 절의 그림 두 장 — 컨텍스트 타임라인과 Table 2 행렬 — 이 이 절의 내용을 시각화한다.)

부록 A는 각 항목을 조금 더 풀어 쓴다: 컨텍스트 확장 쪽에 Gemini 1.5 Pro·Claude-4·GPT-4.1, Longformer·BigBird·Linformer·Performer·FlashAttention, RoPE·YaRN·NTK·ALiBi, LLaMA-2-Long·LongRoPE, PagedAttention·H2O·SnapKV·Ring Attention을 열거하고, 메모리 쪽에서 state-space 모델을 "attention을 재귀 동역학으로 대체해 선형 확장과 이론상 무한 기억"으로, AutoCompressor를 "정보 보존 압축 표현을 학습해 토큰 사용을 줄이는 직교적 전략"으로 설명한다. 벤치마크 쪽에는 DialSim 350K, LoCoMo 50대화·평균 9K·35세션, MemoryBank 300세션·194문항, LongMemEval 500문항 같은 규모를 덧붙인다.

6. 결론 (§6)

원문은 기존 장기 기억 벤치마크의 한계를 지적하고, 긴 일관 대화(최대 10M)와 다양한 기억 probe를 갖춘 BEAM을 만드는 확장 가능한 프레임워크, 그리고 episodic·working·scratchpad 메모리를 결합한 인지 영감의 LIGHT를 제안했다. 표준 LLM의 성능은 긴 맥락에서 떨어지지만 LIGHT는 평균 3.5%–12.69% 개선한다고 결론짓는다. 원문의 결론에는 한계 절이 따로 없다.

원문 B.6은 하나의 부동산 투자 대화(터키 배경, Halkbank·Ziraat Bank 모기지, 중개인 Mehmet Yilmaz)에서 10개 능력의 대표 질문과 이상 답변을 제시한다. 이 요약에서는 §2.2의 카드 갤러리 그림으로 옮겼다. 몇 가지는 답의 형식 자체가 능력을 정의한다: Contradiction Resolution의 이상 답은 "모순되는 정보를 말씀하셨네요 — 웨비나에 간 적 없다고 하셨지만 터키 다가구 임대 수요 웨비나에 참석했다고도 하셨습니다. 어느 쪽이 맞나요?"처럼 질문으로 끝나야 하고, Event Ordering 질문은 "정확히 10개만 말하라(Mention ONLY and ONLY ten items)"고 개수를 고정해 τb 계산을 가능하게 한다.

부록 F. 사례 연구 — scratchpad의 효용

원문은 scratchpad를 "지속적이고 반복 압축되는 의미 계층"으로 규정하고 네 가지 역할을 든다: (i) 흩어진 엔티티·사실 통합(Information Extraction), (ii) 사용자 메타 지시를 과제 맥락과 함께 보존(Instruction Following), (iii) 상태 변화·덮어쓰기 기록(Information Update), (iv) 시간 단서를 명시적 앵커로 정규화(Temporal Reasoning). 네 능력에서 "LIGHT 전체" vs "LIGHT w/o scratchpad"를 대비하고, 정답을 가능케 한 정확한 scratchpad 단서를 보여 준다(나머지 여섯 능력에도 비슷한 이득이 있다고 하나 사례는 없다).

원문 정리(Takeaways): 모든 능력에서 scratchpad를 빼면 전체 모델이 피하는 실패가 일관되게 생긴다. IE에서는 흩어진 엔티티·버전 언급을 모아 정확한 도구 버전과 신상(도시·나이)을 복원하고, IF에서는 "항상 팀원 수 포함" 같은 메타 선호를 많은 턴 뒤에도 유지하며, KU에서는 덮어쓰기(연장된 마감, 줄어든 메모리)를 담아 낡은 답을 막고, TR에서는 정규화된 날짜 앵커로 간단·정확한 일수 계산을 가능하게 한다. scratchpad는 working(최신성)·episodic(검색) 메모리를 보완하는 고효용 의미 골격이라는 것이 원문 결론이다.

부록 G. 정성적 오류 분석

LIGHT가 틀린 probing 질문을 능력별로 수작업 검토해 지배적 실패 모드를 정리했다.

  • Abstention: (a) 맥락에 관련 정보가 전혀 없는데 환각으로 답함 — LLM이 지식 여부와 무관하게 항상 답하도록 학습되었기 때문(Kalai et al., 2025 인용), (b) 질문과 무관한 답 — 긴 맥락을 제대로 이해 못함, (c) 주된 모드: 질문이 묻는 것과 비슷하지만 같지 않은 엔티티·날짜·개념이 맥락에 있을 때 그것으로 답을 만든다.
  • Contradiction Resolution: 맥락에 모순의 한쪽만 있어 그것으로 답함(다른 쪽이 없으니 충돌 감지 불가), 또는 양쪽이 다 있어도 위치·빈도 편향으로 한쪽을 과대평가.
  • Event Ordering: 맥락에 있는 항목을 응답에서 빠뜨리거나, 항목은 넣되 순서가 틀림 — 유사도 기반 retriever가 시간 순서를 보존하지 않아 순서 단서가 없고, 관련 사건을 다 검색하지도 못한다.
  • Information Extraction: 답이 맥락에 없음, 답이 있어도 비슷한 세부에 혼동, 답이 불완전.
  • Instruction Following: 지시가 맥락에 있는데 따르지 않음, 또는 지시가 맥락에 없음.
  • Knowledge Update: 맥락에 옛 값만 있음(retriever가 시간 순서를 보존하지 않음), 더 흔하게는 옛 값과 새 값이 모두 있는데 옛 값으로 답함 — 검색 문서가 올바른 시간순으로 제시되지 않기 때문.
  • Multi-hop Reasoning: 필요한 조각이 맥락에 있는데 쓰지 않음, 또는 추론 사슬의 일부가 빠짐.
  • Preference Following: 선호가 맥락에 없거나, 있어도 반영하지 않음.
  • Summarization: 맥락에 있는 정답 요소를 요약에서 빠뜨리거나, 맥락 자체에 일부가 없음.
  • Temporal Reasoning: 필요한 날짜가 있는데 다른 날짜에 혼동, 두 날짜가 다 있는데 산술 오류, 필요한 날짜가 없어 다른 날짜로 대체.

강점

  • "이어 붙이기"가 아닌 단일 서사 대화: 계획 → sub-plan → batch → 턴의 계층적 생성과 10M용 두 seed 전략은 길이를 키우면서도 같은 사용자·같은 관계망·일관된 타임라인을 유지한다. 기존 벤치마크의 가장 큰 약점(구간 분리 가능성)을 정면으로 다룬다.
  • 능력 설계가 대화의 시간 구조를 겨냥: CR·EO·IF를 새로 넣고, 계획 증강 단계에서 모순·갱신·지시 bullet을 일부러 심어 각 능력에 근거가 반드시 존재하도록 만든 점이 정교하다. 질문마다 provenance가 있어 근거 위치 분석(B.5)도 가능하다.
  • 1M–10M 구간의 실측: 1M 창 상용 모델이 500K부터 이미 약해지고 10M에서 0.10–0.13으로 떨어진다는 결과는 "긴 창 = 기억 해결"이라는 가정을 반박하는 구체적 증거다.
  • LIGHT의 실용성: 학습이 필요 없고 백본 무관하며, 32K 창의 Qwen으로도 128K 창 long-context보다 높은 점수를 낸다. 구성요소(검색·노트·필터)가 모두 프롬프트 수준이라 바로 이식할 수 있다.
  • 투명한 부록: 44개 프롬프트, 알고리즘, 하이퍼파라미터(Table 6), 능력별 전체 표(Table 8–13), 실패 모드 분석, 코드·데이터 공개.

한계와 의문점

  • 통계적 불확실성 미보고: 모든 표가 단일 실행이며 표준편차·신뢰구간이 없다. 요약자 역산(§4.1)으로는 10M이 10개 대화·능력당 20문항이라, 10M의 개별 칸(예: Gemini 10M의 RAG 우위, 10M K=10의 골짜기, bge-large +16.37%)은 문항 몇 개의 변동으로도 설명될 수 있다.
  • 헤드라인 수치의 집계 불명확: 초록의 "3.5%–12.69%"와 §4.2의 능력별 상대 이득(+160.6%, +27.2% 등)은 Table 1에서 어떤 집계로도 정확히 재현되지 않는다. 또 "+155.7%" 같은 큰 수치는 10M에서 "최근 구간만 본" Vanilla를 분모로 한 것이다.
  • Abstention 트레이드오프: LIGHT는 Abstention에서 RAG보다 16칸 중 15칸에서 낮고(1칸 동률), ablation에서도 모듈을 뺄수록 Abstention이 오른다. 원문은 "모든 방법이 Abstention에서 가장 높다"고만 쓰고 이 역전을 논의하지 않는다. 실서비스에서 "지어내기 증가"는 평균 점수 이득보다 치명적일 수 있다.
  • Working memory의 효용 부족: 100K·500K·1M에서 working memory를 빼는 편이 낫다. "전체 구조가 일관되게 최고"라는 결론은 10M에서만 성립하며, 이 결과는 BEAM의 근거가 대화 앞쪽에 몰리도록 설계된 것(Listing 1의 "batch 1–3에서 70–80%")과 얽혀 있어, 벤치마크 설계가 특정 메모리 구성요소의 가치를 결정하는 순환이 있다.
  • 비교 공정성: LIGHT는 구축 단계에서 턴마다 Qwen2.5-32B를 두 번(KV 추출·scratchpad) 호출하고 GPT-4.1-nano로 압축하며, 추론 시에도 청크마다 필터 호출을 한다. RAG 베이스라인은 이런 전처리가 없다. 계산 비용·지연 시간 비교가 없고, scratchpad 추출 모델(Qwen)이 GPT·Gemini 백본 실험에서도 그대로 쓰였다면 "백본 무관" 주장에 외부 모델의 기여가 섞인다. 또한 K=15가 더 좋음에도 주 결과는 K=5이고, RAG 베이스라인의 K는 튜닝되지 않았다.
  • 강한 메모리 베이스라인 부재: 비교 대상이 long-context, 단순 RAG, ReadAgent뿐이다. MemGPT/Letta, A-Mem, Mem0, HippoRAG 같은 최신 메모리 시스템과는 비교하지 않았다(원문은 HippoRAG를 관련 연구로만 인용).
  • 평가 파이프라인의 재현성: nugget 판정 LLM과 Event Ordering 동치 판정기의 정체, 판정자–사람 일치도, τb에서 누락 사건 처리 방식이 본문에 명시되지 않는다. Event Ordering 점수가 방법·길이와 거의 무관하게 0.16–0.27에 머무는 것은 지표의 변별력 문제일 수 있다.
  • 합성 데이터의 편향: 대화·질문·이상 답 모두 LLM(LLaMA-3.3, GPT-4.1 계열)이 생성했다. 평가 대상에 GPT-4.1-nano가 포함되어 같은 계열 모델의 문체·사실 표현에 유리할 수 있고, 사람 품질 평가는 저자 측 2인이 대화 일부만 읽는 방식이다.
  • 표의 오기와 불일치: Table 3의 128K follow-up 216, Table 10의 "0.43"·"320.220", Table 8·9의 일부 Average가 능력별 값과 불일치(예: 1M K=20 0.330 vs 재계산 0.338), 100K/128K 명칭 혼용, Table 5의 제목 106개 vs 100개 대화, Figure 1의 δ<3 vs 본문 δ=2. 개별로는 사소하지만 벤치마크 논문으로서 정밀도에 대한 신뢰를 떨어뜨린다.
  • Contradiction Resolution의 바닥 효과: 모든 방법이 0.06 미만이라 이 능력에서 방법 간 비교는 사실상 불가능하다. CR nugget이 "모순 지적 + 양쪽 진술 + 확인 요청"을 요구하는데, 일반 어시스턴트는 모순을 지적하기보다 최신 진술을 따르도록 학습되어 있어 "능력 부족"과 "행동 규범 차이"가 섞여 측정된다.

Key Takeaways — 이 논문에서 가져갈 것

  1. 1M 컨텍스트 창은 장기 대화 기억을 해결하지 않는다: 1M 창 상용 모델도 500K부터 성능이 크게 꺾이고 10M에서는 0.10–0.13까지 떨어진다. 긴 대화 제품에서 "모델 창이 크니 전부 넣자"는 전략은 BEAM 기준으로 검색·노트를 더한 간단한 구성보다 일관되게 열세다.
  2. 장기 대화 벤치마크를 만들 때는 "계획 먼저, 떡밥은 따로": 대화 계획을 먼저 세우고, 평가하려는 능력(모순·갱신·지시)용 bullet을 별도 단계에서 심고, bullet–턴 provenance를 유지하는 BEAM의 설계는 다른 도메인(에이전트 로그, 고객 상담) 벤치마크 생성에도 그대로 옮길 수 있는 레시피다.
  3. "지금 유효한 사실" 장부(scratchpad)가 검색을 보완한다: 갱신·지속 지시·날짜 정규화는 유사도 검색이 구조적으로 놓치는 정보다. 매 턴 사실을 정규화해 누적하고 질문 시 관련 청크만 필터링하는 단순한 장치가 요약·지시·선호 능력에서 가장 큰 이득을 냈다(§4.2, §F).
  4. 짧은 이력이면 검색보다 노트, 긴 이력이면 둘 다: 100K에서는 scratchpad만으로 충분하고 working memory는 오히려 방해였지만, 10M에서는 모든 모듈이 필수였다. 검색 깊이도 K=5보다 K=15가 길이 전반에서 6–11% 좋았다 — 메모리 구성은 대화 규모에 맞춰 조정해야 한다.
  5. 시간 순서가 retriever의 맹점: Knowledge Update·Event Ordering 실패의 원인은 "유사도 검색이 순서를 잃는 것"으로 진단되었다. 검색 결과를 타임스탬프 순으로 재정렬하거나 최신 값을 우선하는 후처리가 저비용 개선 후보다(원문 미실험, 요약자 제안).
  6. (비판적 관점) 더 많이 기억시키면 더 많이 지어낸다: ##LIGHT는 평균 점수를 올리지만 Abstention에서는 RAG보다 거의 항상 낮고, 모듈을 뺄수록 Abstention이 오른다##. 헤드라인 개선율(최대 +155.7%)도 약한 10M Vanilla 대비이며 RAG 대비로는 약 4–12%(전체 평균은 한 자릿수) 수준이다. 실무에 도입할 때는 평균 점수와 함께 "모를 때 모른다고 하는가"를 별도 지표로 지켜봐야 한다.
