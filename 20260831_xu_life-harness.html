목차

TL;DR

  • 문제: 에이전트 적응은 여전히 모델 적응으로 프레이밍된다 — 스케일링, fine-tuning, RL, distillation. 그러나 ##결정론적·규칙 지배 도메인에서는 관련 구조의 상당 부분이 모델 밖에 있다## — 도구 스키마, API 계약, 허용 행동, 피드백 규칙, 정지 조건, 복구 전략. 정적 능력과 상호작용 성능의 격차가 이를 보여준다: Qwen3.5-4B는 경쟁 수준 수학 벤치마크 HMMT Feb (Harvard–MIT Mathematics Tournament, 경쟁 수학 대회)에서 74.0%인데 결정론적 임바디드 벤치마크 ALFWorld에서는 43.1%다.
  • 해결: Life-Harness — 모델 가중치도 평가 환경도 바꾸지 않고 frozen LLM 에이전트를 개선하는 lifecycle 인식 런타임 harness. 학습 궤적에서 반복되는 상호작용 실패를 재사용 가능한 개입으로 변환하고, 평가 시에는 고정된다. 개입은 에이전트 상호작용 생애주기의 4개 층에 배치된다 — 환경 계약(상호작용 전) / 절차적 skill(과제 조건화) / 행동 실현(실행 전) / 궤적 규제(실행 후).
  • 왜 작동하는가: 결정론적 환경에서 실패가 상호작용 생애주기의 특정 단계에 국소화되기 때문이다. 실패 진단(393개 실패 에피소드 수동 검사)이 이를 확인한다 — ##행동 실현 33.6% / 환경 계약 33.3% / 궤적 퇴화 23.2% / 일반 추론 9.9%##. 즉 실패의 90%가 추론 능력이 아니라 인터페이스 불일치다. 그리고 그 불일치는 환경 쪽 구조이므로 모델에 무관하게 고칠 수 있다.
  • 결과: 7개 결정론적 환경(τ-bench, τ²-bench, AgentBench) × 18개 모델 백본에서 ##126개 model–환경 설정 중 116개(92%) 개선, 평균 상대 개선 88.5%##. 결정적으로 harness는 Qwen3-4B-Instruct 궤적만으로 진화되었고 나머지 17개 백본에 그대로 재사용된다. 그리고 도구 사용 특화 학습을 능가한다 — ##Qwen2.5-32B + Life-Harness(0.579)가 그 파생 모델 xLAM-2-32B(0.504)를 7.5%p 앞선다##.
  • 비유: 신입 직원이 실수하는 이유가 머리가 나빠서가 아니라 사내 규칙과 양식을 모르기 때문일 때, 해법은 사람을 재교육하는 것이 아니라 업무 매뉴얼·입력 검증·체크리스트를 정비하는 것이다. 그리고 그 매뉴얼은 다음에 오는 직원에게도 그대로 쓸 수 있다 — 이것이 harness가 18개 모델에 전이되는 이유다.

핵심 기여 (Key Contributions)

  1. runtime interface adaptation의 형식화: 기존 방식 $\theta' \leftarrow A_{param}(\theta, T_{train})$과 대비되는 $H' \leftarrow A_{harness}(H, T_{train})$, $\theta$ 고정. ##이 적응은 환경 특정적이지만 모델 무관(environment-specific but model-agnostic)하다## — 한 환경에서 진화한 harness가 같은 상호작용 프로토콜을 따르는 다른 백본에 재학습 없이 일반화된다.
  2. 실패 진단에 기반한 4층 설계: 무작정 harness를 설계하지 않고 먼저 진단한다. frozen Qwen3-4B-Instruct를 학습 과제에 실행해 실패 궤적을 수동 검사하고, 각 실패에 에이전트–환경 루프에서 가장 이른 지배적 병목에 따라 주 실패 유형을 배정한다. 그 결과 네 범주가 나오고, 각 범주에 대응하는 층이 만들어진다.
  3. Life-Harness의 4개 lifecycle 층: ⑴ Environment Contract Layer($C' = C \oplus \Delta_C$) — 상호작용 전 안정적 환경 제약을 명시화. ⑵ Procedural Skill Layer($K_x = \mathrm{TopK}\,\mathrm{score}(x,k)$, BM25) — 학습 궤적에서 증류한 skill 라이브러리 검색. ⑶ Action Realization Layer($z_t \in \{\mathrm{EXEC}(a_t), \mathrm{BLOCK}(m_t)\}$) — 실행 전 검증·정규화. ⑷ Trajectory Regulation Layer — 실행 후 퇴화 패턴 감지와 복구 촉발.
  4. 궤적 주도 harness 진화: coding agent(Codex)가 학습 궤적과 harness 설계 기준을 함께 읽고 각 층에 대한 업데이트를 제안한다. 목표가 두 개다 — ⑴ 반복 실패 패턴에 대한 커버리지 확장, ⑵ 개입이 과도 발동하거나 정상 행동을 해치는 회귀 사례 탐지. 자유형 harness 코드를 통째로 탐색하지 않고 4층으로 국소화하는 것이 빠른 수렴의 이유라고 저자들은 설명한다.
  5. 18개 백본 × 7개 환경의 광범위 검증: instruct 계열 8개, reasoning 계열 6개, agent 특화(xLAM) 4개. 126개 설정 중 116개 개선. Table 1의 벤치마크별 상대 이득은 +10% ~ +84%.
  6. prompt 최적화만으로는 부족함을 보인다: prompt-only evolving(GEPA, OPRO 계열)과 비교해 Life-Harness가 평균 상대 개선 120%를 추가한다. "agentic 과제의 성능은 초기 prompt만이 아니라 런타임이 도구·행동·피드백·다단계 궤적을 매개하는 방식에 달려 있다"는 것이 이 격차의 해석이다.
  7. 모델 학습과 harness의 관계를 세 패턴으로 정리: ⑴ harness가 특화 학습을 능가할 수 있다(가중치 갱신 없이 7.5%p). ⑵ 학습 후에도 harness가 유익하다(xLAM에 얹으면 6.8~28.9%p 추가). ⑶ 특화 도구 사용 학습이 out-of-domain (OOD, 학습 분포 밖 도메인)으로 전이되지 않는다 — τ²-bench와 AgentBench에서 xLAM이 자기 base인 Qwen2.5-32B보다 낮다.
  8. leave-one-layer-out ablation: 네 층 모두 필수적이며, 과제마다 다른 층이 기여한다. Airline에서 Action 층 제거가 −61.7%인 반면 Trajectory 층 제거는 −3.3%인데, Retail에서는 네 층이 −15.9 ~ −17.5%로 고르다.

배경 — 왜 지금 "harness"인가

1. 에이전트는 LLM이 아니다

출발 명제: 논문의 첫 문장은 "An LLM agent is not just an LLM"이다. 표준 LLM은 입력을 받아 출력을 내는 무상태 함수지만, 에이전트는 상태를 가진 상호작용 루프에 박혀 있는 모델이다 — 환경이 관측을 노출하고, 런타임 시스템이 사용 가능한 도구와 행동을 규정하고, 모델이 행동이나 도구 호출을 내보내고, 실행기가 그것을 환경에 적용하고, 그 결과 피드백이 다음 결정을 갱신한다.

이때 런타임 harness는 그 루프에서 모델과 환경 사이를 매개하는 모든 것이다 — 관측을 어떻게 보여줄지, 도구를 어떻게 설명할지, 행동을 어떻게 실행 가능한 형태로 만들지, 피드백을 어떻게 해석할지, 궤적을 어떻게 통제할지. 따라서 결과 행동은 $\pi_\theta$만이 아니라 harness에 의해서도 결정된다. 이 시스템 수준 관점은 소프트웨어 엔지니어링 어시스턴트(SWE-agent, Claude Code, OpenCode), 웹 내비게이션(WebArena), 데이터베이스 조작(Spider 2.0), OS 제어(OSWorld, AgentBench), 도구 사용 비즈니스 워크플로우(τ-bench, τ²-bench), 임바디드 상호작용(ALFWorld)에 걸쳐 점점 중요해지고 있다.

2. 적응은 어디서 일어나야 하는가

왜 문제인가: 그럼에도 에이전트 적응은 여전히 모델 적응으로 프레이밍된다 — 모델 스케일링(Llama 3, Qwen2.5), fine-tuning(FireAct, APIGen-MT), 강화학습(DeepSeek-R1, WebRL, ToolRL), distillation(on-policy distillation). 이 접근들은 강력하지만 도메인 특정 행동을 암묵적으로 가중치 안에 흡수한다. 그리고 결정론적·규칙 지배 도메인에서는 관련 구조의 상당 부분이 모델 밖에 산다 — 도구 스키마, API 계약, 허용 행동 집합, 피드백 규칙, 정지 조건, 복구 전략.

이 구별이 실무에서 비용으로 나타난다. 파라미터 적응은 모델·과제 특정적이므로 base 모델이 바뀌거나 새 환경에 배치될 때마다 반복되어야 한다.

해법: $\theta$를 고정하고 harness를 적응시킨다.

$$\theta' \leftarrow A_{param}(\theta, T_{train}) \quad \text{(기존)} \qquad \text{vs} \qquad H' \leftarrow A_{harness}(H, T_{train}),\ \theta\ \text{fixed} \quad \text{(이 논문)}$$

적응된 harness $H'$는 모델이 환경과 상호작용하는 방식을 바꾸되, 모델 가중치와 평가 프로토콜은 그대로 둔다. 저자들은 이를 runtime interface adaptation이라 부르고, 그 결정적 성질을 이렇게 규정한다:

직관적으로 말하면: 이 적응은 환경 특정적이지만 모델 무관(environment-specific but model-agnostic)하다. 한 환경을 위해 진화된 harness는 같은 상호작용 프로토콜을 따르는 다른 모델 백본에 재학습 없이 일반화된다. 파라미터 적응이 "모델 하나당 한 번"의 비용이라면, harness 적응은 "환경 하나당 한 번"의 비용이다. 모델 수가 환경 수보다 훨씬 빨리 늘어나는 현실에서 이 차이는 곱셈이 아니라 나눗셈이 된다.

3. 선행 연구 지형 — harness 최적화는 이미 시작됐다

이 논문이 진공에서 나온 것은 아니다. frozen LLM 시스템 주변의 scaffold를 최적화하는 연구 계열이 최근 급격히 형성되었고, 논문은 이들과의 차이로 자기 위치를 규정한다.

4. prompt 최적화와는 무엇이 다른가

가장 혼동되기 쉬운 이웃 계열이 prompt adaptation이다. 이들도 frozen LLM 시스템을 가중치 대신 지시문·시연·템플릿을 다시 씀으로써 적응시킨다 — PromptWizard, Promptbreeder, LLM-as-optimizer 계열의 OPRO, textual-gradient 계열의 ProTeGi와 TextGrad, reflective optimizer인 GEPA.

논문의 구별은 명확하다: prompt 최적화는 모델을 향한 텍스트(model-facing text)만 최적화하는 반면, Life-Harness는 런타임 인터페이스 전체를 적응시킨다 — prompt를 향한 계약뿐 아니라 행동 검증, 피드백 주도 복구, 궤적 규제까지. 이 구별은 수사가 아니라 §prompt-only 비교에서 평균 상대 개선 120% 차이로 실측된다.

§3 형식화 — 파라미터 적응에서 런타임 인터페이스 적응으로

3.1 런타임 시스템으로서의 LLM 에이전트

논문은 LLM 에이전트를 상태를 가진 환경과 상호작용하는 정책 $\pi_\theta$로 형식화한다. 여기서 환경은 환경 $E$뿐 아니라 사용자 $U$도 포함할 수 있다 (τ-bench류의 대화형 과제에서 사용자도 상태를 가진 상대다).

한 에피소드는 네 요소로 정의된다 — 과제 $x$, 결합 환경 $E$ (사용자 $U$ 포함), 환경 계약 $C$, 스텝 예산 $B$. 이 중 $C$가 이 논문의 조작 대상이다:

환경 계약 $C$란: 의도된 상호작용 프로토콜을 규정하는 것 — 사용 가능한 도구, 인자와 피드백 포맷, 답변 포맷, 과제 특정 정책. 즉 "이 환경에서 무엇이 올바른 행동인가"를 모델에게 알려 주는 모델 가시적 명세 전체다. 논문은 이것을 고정된 환경 속성이 아니라 조작 가능한 인터페이스 변수로 재해석한다. 이 재해석이 ❶ Environment Contract Layer의 근거다.

에피소드는 다음으로 시작한다:

$$s_0,\ o_0 = E.\textsc{Init}(x)$$

스텝 $t$에서 궤적은 계약·과제·과거 행동·관측을 모두 담는다:

$$\tau_t = (C,\ x,\ o_0,\ a_0,\ o_1,\ \ldots,\ a_{t-1},\ o_t)$$

에이전트가 행동을 생성하고:

$$a_t \sim \pi_\theta(\cdot \mid \tau_t)$$

여기서 $a_t$는 도구 호출, 텍스트 명령, 최종 답변 제출 중 하나일 수 있다. 논문은 표기 통일을 위해 텍스트 행동도 pseudo-tool로 취급한다 (예: ACT, SubmitAnswer). 환경이 행동을 처리한다:

$$s_{t+1},\ o_{t+1} = E.\textsc{Step}(s_t,\ a_t)$$

여기서 중요한 세부가 하나 있다 — $a_t$가 지원되지 않거나 무효면 환경은 에러 메시지를 반환할 수 있고, 그 피드백도 여전히 상호작용 궤적의 일부다. 즉 실패한 행동이 컨텍스트를 소모하며 궤적에 누적된다. 갱신된 궤적은:

$$\tau_{t+1} = (C,\ x,\ o_0,\ a_0,\ \ldots,\ a_t,\ o_{t+1})$$

에피소드는 과제 완료, 환경 종료, 또는 스텝 예산 소진까지 계속된다.

직관적으로 말하면: 이 형식화의 요점은 마지막 문장에 있다 — 성능은 $\pi_\theta$만이 아니라 출력이 실행 전후로 어떻게 매개되는가에도 달려 있다. 위 수식들에서 $\pi_\theta$는 딱 한 줄($a_t \sim \pi_\theta$)이고, 나머지는 전부 $C$, $E.\textsc{Step}$, $\tau_t$의 구성 방식, $B$의 소진 방식 — 즉 harness가 결정하는 것들이다. 수식이 이미 harness가 다수임을 보여 준다.

3.2 파라미터 적응 vs 런타임 인터페이스 적응

이 절의 내용은 §배경에서 이미 다뤘으므로 여기서는 수치로 본 비용 구조만 짚는다. 논문이 명시적으로 계산하지는 않지만, 실험 설계 자체가 이 계산을 함축한다.

§4.1 실패 진단 — 설계보다 진단이 먼저다

방법론적 미덕: 이 논문의 가장 좋은 점은 harness를 먼저 설계하지 않았다는 것이다. 저자들은 frozen Qwen3-4B-Instruct를 여러 상호작용 환경의 학습 과제에 실행해 실패 궤적을 모으고, 수동 검사한다. 각 실패 에피소드에 에이전트–환경 루프에서 가장 이른 지배적 병목(earliest dominant bottleneck)에 따라 주 실패 유형 하나를 배정한다. 분류는 부록 A.1의 규칙 기반 프로토콜을 따르며, Codex가 완전한 상호작용 trace를 읽고 궤적 하나하나에 대해 수행한다 — 집계 통계에서 유추하지 않는다.

우선순위 기반 분류 프로토콜 — 왜 순서가 중요한가

왜 문제인가: 한 실패 에피소드에는 보통 여러 문제가 겹쳐 있다. 위 §3.1 수치 예제에서 봤듯 나중에 나타난 증상(예산 소진, 반복)이 먼저 발생한 인터페이스 실패를 가릴 수 있다. 그래서 저자들은 우선순위 프로토콜을 쓴다 — 주석자는 먼저 action realization 실패를 확인하고, 그다음 environment contract 불일치, 그다음 trajectory degeneration을 확인한 뒤, 남는 것을 잔여 범주에 배정한다.

논문이 든 예: 에이전트가 도구 호출을 일반 텍스트로 작성하면 환경은 그것을 절대 실행하지 않고, 에피소드는 결국 스텝 예산을 소진한다. 이때 궤적 퇴화가 아니라 행동 실현 실패로 주석한다. 이 순서가 "나중의 증상이 앞선 인터페이스 실패를 숨기는 것"을 막는다.

§4.2~4.3 방법 — 네 개의 lifecycle 층

설계 원리: 위 진단을 그대로 따라, Life-Harness는 에이전트 생애주기의 서로 다른 단계에 통합된 네 층으로 구성된다. 각 층은 임의로 고른 개입 지점이 아니라 진단된 실패 범주 하나씩에 대응한다. 아래 시퀀스 다이어그램이 네 층이 정확히 어느 왕복 지점에 끼어드는지를 보여 준다.

4.3.1 ❶ Environment Contract Layer — 상호작용 전

왜 문제인가: 실패의 33.3%가 "문법은 맞지만 의도된 도구 사용이나 호출 규약을 위반"하는 경우다. 모델은 도구를 호출할 줄은 아는데 그 도구가 무엇을 위한 것인지, 언제 쓰면 안 되는지, 인자의 의미적 포맷이 무엇인지를 모른다. 그리고 이 정보는 대부분 환경 쪽에 안정적으로 존재하지만 모델에게 노출되지 않는다.

해법: 모델 가시적 계약 $C$를 보강한다.

$$C' = C \oplus \Delta_C$$

여기서 $\Delta_C$는 환경 정책, API 동작, 학습 궤적에서 반복된 실패로부터 유도된 간결한 갱신을 담는다. 보강된 계약 $C'$가 $C$를 대신하여 모델에게 제시된다. 실무적으로 $\Delta_C$는 ⑴ 도구를 어떻게 호출해야 하는지, ⑵ 환경 프로토콜 하에서 어떤 행동이 허용되는지, ⑶ 어떤 환경 특정 함정을 피해야 하는지를 명시한다.

직관적으로 말하면: 도구 설명(tool description)은 보통 환경 개발자가 사람을 위해 쓴 것이지, LLM이 반복해서 빠지는 함정을 알고 쓴 것이 아니다. ❶은 그 설명서를 실패 로그를 읽고 다시 쓰는 층이다. 가중치를 건드리지 않고 "모델이 보는 세계의 명세"만 바꾼다.

4.3.2 ❷ Procedural Skill Layer — 과제 조건화 단계

skill이란 무엇인가: 논문의 정의는 "특정 하위 과제를 어떻게 달성하는지의 본질을 포착한, 간결하고 재사용 가능한 전략"이다. 즉 이 논문에서 "skill"은 실행 가능한 코드나 도구가 아니라 학습 궤적에서 증류한 절차적 조언 문장이다 — 예컨대 ALFWorld의 "청소/가열/냉각 전에 물체를 먼저 집어라", WebShop의 "예산 초과 약 5%까지는 허용될 수 있다".

해법: 학습 궤적으로 구성한 skill 메모리 $S$에서 과제 설명 $x$에 관련된 skill을 검색한다.

$$K_x = \mathrm{TopK}_{k \in S}\ \mathrm{score}(x, k) \tag{BM25}$$

실험에서 $\mathrm{score}$는 BM25로 구현되고, 검색된 skill $K_x$가 초기 system prompt에 삽입된다. 부록 B가 중요한 하이퍼파라미터를 밝힌다 — ##모든 실험에서 top-1만 사용한다. 무관한 skill이 모델 컨텍스트를 오염시키는 것을 막기 위해서다##.

직관적으로 말하면: 이것은 non-parametric 지식 주입이다. 같은 조언을 fine-tuning으로 가중치에 넣는 대신, 과제가 들어올 때 관련된 것 하나만 꺼내서 붙인다. 그래서 모델이 바뀌어도 그대로 쓸 수 있고, 새 실패 패턴이 발견되면 라이브러리에 한 줄 추가하면 된다. 대신 top-1이므로 검색 정밀도가 전부다 — 잘못 뽑으면 아무 도움이 안 될 뿐 아니라 잘못된 방향을 지시한다.

4.3.3 ❸ Action Realization Layer — 환경 실행 직전

왜 문제인가: 가장 큰 실패 범주(33.6%)다. 모델의 의도는 타당한데 환경이 실행할 수 있는 형태로 제출되지 않는다. 그리고 §3.1 수치 예제에서 봤듯 이 실패는 자기 강화적이다 — 실행되지 않은 행동이 궤적에 에러로 남고, 모델은 같은 형태를 반복하며 예산을 소진한다.

해법: 모델이 행동을 출력한 후, 환경이 실행하기 전에 개입한다. 모델 행동 $a_t$, 현재 궤적 $\tau_t$, 현재 상태 $s_t$가 주어지면 이 층은 행동을 환경에 제출하거나 모델 가시적 차단 메시지 $m_t$를 돌려준다:

$$z_t = \textsc{RealizeAction}(a_t,\ \tau_t,\ s_t), \qquad z_t \in \{\textsc{Exec}(a_t),\ \textsc{Block}(m_t)\}$$

판정 근거는 전부 결정론적 환경 증거다 — 도구 스키마, 허용 행동 집합, 인자 제약, 과제 정책. 즉 이 층은 추측하지 않는다. "이 행동은 실행하면 결정론적으로 실패한다"가 확정될 때만 차단한다.

직관적으로 말하면: 컴파일러의 타입 체커와 같다. 프로그램을 실행해 보고 죽는 것을 기다리는 대신, 실행 전에 확실히 틀린 것만 걸러 낸다. 그리고 차단 메시지 $m_t$가 모델에게 되돌아가므로, 모델은 "왜 안 되는지"를 알고 다시 시도한다 — 침묵하는 에러보다 훨씬 정보가 많다.

4.3.4 ❹ Trajectory Regulation Layer — 실행 직후

왜 문제인가: 논문의 관찰이 날카롭다 — 많은 에이전트 실패는 자기 강화적(self-reinforcing)이다. 에이전트는 같은 무효 명령을 반복하고, 동등한 상태 사이를 오가고, 진전 없이 예산을 소진한다. 그리고 결정적으로: 이런 실패는 깊은 의미 이해 없이 궤적 수준 패턴만으로 탐지 가능하다.

해법: 실행된 행동, 반환된 관측, 남은 예산, 환경 증거가 주어지면 이 층이 계산한다:

$$r_t = \textsc{RegulateTrajectory}(\tau_t,\ a_t,\ o_{t+1},\ b_t), \qquad b_t = B - t - 1$$

출력 $r_t$는 네 강도 중 하나다 — 비어 있음 / 부드러운 복구 메시지 / 반복 실패 경고 / 명확한 퇴화 징후일 때의 강한 교정 지시. 즉 개입의 세기가 궤적 상태에 따라 단계적으로 올라간다.

Algorithm 1 — 네 층이 결합된 전체 루프

Algorithm 1: LIFE-HARNESS loop
  Input: task x, environment E, contract C, budget B

1   C' ← EnvContract(C);   x' ← SkillLayer(x)          ← ❶ ❷ (상호작용 전, 1회)
2   s₀, o₀ ← E.Init(x');   τ₀ ← (C', x', o₀)
3   for t = 0, …, B−1 do
4       a_t ← LLM(τ_t)                                  ← frozen 모델, 여기서만 호출된다
5       z_t ← RealizeAction(a_t, τ_t, C', s_t)          ← ❸ (실행 전)
6       (s_{t+1}, o_{t+1}) ← ExecuteOrBlock(E, s_t, z_t)
7       τ_{t+1} ← τ_t ⊕ (z_t, o_{t+1})
8       τ_{t+1} ← RegulateTrajectory(τ_{t+1}, C', s_{t+1})   ← ❹ (실행 후)
9       if IsEnd(s_{t+1}, o_{t+1}) then
10          break
11      end
12  end

이 의사코드에서 읽어야 할 세 가지: ⑴ line 4가 유일한 모델 호출이다 — 나머지 전부가 harness다. ⑵ line 7이 $z_t$를 궤적에 넣는데, 이는 실행된 행동이 아니라 harness의 결정($\textsc{Exec}$ 또는 $\textsc{Block}$)이 기록된다는 뜻이다 — 차단당한 사실 자체가 모델의 다음 컨텍스트에 남는다. ⑶ line 8이 $\tau_{t+1}$을 받아서 $\tau_{t+1}$을 반환한다 — ❹는 관측을 사후 편집하는 층이다.

4.4 궤적 주도 harness 진화

절차: Life-Harness는 coding agent Codex의 도움으로 학습 궤적에서 진화한다. frozen 모델을 학습 과제에 반복 실행해 완전한 상호작용 trace를 수집하고, coding agent가 그 trace를 harness 설계 기준과 함께 읽어 해당 층에 대한 업데이트를 제안한다. 목표는 둘이다:

  1. 커버리지 확장 — 반복되는 실패 패턴에 대한 harness 대응 범위를 넓힌다
  2. 회귀 탐지 — 개입이 과도 발동하거나 원래 올바르던 행동을 해치는 경우를 찾는다

§5 실험

5.1 실험 설정

벤치마크: 세 스위트에서 7개 과제 시나리오 — τ-bench(Airline, Retail), τ²-bench(Telecom), AgentBench(ALFWorld, WebShop, OS, DBBench). 논문이 밝히는 선정 기준이 중요하다: 이 벤치마크들은 안정적 환경과 결정론적 과제라는 성질을 공유하며, 그래서 런타임 harness가 레버리지가 큰 적응 대상이 된다. 즉 이 선정 자체가 방법의 적용 범위를 규정한다.

모델: harness 진화의 소스 모델은 Qwen3-4B-Instruct 하나뿐이다. 학습 과제에 실행해 궤적을 모으고, Codex가 trace를 검사해 harness를 반복 갱신한다. 진화 과정에서 테스트셋은 항상 은닉된다. 최종 진화된 harness는 동결되어 나머지 17개 오픈소스 백본 평가에 그대로 재사용된다. 모델 집합은 Qwen 계열, Llama 계열, xLAM 계열을 아우르며 instruction-tuned·reasoning·agentic 사후학습 모델을 포함한다.

평가 파라미터: 모든 평가가 sampling temperature 0.0. τ-bench와 τ²-bench는 DeepSeek-V4-Flash를 user LLM으로 쓰고 각 과제를 3회 평가하여 단일 실행 성공률과 Pass^3(3회 전부 성공해야 함)를 함께 보고한다. AgentBench는 공식 구현을 따라 1회 평가한다.

5.2 주요 결과

이 절이 답하려는 질문: 논문은 세 질문을 순서대로 던진다. ⑴ harness가 성능을 올리는가, 그리고 얼마나? ⑵ Qwen3-4B-Instruct 하나로 진화한 harness가 다른 백본에 전이되는가? ⑶ 그 전이가 성립한다면, 그것은 harness가 모델 특정 행동이 아니라 환경 쪽 구조를 포착했다는 뜻인가?

결과 ⑴ — 일관된 개선: Life-Harness는 모든 벤치마크에서 성능을 개선하며 상대 이득은 10~84%다. 논문의 부수적 관찰: "진화된 런타임 harness와 함께라면 더 작은 모델이 훨씬 큰 베이스라인과 경쟁할 수 있다."

패턴 분석: 덤벨 차트에서 두 가지가 읽힌다. 첫째, 출발점이 낮을수록 이득이 크다 — ALFWorld(41.1 출발, +84%)가 최대이고 Retail Pass@1(56.2 출발, +10%)이 최소다. 둘째, 더 흥미롭게도 ##Pass^3의 상대 이득이 Pass@1보다 일관되게 크다## (Airline +50% vs +26%, Retail +19% vs +10%, Telecom +27% vs +25%). Pass^3은 3회 전부 성공해야 하므로, 이는 harness가 평균 성능뿐 아니라 실행 간 일관성을 올린다는 뜻이다 — 결정론적 검증·차단이 "운 좋으면 되고 아니면 안 되는" 변동을 줄이기 때문으로 해석할 수 있다. 논문은 이 패턴을 명시적으로 논평하지 않는다.

결과 ⑵·⑶ — 광범위한 전이: Life-Harness는 Qwen3-4B-Instruct 궤적만으로 진화했음에도 다른 백본에 폭넓게 일반화된다 — 모든 model–benchmark 설정의 92%가 개선되며, instruct 모델, reasoning 모델, agentic 과제 특화 학습 모델을 모두 포함한다. 논문의 결론: "이 결과는 Life-Harness가 모델 특정 행동이 아니라 재사용 가능한 환경 쪽 구조를 포착함을 시사한다."

그러나 행렬을 자세히 보면: 92%라는 집계 수치가 감추는 구조가 있다. 개선에 실패한 10칸 중 9칸이 reasoning 계열 6개 모델에 몰려 있고, 나머지 12개 모델의 84칸에서는 단 1칸(Llama3.1-8B의 Retail −0.01)뿐이다. 즉 reasoning 계열의 개선율은 78.6%(33/42), 나머지는 98.8%(83/84)다. 평균 이득으로 보면 격차가 더 뚜렷하다. (18개 백본 전부의 벤치마크별 w/o·w/ 절대 성능은 원문 부록 B Table 8에 실려 있으며, 아래 히트맵은 그 차분값이다.)

진화 동역학 — 몇 번 돌려야 하는가

실험 의도: harness 진화가 실용적인가를 묻는다. 만약 수십 번의 반복이 필요하다면 "재학습보다 싸다"는 주장이 흔들린다.

결과: Figure 6은 Life-Harness가 각 과제에서 반복 진화될 때 Qwen3-4B-Instruct의 학습셋 성능을 보여 준다. 성능은 진화 라운드에 걸쳐 꾸준히 개선되다가 결국 포화한다. 논문의 해석: "반복적 harness 진화가 실용적이고 효율적임을 시사한다. 이 빠른 수렴은 4층 설계의 이점을 반영하기도 하는데, 업데이트가 제약 없는 전체로 harness를 다시 쓰는 대신 식별 가능한 실패 모드에 국소화되기 때문이다."

prompt 최적화와의 비교 — harness는 prompt의 상위집합인가

실험 의도: 가장 중요한 반증 가능성 검사다. 만약 Life-Harness의 이득이 사실상 "더 좋은 prompt"에서 온 것이라면, 인터페이스 적응이라는 이 논문의 프레이밍은 불필요한 포장이 된다. 그래서 저자들은 입력 prompt만 반복 최적화하는 prompt-only evolving(GEPA, OPRO 계열)과 직접 비교한다.

결과: prompt-only도 완만한 이득을 주지만, Life-Harness는 실질적으로 더 높은 Pass@1을 달성한다 — ##평균 상대 개선 120%를 추가##한다.

이 실험이 뒷받침하는 주장: 논문의 해석이 명확하다. "이 격차는 agentic 과제의 핵심 성질을 부각한다 — 성능은 초기 prompt만이 아니라 런타임이 도구·행동·피드백·다단계 궤적을 매개하는 방식에 달려 있다." 즉 §배경 4에서 그린 커버리지 그림(❸❹는 에피소드가 시작된 뒤에 작동하므로 prompt에 담을 수 없다)이 수치로 확인된 것이다.

5.3 Ablation — 네 층 중 무엇이 실제로 일하는가

실험 의도: 4층 설계가 사후 정당화가 아니라 필요한 분해임을 보여야 한다. 층 하나씩 제거하는 leave-one-layer-out을 Qwen3-4B-Instruct에서 수행한다.

결과와 논문의 결론: "네 층 모두 불가결하다 — 어떤 층을 제거해도 일부 데이터셋에서 실질적 성능 하락이 발생한다. 또한 과제마다 다른 층에서 이득을 얻으며, 이는 각 과제 환경의 서로 다른 특성을 반영한다."

패턴 분석 — 논문이 짚지 않는 세 가지:

  1. 층별 기여도의 분산이 극단적이다. ❸ Action은 Airline −61.7%, OS −59.6%로 지배적인데 ALFWorld에서는 −1.0%다. ❹ Trajectory는 정반대로 ALFWorld −86.5%, Airline −3.3%다. 즉 같은 harness가 환경에 따라 완전히 다른 이유로 작동한다 — 이것은 "재사용 가능한 환경 쪽 구조"라는 주장과 정합적이지만, 동시에 새 환경에서 어느 층이 중요할지 예측할 수 없다는 뜻이기도 하다.
  2. Retail만 균등하다. 네 층이 −15.9 ~ −17.5%로 거의 같다. 이는 Retail의 실패가 특정 단계에 몰려 있지 않고 생애주기 전반에 퍼져 있음을 시사한다. 흥미롭게도 Retail은 §5.2에서 상대 이득이 가장 낮은(Pass@1 +10%) 환경이기도 하다 — 개선 여지가 고르게 흩어져 있으면 어느 층도 큰 지렛대를 얻지 못한다는 해석이 가능하다.
  3. ALFWorld 열이 통계적으로 수상하다. ❹를 뺀 세 층이 정확히 −1.0%로 동일하다. ALFWorld 테스트셋이 109개 과제이므로 1/109 ≈ 0.92%이며, 이는 세 조건 모두 과제 1개 안팎만 달라졌음을 시사한다. 즉 "네 층 모두 불가결"이라는 주장은 ALFWorld에 관한 한 ❹ 하나에만 근거한다. 논문은 이 열을 논평하지 않는다.

모델 학습이 harness의 필요를 없애는가

실험 의도: 가장 직접적인 경쟁 가설에 대한 검사다 — "도구 사용을 제대로 학습시키면 harness 따위는 필요 없지 않은가?" 저자들은 xLAM-2-32B를 대표 학습 모델로 쓴다. 이 모델은 Qwen2.5-32B-Instruct에서 초기화되어 τ-bench 관련 도구 사용 시나리오로 추가 학습된 것이므로, 같은 base에서 갈라진 "학습 버전"과 "harness 버전"을 직접 비교할 수 있다. 이 통제가 이 실험의 설계상 강점이다.

논문이 읽어내는 세 패턴:

  1. harness가 특화 학습을 능가할 수 있다 — 가중치 갱신 없이. Life-Harness를 장착한 Qwen2.5-32B가 in-domain τ-bench에서 xLAM-2-32B를 7.5%p 앞선다 (0.579 vs 0.504).
  2. 학습 후에도 harness는 유익하다. xLAM에 Life-Harness를 적용하면 평가된 모든 벤치마크 그룹이 6.8 ~ 28.9%p 개선된다.
  3. 특화 도구 사용 학습이 OOD로 반드시 전이되지는 않는다. τ²-bench와 AgentBench에서 xLAM이 자기 base인 Qwen2.5보다 낮다 — OOD 일반화가 저하되었음을 시사한다. 같은 추세가 Llama-3.1-8B-Instruct에서 학습된 xLAM-2-8B에서도 관측된다.
논문의 종합: "학습과 harnessing은 에이전트 시스템의 다른 부분을 적응시킨다 — 학습은 모델 파라미터를 소스 분포에 맞추고, Life-Harness는 런타임 인터페이스를 타깃 결정론적 환경에 맞춘다. 따라서 harnessing은 재사용 가능한 환경 쪽 구조를 겨냥하며, 모델 무관하고 모델 학습에 보완적이다."

이 그림에서 가장 강한 수치: AgentBench 패널이다. xLAM-2-32B는 0.231인 반면 그 base인 Qwen2.5-32B는 0.498로, ##특화 학습이 out-of-domain에서 26.7%p의 순손실을 낸다##. 그리고 harness를 얹으면 xLAM이 0.520까지 회복한다 — 즉 harness가 특화 학습의 부작용을 상당 부분 되돌린다. 이것은 논문이 "mitigates the limited OOD transfer"라고 요약한 내용의 가장 극적인 사례다.

§6 결론과 Limitations

결론: 논문은 Life-Harness를 "결정론적 LLM 에이전트를 위한 lifecycle 인식 런타임 harness"로 정리한다. 모델 파라미터를 갱신하는 대신 학습 궤적에서 재사용 가능한 인터페이스 개입을 진화시키며, 그 범위는 환경 계약·절차적 skill·행동 실현·궤적 규제에 걸친다. 7개 환경 18개 백본에서 광범위한 성능 향상을 달성하면서 모델 가중치와 평가 환경을 모두 고정한다. 결론 문장: "많은 에이전트 실패가 frozen LLM과 규칙 지배 환경 사이의 런타임 인터페이스를 적응시킴으로써 완화될 수 있으며, 이는 모델 중심 에이전트 학습에 대한 보완적 대안을 제공한다."

저자들이 밝히는 한계: 이 연구는 도구 인터페이스·피드백 규칙·평가 기준이 비교적 안정적인 결정론적·규칙 지배 환경에 초점을 맞춘다. 이 설정은 DB 조작, 웹 쇼핑, 정책 기반 비즈니스 워크플로우에서 흔하며, 실패를 재현하고 재사용 가능한 harness 개입으로 변환할 수 있게 해 준다. 선행 런타임 harness 연구도 주로 인터페이스와 과제 구조가 잘 정의된 coding·텍스트 에이전트에 집중해 왔다.

그러나 저자들은 이렇게 인정한다 — "같은 아이디어를 완전히 오픈엔디드한 에이전트 과제로 확장하는 것은 여전히 어렵다. 오픈 도메인 환경에서는 각 과제가 서로 다른 목표·도구·외부 자원·성공 기준을 가질 수 있어, 안정적 런타임 인터페이스를 정의하거나 임의의 과제에 일반화되는 harness를 진화시키기가 더 어렵다." 오픈엔디드 환경에서의 harness 구성이 향후 연구의 중요한 방향이라는 것이 논문의 마무리다.

AI 도구 사용 공개: 부록 C에서 밝히듯 언어 다듬기에 AI 어시스턴트를 사용했고, 실험 구현에서는 런타임 harness의 반복 개발을 Codex가 보조했다. 모든 실험 설계·분석·최종 결과는 저자가 검토·검증했다고 명시한다.

비판적 분석

강점

  1. 진단이 설계에 선행한다. 이 논문의 가장 방법론적으로 견고한 점이다. 393개 실패 에피소드를 우선순위 프로토콜로 수동 분류하고, 그 결과 나온 네 범주에 일대일 대응하는 네 층을 만든다. harness 논문 상당수가 "그럴듯한 컴포넌트 모음"을 제시하는 데 그치는 것과 대조된다. 게다가 부록 A.1이 분류 규칙 전문을 싣고 있어 재현·재검증이 가능하다.
  2. 전이성 검증의 통제가 강하다. harness를 단 하나의 소스 모델(Qwen3-4B-Instruct) 궤적으로만 진화시키고 나머지 17개에 그대로 적용한 것은, "환경 쪽 구조를 포착했다"는 주장에 대한 가장 직접적인 검사다. 백본마다 다시 진화시켰다면 이 주장은 검증 불가능했을 것이다.
  3. xLAM 비교의 설계가 좋다. xLAM-2-32B가 Qwen2.5-32B-Instruct에서 파생되었다는 사실을 이용해, 같은 base에서 갈라진 "학습 경로"와 "harness 경로"를 직접 대조한다. 게다가 in-domain(τ-bench, xLAM의 학습 분포)과 OOD(τ²-bench, AgentBench)를 분리해 특화 학습의 부작용까지 드러낸다. 이는 harness 논문에서 보기 드문 수준의 반증 설계다.
  4. 재현성 자산이 충실하다. 진화 prompt 전문(부록 A.2), 4층 설계 원칙, 회귀 검사 절차, 그리고 7개 환경 전부에 대한 최종 harness 인벤토리(Table 5·6·7)가 실려 있다. 코드도 공개된다. 인벤토리는 "이 방법이 실제로 무엇을 하는지"를 은폐하지 않는데, 이 투명성 덕분에 아래 4번 우려를 독자가 직접 판단할 수 있다.
  5. 범위 제약을 스스로 명시한다. 진화 prompt가 테스트 라벨 사용·과제 수정·환경 전이 변경·평가 기준 변경을 금지하고, "정답이 모호할 때 모델 추론을 override하지 말 것"을 명령한다. 그리고 Limitations에서 오픈엔디드 확장의 어려움을 인정한다.

한계와 의문점

  1. 88.5%라는 헤드라인 수치는 비율의 평균이며, 작은 분모에 의해 팽창한다. 벤치마크 수준에서 보면 상대 이득은 10~84%(단순 평균 33.4%), 절대 이득은 평균 13.8%p다. 126개 설정의 개별 상대 이득을 평균하면 88.5%가 나오는데, 이는 baseline이 0.05인 설정이 0.82로 오르면 +1,540%가 되기 때문이다. 두 수치가 다 사실이지만 독자가 받는 인상은 크게 다르다.
  2. 분산 추정치가 논문 전체에 없다. temperature 0.0이고 AgentBench는 1회 평가이므로 표준편차·신뢰구간이 존재하지 않는다. τ-bench의 3회 반복은 temperature 0에서 user LLM 쪽 변동만 반영한다. 문제는 테스트셋이 작다는 점과 겹친다 — Airline 테스트는 20과제이므로 1과제 = 5%p이고, Retail·Telecom은 40과제(1과제 = 2.5%p)다. Table 1에서 Retail Pass@1 +5.6%p는 40과제 중 2.2과제에 해당한다.
  3. reasoning 계열에서 방법이 거의 작동하지 않는데, 논문이 이를 언급하지 않는다. Figure 5를 계산해 보면 그룹 평균이 Instruct +0.185, Agent-trained +0.196, Reasoning +0.059다. 개선 실패 10칸 중 9칸이 reasoning 6개 모델에 몰려 있다(개선율 78.6% vs 나머지 98.8%). Qwen3.6-27B는 평균 +0.016으로 사실상 0이다. 두 해석이 가능하고 함의가 정반대다 — ⑴ 강한 reasoning 모델은 인터페이스 실패가 애초에 적다(harness의 자연스러운 한계, 좋은 소식), ⑵ harness가 Qwen3-4B-Instruct의 실패 분포에 과적합되었다(전이성 주장의 약화). reasoning 모델 하나로 harness를 재진화시키는 ablation 하나면 판별되는데, 그 실험이 없다.
  4. "안정적 환경 구조 노출"과 "정답 유출"의 경계가 자체 판정에 맡겨져 있다. Table 5의 Airline 항목을 보면 $\Delta_C$가 "네 가지 유효 취소 조건", "최대 5인 승객", "인증서 1개 제한, 신용카드 1개, 기프트카드 3개", "정확한 수하물 요금과 결제 총액"을 명시한다. 이것들은 분명 환경에 원래 존재하는 규칙이지만, 동시에 τ-bench 채점 기준과 매우 가깝다. 진화 prompt가 유출을 금지하고 저자가 검토했다고는 하나, 경계 판정에 외부 감사나 정량적 기준이 없다. 재현성 자산이 공개되어 있으니 후속 연구가 검증할 수 있다는 것이 그나마의 안전장치다.
  5. ALFWorld ablation 열이 사실상 한 층에만 근거한다. ❹를 제외한 세 층 제거가 정확히 −1.0%로 동일한데, 테스트 109과제 기준 1/109 ≈ 0.92%이므로 세 경우 모두 1과제 안팎만 변했다는 뜻이다. "네 층 모두 불가결하다"는 주장은 ALFWorld에서는 성립하지 않는다.
  6. harness 진화의 비용이 보고되지 않는다. "재학습보다 싸다"가 이 논문의 실용적 판매 논거인데, Codex 반복 5회에 든 토큰·시간·달러가 어디에도 없다. 반면 비교 대상인 fine-tuning의 비용도 보고되지 않으므로, 비용 비교는 정성적 수준에 머문다. §적응 비용 스케일링 그림의 y축이 "실행 횟수"이지 FLOPs가 아닌 이유다.
  7. 선행 harness 연구와의 직접 비교가 없다. §2가 Meta-Harness, AHE, HARBOR, Workspace Optimization을 상세히 논하지만 같은 벤치마크에서 성능을 비교하지 않는다. 실제 비교 대상은 prompt-only evolving 하나뿐이다. "4층 국소화가 자유형 코드 탐색보다 빨리 수렴한다"는 주장도 자기 방법의 수렴 곡선만 있고 대조군이 없다.
  8. Table 5~7을 보면 "harness"가 사실상 환경별 규칙 집합이다. Airline 한 환경의 인벤토리만 해도 book_reservation 검사 6종, update_reservation_flights 차단 6종 등 수십 개 규칙이다. 이는 방법의 효과를 설명하기도 하지만, 동시에 이 접근이 일반 원리를 학습한 것이 아니라 환경별 규칙 하드코딩을 자동화한 것이라는 해석을 열어 둔다. 새 환경마다 이 규모의 진화가 필요하다면 "환경 하나당 한 번"이라는 비용도 가볍지 않다.
  9. 잔여 추론 실패 9.9%는 하한이지 상한이 아니다. harness가 인터페이스 실패 90.1%를 전부 잡는 것도 아니다. 실제로 Table 1에서 harness 적용 후에도 ALFWorld 75.7%, Retail 61.8%로 여전히 상당한 실패가 남는다. 남은 실패의 구성이 어떻게 바뀌었는지 — 즉 harness 적용 후 실패 분포를 재진단한 결과 — 가 있었다면 방법의 도달 범위를 훨씬 명확히 알 수 있었을 것이다.
  10. 소스 모델 선택의 민감도가 검증되지 않았다. Qwen3-4B-Instruct는 상대적으로 약한 모델이라 실패가 많고 따라서 진화 신호가 풍부하다. 이것이 우연한 좋은 선택인지 필연인지 알 수 없다. 더 강한 모델로 진화시키면 harness가 더 정교해질까, 아니면 신호가 부족해 빈약해질까? 논문은 답하지 않는다.

Key Takeaways

  1. "에이전트 적응 = 모델 적응"이라는 기본 가정을 실증적으로 흔든다. 결정론적 환경에서 실패의 90.1%가 인터페이스 문제이고 순수 추론 실패는 9.9%에 불과하다는 393개 에피소드 진단이 이 논문의 진짜 기여다. 이 숫자 하나가 "왜 harness인가"에 답한다.
  2. 진단 → 층 설계의 일대일 대응이 재사용 가능한 방법론이다. 자기 시스템의 실패 로그를 가장 이른 지배적 병목 기준으로 분류하고, 각 범주를 상호작용 생애주기의 어느 단계에서 막을 수 있는지 매핑하는 절차는 이 논문의 4층 구조와 무관하게 쓸 수 있다. 부록 A.1·A.2의 프로토콜과 prompt를 그대로 가져다 쓸 수 있게 공개해 둔 것도 실용적이다.
  3. ##한 모델의 궤적으로 진화한 인터페이스 개입이 17개 다른 모델에 전이된다##는 것이 가장 강한 실험적 발견이다. 이는 harness가 모델 특정 행동이 아니라 환경 쪽 구조를 포착한다는 뜻이며, 실무적으로는 모델을 교체해도 harness 자산이 유지된다는 의미다. 모델 교체 주기가 짧은 프로덕션 환경에서 이 성질의 가치는 성능 수치보다 클 수 있다.
  4. 특화 학습이 OOD에서 순손실을 낼 수 있다는 반례가 제시된다. xLAM-2-32B가 AgentBench에서 자기 base인 Qwen2.5-32B보다 26.7%p 낮다. 도구 사용 SFT (supervised fine-tuning)를 검토 중이라면 학습 분포 밖 성능을 반드시 측정해야 한다는 경고로 읽어야 한다. 그리고 harness가 그 손실을 상당 부분 되돌린다는 것이 이 논문의 부수적 발견이다.
  5. 실행 전 검증(❸)과 실행 후 규제(❹)는 prompt로 대체할 수 없다. prompt-only 대비 +120% 상대 개선의 구조적 이유는 성능 차이가 아니라 도달 가능 범위의 차이다 — 초기 prompt는 에피소드가 시작된 뒤의 상태를 볼 수 없다. 에이전트 시스템을 설계할 때 "프롬프트 엔지니어링"과 "런타임 엔지니어링"을 분리해서 생각해야 하는 이유다.
  6. 층별 기여도가 환경마다 극단적으로 다르다(❸ Airline −61.7% vs ALFWorld −1.0%, ❹ ALFWorld −86.5% vs Airline −3.3%). 새 환경에 harness를 도입할 때 어느 층이 중요할지 미리 알 수 없으므로, 네 층을 모두 갖춘 뒤 실패 진단으로 우선순위를 정하는 순서가 실무적으로 맞다.
  7. 비판적으로 — 이 방법은 모델이 약할수록 잘 듣는다. Figure 5를 계산하면 reasoning 계열의 평균 이득은 +0.059로 instruct(+0.185)·agent-trained(+0.196)의 약 1/3이고, 개선 실패 10칸 중 9칸이 그 그룹에 몰려 있다. 논문은 이 패턴을 언급하지 않는다. 만약 원인이 "강한 모델은 고칠 인터페이스 실패가 적어서"라면 harness의 가치는 모델이 좋아질수록 줄어든다는 뜻이고, "harness가 소스 모델의 실패 분포에 과적합돼서"라면 전이성 주장 자체가 약해진다. ##reasoning 모델로 harness를 재진화시키는 ablation 하나면 판별되는데 그 실험이 없다## — 이 논문을 후속 연구로 이어갈 때 가장 먼저 채워야 할 빈칸이다.
